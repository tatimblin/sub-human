# Architecture

How sub-human works today, for a new contributor or a fresh Claude session. User-facing behaviour is in [`plugin/sub-human/README.md`](../plugin/sub-human/README.md); the Claude Code internals behind it are in [`docs/internals/cc-2.1.281.md`](internals/cc-2.1.281.md), with the 2.1.292 and 2.1.296 changes in [`docs/internals/cc-2.1.292.md`](internals/cc-2.1.292.md) and [`cc-2.1.296.md`](internals/cc-2.1.296.md), and the native task files and plan mode the room's tasks and plans use in [`cc-2.1.296-tasks-plans.md`](internals/cc-2.1.296-tasks-plans.md). Sections marked *generated* are rewritten by `npm run docs` (`scripts/arch-doc.ts`) from the code; edit the code, not the table. `npm test` fails when they are stale.

## Purpose and design rules

Several people, each in their own Claude Code session, share a **room**. The room lives on one machine (its host); people on other machines join it over a link (see [Remote rooms](#remote-rooms)). A person's exact words reach the room only through a hook (`@room …`). Claudes talk to each other with native `SendMessage`, addressed `NAME.CODE`. A headless **room session** (member `claude`, `claude.CODE`) shows the room's task list, which the plugin writes from the log, and keeps the agent-panel rows; its model never plans, posts or answers. The room keeps **plans** with versions: a member's Claude edits one in its person's own plan mode, and the hooks store each version. Sign-off on a version is recorded only from the person's own answer in a native dialog.

The one security goal: **a model can never speak or consent as a person.** The rules that follow from it, and from keeping the plugin unobtrusive (also in `CLAUDE.md`):

- Never pin a model (agents, the room session's spawn, the demo, tests).
- No writes to user settings files and no symlinks into `~/.claude`. The plugin keeps its own home; under Claude Code's config dir it writes only the room session's native task files and, during an edit or a review, the member's own session plan file (Tasks, Consent).
- The room's Claude (the room session) takes no typed input. People type in their own session: `@room` for the room, or ask their own Claude.
- Keep the agent-panel rows (the room row with members nested in it; the room session's panel lists every human).
- Consent is native: plan view first, question card as fallback; where the plan view cannot take a sign-off on a Claude Code version (the verdict's `sign-off` off), Claude Code's own MCP question (the plan tool's `signoff`); only `via=human` answers count.
- Unprescriptive: no required workflow; injected text covers mechanics only.
- Every undocumented Claude Code behaviour relied on is listed in `lib/cc/contract.json` and checked by `npm run probe`.
- Zero dependencies, Node 22.18+ or 24.3+, macOS/Linux. The runtime is ESM TypeScript with no build step (see [TypeScript](#typescript)); the plugin's node tests (`plugin/sub-human/test/**/*.node-test.ts`) are ESM TypeScript run the same way; repo `scripts/` and their tests are ESM TypeScript too; the module's wiring tests (`mod/test/*.test.ts`) run under `claude plugin test`.

## Process model

```
 member session (claude, interactive)                    the room session (claude --bg, one per room, idle)
 ┌──────────────────────────────────────────┐            ┌───────────────────────────────────────┐
 │ main thread (the person's Claude)        │  (inbound  │ main thread: agent sub-human:room-claude
 │   spawns ─► room row  (agent room, bg)   │  refused)  │   rows-only turns: participant rows   │
 │               spawns ─► participant rows │            │   native task list sh-CODE: written   │
 │ hooks: one hooks module (+3 command hooks)│            │     by the plugin from the log        │
 │ tail child: scripts/sub-human tail (module)  │            │ hooks: the same, module included       │
 │ MCP: mcp/room-server.ts (+hold, +task)   │            │ tail child (joins, watchdog, tasks)   │
 │ opt-in subagentStatusLine (user settings)│            └───────────────────────────────────────┘
 └──────────────┬───────────────────────────┘                             │
                │          all read/write through lib/room/store.ts       │
                └────────────────► <home>/rooms/<CODE>/ ◄─────────────────┘
```

Per session, Claude Code starts:

- **Hooks.** The hooks module (`mod/register.ts`) runs in-process in every session: the store guard, the prompt gate, the delivery, and shims that start node only where a handler can act (`mod/core/prefilter.ts`; table below). Every node start of a hook is one entry, `node --import hooks/compile-cache.js hooks/run.ts <handler>`: it reads stdin once, loads only `hooks/handlers/<handler>.ts` and writes that handler's one answer at the edge (`hooks/reply.ts`; the `Reply` type in `hooks/types.ts`: the join's `say`, `refused`, `secret` and `joined`, every other hook's `classic` lines, exit code and stderr). `hooks.json` keeps three command hooks: the `/sub-human` expansion (`join`, behind the node version check), `SessionEnd` (`session-end`, behind a shell check that starts node only for a session with a lease, a session index or a seat by pid), and a PreToolUse on `EnterPlanMode` that starts no node: for a session with a session index, a few shell lines write the call's `permission_mode` to `<home>/sessions/mode/<sid>`, which consent reads (once, while fresh) as the mode the review must put back, since the module's own PreToolUse event carries none and its last-seen mode is stale after a shift+tab mid-turn. The module runs the rest with `$.process.run`: `prompt` (at-room and consent's prompt handler in one process), `consent` (the plan-view review and a room plan edit), `presence`, `row-guard`, `row-map`, `row-hold`, `row-rewake`, `session-restore` and `mod-hello` (the hello, below). Shared pieces: `hooks/seat.ts` resolves the seat (no signer), `hooks/context.ts` builds the mechanics block, `hooks/launcher.ts` writes the launcher of the opt-in row status line. Only the handlers that sign arm the seat key's signer (`at-room`, `consent`, `join`: `hooks/seat-key.ts` arm); the room MCP server's plan `signoff` loads the key for one answer only (`signing`, below). Identity comes from the payload's `session_id`, then `CLAUDE_PID` (Claude Code sets it for a command hook; `hooks/run.ts` sets it to its parent, the claude process, for one the module runs); the tail child finds its seat by the `CLAUDE_CODE_SESSION_ID` the module gives it; see Identity and liveness.
- **The tail child** (`mod/deliver.ts` starts `scripts/sub-human tail --ndjson` → `lib/tail.ts` with `$.process.spawn`): one per seated session (and per seatless session whose PIN join waits for the host's card: below), for the session's life, restarted with backoff if it exits. It follows the seat's room and writes one JSON event per line, which the module routes: `chat` → `$.ui.log` (a dim notice the person sees; no model turn), `pull` → held in `$.state` (`pulls`, the newest lines under `PULL_CAP`) and carried as context beside the next prompt that starts a turn (`mod/prompt.ts`: prompt.submit's `context`, or classic UserPromptSubmit `additionalContext` for a prompt the plugin submits from inside its own hook), never a user row of its own: a row of it, then an `@room` and its stop, then the person's prompt, with no assistant turn between, read as one user turn whose last line was an unattributed room line (stage 8e B); a prompt the plugin stops (an `@room`'s receipt) starts no turn, so the context waits for the next, `wake` → `$.prompt.submit` (origin `plugin`; a member's wake goes `asUser` with only its lines for the person, its `(for Claude)` lines as context, since Claude Code never asks a plugin to redraw its own prompt (CONTRACT `render-own-prompt-reentry`); folded into a running turn instead when busy), `rows` → held for the person's next prompt. It is the seat's only delivery, which is why a seat needs the module: the join (`lib/commands/index.ts`) refuses without its hello lease. A line is sent at most once (the tail's cursor moves when the line is written). A wake whose submit is dropped by a hook or fails falls back to the isMeta append, and when that fails too it is held and appended at the next `turn.start`, so it arrives once; its room lines (not the `(for Claude)` ones) are then logged as notices, since no prompt row shows them. Every delivery failure (an event not applied, a child that exited or did not start, a wake nothing took) adds to `$.state` `deliveryErrors` and shows one dim notice, at most every 5 min: "a room message could not be delivered; `sub-human read` shows the room".
- **Remote Control.** Nothing is phone-specific: a prompt typed through Remote Control (prompt.submit origin `bridge`) counts as typed, so a phone-typed `@room` posts; the join's and consent's refusals are `systemMessage`s, which the bridge forwards; a `$.ui.log` notice stays in the terminal.
- **The MCP server** (`.mcp.json` → `mcp/room-server.ts`): stdio JSON-RPC, one per session. Its plug-ins `mcp/hold.ts` and `mcp/task.ts` add tools. It resolves the caller from `process.ppid` on every call. It cannot sign `via=human`, but for the sign-off fallback: plan `signoff`, only while the verdict turns `sign-off` off, sends one `elicitation/create` (cc CONTRACT `mcp-elicitation`), which Claude Code draws as its own dialog the model never sees, and records the person's agree or object as theirs, signed with the seat key armed for that one append (`hooks/seat-key.ts` signing; refused unless the server's parent is the seat's Claude Code). `docs/internals/cc-2.1.302-elicitation.md` has what was checked.
- **Rows**: background subagents that make one blocking MCP call (`hold`) and stream progress, so they cost no tokens while they hold. Their panel text is their name, and the room's state when the person opts in: the plugin sets no `subagentStatusLine` (a plugin settings.json command gets no `${CLAUDE_PLUGIN_ROOT}`, and the plugin directory refuses a path the shell computes) and writes no settings file, so the README's "Rows" gives the line a person adds to their own user settings, `"${SUB_HUMAN_HOME:-$HOME/.sub-human}/bin/row-status"`, the launcher `hooks/launcher.ts` writes on a join or a restore, which runs `sub-human agent-statusline` (`statusline/`).

Who spawns whom:

| Spawner | Spawns | How |
|---|---|---|
| `hooks/handlers/join.ts` → `lib/seats.ts` ensureRoomClaude (first member, or a room with no live room session; host only) | the room session | claim under the members lock, `openTaskList` (records `members.claude.tasks_dir` and makes the directory), then detached `node lib/room-claude.ts start` → `claude --bg -n claude.CODE [--plugin-dir DIR] --agent sub-human:room-claude --permission-mode plan --settings {env…, crossSessionInbound: "refuse"} /sub-human` |
| a member's main thread | one `sub-human:room` row | the `Agent` call the join/restore context lists under ROWS |
| a room row | one `sub-human:participant` row per other member | on start, and when `hold({room})` returns `JOINED`/`RESPAWN` |
| the room session's main thread (its only tool: `Agent(sub-human:participant)`) | one participant row per human | the ROWS line of its launch turn, then a rows-only turn per `member_joined` whose row note says no row runs |
| the hooks module (`mod/deliver.ts`) | the tail child, per seated session | `$.process.spawn node scripts/sub-human tail --ndjson` |
| `hooks/handlers/session-end.ts`, `lib/room-claude.ts` watchdog | the reaper | detached `node lib/room-claude.ts reap CODE` |

The row hooks are the module's (`mod/rows.ts`), and start node only for a row agent (`sub-human:room`, `sub-human:participant`) in a seated session: `row-guard` (classic.PreToolUse Agent) denies a duplicate row spawn; `row-map` (PostToolUse) records which panel row is which agent; `row-hold` (SubagentStop) tells a row that gave up to hold again; `row-rewake` (classic.SessionStart resume, in the background) re-spawns rows after `--resume`: its row calls go to the model as a wake, one line shown to the person.

### Function hooks (generated)

The plugin ships one hooks module (Claude Code 2.1.292+). Its hooks run in-process, above the command hooks of the same event. `hooks/handlers/mod-hello.ts` (run by the module with `$.process.run`, not a hooks.json entry) writes the module's lease `<home>/sessions/mods/<sid>.json` and tells it the home, this session's seat and whether a SessionStart has a seat to put back (`restorable`), which it keeps in `$.state`. The module never writes room state. Its pure logic is in `mod/core/*.ts` (node-tested in `test/mod-core*.node-test.ts`), its wiring tests in `mod/test/*.test.ts` (`npm run test:mods`).

- **The lease** holds the claude pid (the hello's parent) and its start time, the time written, and the session's nonce (below). The join accepts a lease from this claude process, or one written within `MOD_LEASE_FRESH_MS`; `session-end.ts` deletes it, and join's sweep prunes leases whose process is gone. Without one the join is refused with `NO_MODULE`: Claude Code older than 2.1.292, `--bare`, safe mode, hooks modules turned off by policy, or an old session id resumed where the module is off.
- **The hello at session start** runs node only when the session may have a seat: its session index `<home>/sessions/by-sid/<sid>.json` exists (`$.fs.exists`; `mod/core/seat.ts` sidIndex, the path `lib/identity.ts` writes), or this process knew a seat before (a `/clear`). Otherwise the hello is the module's own (`localHello`: the home from `SUB_HUMAN_HOME` or `HOME` by `lib/home.ts`'s rule, its real path, no seat), so a session that never joins starts no node at all; its lease is written before its first `/sub-human` (`command.run`, or `classic.UserPromptExpansion` beneath when the module does not answer), since the join refuses a session without one.
- **The hello refresh** runs after the join and after a SessionStart restore. One that fails keeps the last hello (the guard still knows the home) but with `sid` null, as no session's, so every prefilter runs node until a refresh succeeds: a join whose hello failed must not make "no seat" look certain.
- **classic.PreToolUse carries the call alone** (`tool`, `tool_use_id`, the arguments), while `row-guard` and `consent` read `session_id`, `transcript_path`, `permission_mode` and `agent_id`. The module keeps the transcript path and mode of the last main-loop classic event it saw (UserPromptSubmit, PostToolUse, Stop, SessionStart, …) and the `agentId` a `tool.call` carried while that call runs (`mod/core/facts.ts`), and builds the payload from them. A mode changed with shift+tab in the middle of a turn is seen at the next event. Both classic.PreToolUse hooks call `next(e)` on every path and put their answer above what the hooks beneath said (`mergePre`: a deny wins, then an ask, then an allow; cc CONTRACT `classic-chain-order`); an allow's reason, which a command hook's allow showed the person, is a notice.
- **The tail child's life.** It starts on `session.start` (also after a reload or a lost worker), after the join and after `classic.SessionStart`, unless the hello is sure the session has no seat (and no PIN join of its own waiting: `pending`). A `/clear` runs on under a new session id: the old child is stopped and one is started for the new id; `session.end` stops the child for good. A child that exits is started again after 1 s, doubling to 60 s; one that ran over 60 s before it exited was healthy, and the backoff starts over. It dies with the module (a reload, the session's end): the `$.process.spawn` loop is its life.
- **Mid-turn wakes.** A wake while a main-loop turn runs (a `turn.start` with no `turn.complete` yet) is appended as an isMeta row, and its visible lines are logged. At that turn's `turn.complete` it is submitted after all when no main-loop tool call (`classic.PostToolUse` / `PostToolUseFailure` without `agent_id`) finished after the append: each finished call is followed by a model request, so without one the request then in flight was the turn's last and never carried the row. A wake neither a submit nor an append took is held for the next `turn.start` (at most `PENDING_MAX` 20, newest kept), when the session is evidently running turns again.
- **Presence** has one writer: the module runs `presence` (not awaited) when a typed prompt's turn starts ("working", unless it already wrote that for this seat; a prompt the plugin stops or refuses starts no turn and writes nothing), `Notification` (idle, permission), a tool call that finishes after a permission notification ("working" again), the end of a turn that was working or waiting on the person ("idle") and `StopFailure` (error). No other hook writes it: a seat just taken or put back has none until its person types.
- **`@room` fails closed.** When the prompt shim fails (it throws, times out or exits other than 0 or 2), an `@room` is blocked with the prompt suppressed, never handed to the model as typed text.
- **The session title** `NAME.CODE` is set once per session id and address, so a switch to another room retitles the session.
- **Shared constants and parsers live in `mod/core`.** What both the module and node read has one copy, in `mod/core` (pure, no imports): the `@room` parser, `TYPED_ORIGINS` and the refusal wordings (`mod/core/prompt.ts`), the nonce check `attested` (`state.ts`), the hidden-reply rule `mayHoldSecret` (`command.ts`), the name, code and session-id patterns (`seat.ts`), the row agent types (`rows.ts`), and the restart, notice and chat-line constants (`constants.ts`). `lib/` and the hook handlers import them from there (`lib/config.ts`, `lib/text.ts` and `lib/rows.ts` re-export theirs); nothing is copied, so no test pins copies.

## The room store

Everything persistent goes through the **RoomStore** interface in `lib/room/store.ts` (the header there is the full contract). `lib/room.ts` wraps it: `room.open(code) → Room` (cached per code, no process-wide state) adds delivery, rendering and the consent queries on top, each judged by the store's own trust.

The store is six files behind `store.ts`, each with one job:

| File | Job | I/O |
|---|---|---|
| `lib/room/trust.ts` | whether a `via=human` entry is the person's: `verdict(e, ctx)` over the keys a store passes in (`pins()`, the seat's local `.pub` for a legacy room); `trustOver(ctx)` is a store's `trust` | none |
| `lib/room/rules.ts` | what a placement checks and stamps: `toPayload`, `admit`, `scanTail`, the rates (`rated`: a `plan` entry counts toward none), `checkSigned`, `checkPin`, `placeAfter`, `blobRef`; `normalize` | none |
| `lib/room/log-io.ts` | the log's bytes, in segments with a snapshot: the cached `readAll`, `readView` and its in-memory checkpoint over the active segment, `verifyChain`, the tailer across segments, the locked append and the rotation | the log; imported by `fs-store.ts` alone |
| `lib/room/snapshot.ts` | what a snapshot holds of the sealed lines (`extend`), and whether one from another machine can be taken (`problem`) | none |
| `lib/room/fs-store.ts` | `FsRoomStore`: a room directory on this machine; `pins()` carried forward one new line at a time | the room's files (the only module that names them) |
| `lib/room/registry.ts` | which store a code opens (`open`, `setBackend`), the rooms on this machine, `trustOf(e)` (an entry judged by the store of the room it names) | the rooms directory; `keys.ts` the seats' public keys |

`MirrorRoomStore` (`lib/room/store-mirror.ts`, a room hosted elsewhere) composes an `FsRoomStore` over its mirror directory: every read is that store's, every write an op to the link daemon, and the daemon writes through the store's public `appendVerbatim` and `installSnapshot`. `test/store-bypass.node-test.ts` checks the seam structurally (only `fs-store.ts` imports `log-io.ts`; `FsRoomStore` is imported only by the registry, the mirror and the seam; the mirror extends nothing and calls no private member) and lexically only where an import graph cannot say it (no module outside the store's files names a room file or builds a path into one).

`readAll()` returns the store's cached array, frozen: a repeat read of an unchanged log is the same array, and callers never change it. The seat private keys stay local whatever the store; liveness falls back to the `seen_at` lease for a seat of another machine or with no pid. ## Entries and `via`

An entry is `{id, at, from, via, kind, text?, prev, …kind fields}`. `id` is monotonic, `prev` is `hash12` of the previous line, `from` comes from a trusted caller that resolved identity (never from env or the model). `lib/room/validate.ts` decides which `via` may write which kind:

| via | Kinds | Written by |
|---|---|---|
| `human` | `say`, `signoff`, `objection`, `proposal` | hooks only: `@room` (at-room.ts), the plan view / card answers (consent.ts) |
| `agent` | `say`, `question`, `status`, `proposal`, `task_req`, `plan` | the MCP server (`post`, `plan` ask: `lib/proposal.ts` ask, `task`) on behalf of a member's Claude (`task_req` appended by the host's apply). A `plan` entry (from the editing seat, `for` its person; `plan`, `version`, `base`, `summary`, `hash`, `path`) is written only by the host's `lib/plans.ts` put, which passes `{system: true}` (`validate.ts` `HOST_PUT_KINDS`): a link's `append` or the `post` tool cannot write one, so every version passed its compare-and-swap |
| `system` | `decision`, `member_joined`, `member_left`, `task`, `status` | hooks, the reaper and the host's task apply (`lib/tasks.ts`, from `room`), with `{system: true}` |

**Signing.** Every hook process runs `seat-key.arm()`, which installs a signer. `append` is `place(toPayload(…))`: `toPayload` validates and, for `via=human`, signs (sig v2, `lib/room/envelope.ts`: Ed25519 over the payload with sorted keys plus `room`, `from`, `nonce`, `ts`, without `id`/`at`/`prev`, so a payload signed on one machine can be placed on another). `place` validates again, refuses a replayed nonce or a `ts` outside `SIG_SKEW_MS`, verifies the signature, then stamps `id`, `at`, `prev` under the log lock. The CLI, tail and module never load `seat-key.ts`, and the MCP server loads it only lazily for plan `signoff`'s one append, holding no signer before or after (`test/hooks/security.node-test.ts`), so they cannot write `via=human` otherwise; the store refuses. Keys are pinned in the log: the join hook puts the seat's public key in `member_joined`, the first key seen per name is that name's key for the room's life, and a join with another key is refused (`AUTH`). Readers ask the store that read the entry, `store.trust(e)` (`lib/room/trust.ts`, explicit: the store's keys go in, nothing rides on the entry): `verified` (v2, or v1 from before the pin, against the pinned key, signed for this room; the local `.pub` only in a room that pins none), `legacy` (unsigned, in a room that pins no key, from a seat with no local key), or `unverified` (shown as `bob (unverified): …`, never counted for consent or tasks). `Room` passes its store's trust to every fold, render and delivery; a caller with an entry and no store uses `trustOf(e)` (the store of the room the entry names; an entry naming none is never verified). MCP `read` gives the model the rendered line (`render.line({full})`), so the marker is in what it reads.

**Hash chain, segments and the snapshot.** The log is cut into segments (`lib/room/log-io.ts`). Once an append leaves `log.jsonl` at `SEGMENT_MAX_BYTES` (1 MiB, about 5,000 lines), and only if every line of it chains, it is sealed: linked as the next `log-NNNN.jsonl`, `snapshot.json` written, and `log.jsonl` replaced by the sealed last line alone. Each segment's first line repeats the previous one's last, so the chain runs on across files unchanged (each line's `prev` is still the hash12 of the line before it in the log), an appender that knows only `log.jsonl` (an older plugin still running after an update) still finds the right `id` and `prev`, and every reader skips the repeat. A segment that does not chain is never sealed: a break is never laundered into a snapshot, and stays visible. A crash between the steps is finished by the next append; a lost `snapshot.json` is rebuilt from the sealed segments. (A process of 0.5.0-beta.15 or before, still running after an update, reads a rotated log as a broken chain: restart sessions after updating.)

The snapshot carries what a reader needs of the sealed lines: every non-chat entry (what decides delivery: plans, proposals, answers, decisions, joins, tasks; the consent fold's whole input), the pinned keys they give, and the window of entries the next placement looks back over (the rate buckets of the last minute, and the nonces of the last `2 × SIG_SKEW_MS`, so a payload replayed after a rotation is refused as before). `readView({after})` is that snapshot plus the active segment, read through a checkpoint each process keeps in memory, so a cold reader parses one segment: the pinned keys for a person's append, the status line's rows (`room.readRecent`: every non-chat entry and the lines since the last rotation), and the code that folds plans, proposals or tasks (`proposal.ts` ask, decide and the requests a hook asks for, the consent hook, `plans.ts` put, `tasks.ts` apply and repair: all read non-chat entries only). `readAll` still gives every line, from the sealed segments. A mirror that began from its host's snapshot keeps that snapshot as `snapshot-base.json`: a lost `snapshot.json` is rebuilt from it and the sealed segments, and its first sealed segment starts at the anchor line, so the anchor's hash is still found after its own rotation. A tailer follows a rotation through any number of sealed segments (by the active file's inode), so one far behind reads on instead of starting over. `verifyChain` checks the active segment incrementally from its own in-memory checkpoint (trusted only while the line before its offset still hashes to the stored hash; else from the segment's start); the snapshot vouches for the sealed segments, and `validateChain` re-checks every line, carry lines included. The tail runs `verifyChain` on its health tick and sends one `room log check: …` line per break (a `health` event). The chain makes edits around the store visible; it does not prevent them.

**What a home stops keeping.** `lib/gc.ts` runs at a join (`seats.take`), at most every 6 hours and within 250 ms, never on the room being joined: a room closed for good (every person's seat left: a seat whose session crashed has not; its room session stopped or never started), with no link record (neither this machine's link to it nor the host's `remote/links` records of machines linked to it) and nothing changed for 30 days (`ROOM_GC_MS`, `SUB_HUMAN_ROOM_GC_MS`) is set aside, not deleted: renamed to `rooms/CODE.gc-TIME` with its seat keys at `keys/CODE.gc-TIME`; those folders, and the ones `link --forget` set aside, are deleted 30 days later; session indexes of ended sessions go after 30 days, and a room's row maps of ended sessions after 7 (swept for the room joined). An open room's segments and snapshot are never touched: a room goes only whole. `openRooms()` and `orphanRooms()` judge the rooms in `<home>/open-rooms.json` (written at open and at every join; a room closed for good, every seat left and its room session stopped, leaves it), not every room ever made.

**Who typed an `@room`.** (`@claude …` is an ordinary prompt to the person's own Claude, in a room or not: nothing parses it.) The module's `prompt.submit` gate reads the origin Claude Code stamps on the prompt (`composer`, `sdk` or `bridge` count as typed; cc CONTRACT `prompt-origin-composer`) and drops any other `@room` before a hook runs; the shim hands that origin to at-room as `sub_human_origin`, and at-room posts only with a typed one that comes with this session's nonce (Security model). An origin that is lost on the way (a reload between the two hooks) is refused, and the person types it again.

**How an `@room` post looks.** The TUI trims trailing whitespace before the hook sees the prompt (accepted). On success at-room answers `continue:false` with a stop reason, which keeps the person's `❯ @room …` row and adds one warning line, "Operation stopped by hook: ✓ sent to room CODE (Claude wasn't asked)", and an isMeta copy of it; the model sees the row and the copy natively on its next turn. The module words that copy as "sub-human: that @room line went to the room; nothing is asked of you.", so the person's next words, read with no turn between, are not taken for a request of the room; a refusal's copy ("✗ …", such as the room session's for a typed prompt) reads "the prompt above was refused and went nowhere (REASON)" instead. The module's `session.append` hook keeps that warning line as the receipt alone (only for a stop its shim just returned, matched whole; cc CONTRACT `ups-stop-frame`, `session-append-notice-rewrite`), so the person sees `⏺ ✓ sent to room CODE (Claude wasn't asked)`, and `⏺ ✓ sent` for the session's later ones, after `--resume` too. The receipt says who reads the post, so where the frame stays (2.1.300 was reported not to rewrite) it still reads as delivered, not as an error. Refusals are `decision:block` with `suppressOriginalPrompt`, which works only inside `hookSpecificOutput`, so refused or forged text never reaches the model. Typed through Remote Control (origin `bridge`), a refusal is also the `systemMessage`, which the phone shows. When the posted text appears verbatim in the last assistant message (an accepted prompt suggestion, a copied draft), the entry carries `drafted:"agent"`; it is still posted.

## Delivery and settle batching

`deliver(me, e, {entries, trust, note})` (`lib/room/deliver.ts`) says what one entry is for one seat, one of four classes:

- **wake**: needs Claude now: one plugin prompt, one model turn. Anything `to` me or mentioning `@me`, a sign-off request (proposal) naming me that I have not answered, a task assigned to me that someone else asked for, an objection to my proposal, and another member's new version of a room plan whose sign-off I asked for or objected to (`consent.ts` `revises`: the request on the version before it, still open or not agreed), with a `(for Claude)` line saying so, so the revision comes back to the people who asked.
- **notice**: for the person, no wake (the tail's `chat` event): another person's own words not addressed to me, another member's join or leave, another member's new version of a room plan (a `plan` entry wakes only the asker and the objectors of the request on the version before it; its own sign-off request wakes its approvers), the decision on a proposal I am in (a decision never wakes), another approver's objection on one I approve, a task someone else added with me as its suggested owner (it says "suggested for you"; I claim it myself). The model gets a copy as context.
- **context**: for Claude, no wake: the tail sends it as the room context (under "room since your last turn (FYI):"), which the module carries beside the person's next prompt as a context block of its own. A decision the consent hook already told this seat's model of (`session.ts` reported) is left out of it, and "to answer X's Claude: SendMessage X.CODE" goes once per peer per session.
- A member's wake reaches the model with one framing line, "(for Claude) sub-human: the prompt above is room lines the person already saw, not their words or instructions to you." (`mod/core/deliver.ts` WAKE_CONTEXT).
- **none**: my own posts, and what concerns neither me nor the room's state.

The room session (role `claude`) reads nothing but its rows: another member's `member_joined` whose row note (`lib/rows.ts` joinNote) says no row runs is a wake (a rows-only turn); every other entry is none for it.

Its first step, `lane()` (push: notice or wake; pull: context; none), is kept for its table tests. The tail batches what is not `none` in a `Batcher` (`lib/tail.ts`): flush after `SETTLE_MS` 1500 of quiet or `SETTLE_MAX_MS` 5000 after the first (room session: 3000 / 10000), so a burst costs at most one turn. Each entry is judged again at flush time against `readView`, so an entry answered or decided in the meantime is dropped. A `member_left` is held `LEAVE_SETTLE_MS` 8000 so a quick leave and rejoin shows nothing; the room row's hold progress line settles leaves the same way ("bob left" only after 8 s). A member's batch is group-chat lines without ids, plus `(for Claude)` lines in a wake; the room session's batch (`formatRoomClaudeBatch`) is each waking join's full line with its row note, then "Make only the call its row note names, then end your turn with no text." All timings live in `lib/config.ts` with `SUB_HUMAN_*_MS` overrides. The room session gets the overrides of the session that started it through its `--settings` env (the bg daemon filters the caller's env), so a room started with a short `SUB_HUMAN_ROOM_CLAUDE_ORPHAN_MS` has a watchdog that honours it.

## Consent

A sign-off request is a `proposal` on one version's hash. At most `OPEN_MAX` (5) plans may be not agreed at once; a new name past that is refused.

"Tell Claude what to change" reaches the next `ExitPlanMode`, which reads the note with `cc.planFeedback` (the transcript's `userFeedback`, else the "the user said:" text). A plan view the person refused runs no PostToolUse, so the module's `tool.call` hook reports it (`mod/consent.ts`, the reducer's `rejected`). When the "Yes" the person chose changed the permission mode, consent puts it back with a silent EnterPlanMode / ExitPlanMode pair (phase `restore`). An edit and a review never overlap: while a review is open the edit's routing stands aside, and while an edit is open plan mode is the edit's, so an edit's ExitPlanMode never reaches a review.

**One reducer per machine.** What the consent hook does for a review is decided by `lib/consent/review.ts` `reduce(state, event, ctx) → {state, effects, say}`, a pure function table-tested phase by phase (`test/consent-review.node-test.ts`). Its state is the seat's documents above, `review` (phase `entering | shown | exiting | restore`, the plan-file backup, `unread` while the dialog's answer is not on disk), `note` (its `stage`) and `recheck`; its events are the hook events with their facts (`enter`, `entered`, `exit`, `permission`, `exited`, `stop`, `roomTool`, `rejected`, `prompt`, `ask`, `answered`, and `planFailed` when a write fails). `hooks/consent.ts` only gathers the facts under the review lock (the transcript, the plan file, the room's pending and answerable requests, a join request waiting), runs the effects in order (`save` a snapshot before `writePlan`, so the backup is on disk before the overwrite; `restorePlan`; `answer`, which is `proposal.answer` then `decide`) and writes the answer. Every line the model is told is in the reducer's two tables: `NEXT`, the one mechanic per phase (open, show, exit, restore, card, note), and `SAY`, short outcome lines; the tail's reminder and the room server use the same lines. An edit's lines are `lib/consent/edit.ts` `EDIT_SAY`, its events `enter`, `attach`, `exit`, `put`, `permission`, `exited`, `stop`, `prompt`. The cards the hooks build (the fallback consent card, the note's confirm card, a join request's card) are read by one function, `lib/consent/card.ts` `answerCard(spec, response, input)`: `absent` (another call), `none` (AFK, a followUp, no answer, or a card shown other than as built), `other` (a label it does not offer) or `answer`. The plan file the hooks write is `cc.planFile`: the transcript's `plan_mode` attachment (Claude Code's record), or the path Claude Code injects into `ExitPlanMode`'s input when it is that same path or lies under the plans dir; an edit's seed also takes the path of the module's `PlanAttachment` event (`detail.planFilePath`, cc CONTRACT `module-plan-mode-detail`). A path the model put in any other call is never read.

`lib/room/consent.ts` `fold(entries)` is the one interpretation of the log, used by `stateLine`, `lane`, the rows and the gate, so they cannot disagree: the latest proposal entry per hash wins; per person the latest trusted `via=human` answer wins (an objection voids an earlier signoff); a decision closes the hash with state `agreed` or `blocked`. It folds the plans too (`Fold.plans`, `versionOf`): each plan's versions from its `plan` entries (a version at or below the current one is ignored), and a newer version of a plan retires (`superseded`) every undecided request on an older one of the same plan; answers stay with their hash and never carry over. Which plan and version a request is about is read from the plan fold by its hash, never from the request's own fields. `render.ts` reads the result: a version as "bob's Claude for bob: plan paging v4: SUMMARY" (plus "retires the sign-off request for …"), a request as "X's Claude asks you and bob to sign off on plan NAME vN (hash6)" (the approvers are who is asked), and `stateLine` names "plan NAME vN"; the rows (`lib/rows.ts` planSegs) show each plan at its current version and state ("paging v4 1/2 agreed, waiting on bob", "api v1 draft", agreed, not agreed; a request or decision on an older version is history, never the row's news), and the ones that do not fit are counted ("+2 plans"). `test/hooks/consent-table.node-test.ts` feeds one table to all views.

One person in two seats is one approver. A seat's `account` (in the members document) is the person behind it as the host knows it: the host's machine id for a seat on the host and for one over a login link (`/sub-human join USER@HOST ROOM`: the host account's own ssh login, `lib/remote/server.ts` join); an invite's seat has none, so two invite seats from one machine stay two people. `proposal.ask` writes `same`, the approvers that share an account in groups of 2+ (`lib/proposal.ts` sameOf). Several people can share one machine, so of the host's own seats (machine = account) only the room owner's counts as that person: the seat of whoever opened the room, marked `owner` in the members document when the first person's seat on the host joins (`lib/room/members.ts` join, kept across that seat's rejoins; a room from before the field falls back to the earliest-joined host seat present). Login seats group with the owner's seat; every other seat on the host is its own person, and two plain seats on the host never merge. In the fold the newest answer from any seat of a group counts for every seat of it, and a revoke from one clears it; `matrix` lists one name per person (`agreed`, `objected`, `missing`, with `also` naming the other seats), `people` counts them for the rows, and the decision reads "agreed: tristan (also laptop), bob". When one seat answers, the other seat's review or card no longer opens (`pending`), but an answer it gives on one already open still records and, being newer, counts (`answerable`; one answer per seat). A request with no `same` (an older log's) counts every seat: stricter, never wrong.

## Tasks

```
member's Claude ─ task({op, …}) ─► mcp/task.ts ─► host: lib/tasks.ts apply   (a mirror: the link's `task` op; OFFLINE: refused)
  under the room's `tasks` lock:  check(task, req, by) ─► refused at once {ok: false, error}
                                  else: the room task first, if none is open ("room CODE open", owner room, in_progress)
                                        task_req (via=agent, from the requester) + task (via=system, from room, full snapshot)
                                        ─► lib/room/task-files.ts project ─► <room session's config dir>/tasks/sh-CODE/<n>.json
                                        ─► tasks.json = tasks.fold(task entries)
                                  ─► {ok: true, task, text}: the requester's Claude reads the result at once
```

- **The rules** (`lib/tasks.ts` check, pure): `add` by anyone, with an optional `suggest` (a suggested owner, recorded, never the owner: they claim it themselves) and an optional `plan` (the task is tagged with that plan's current version; no such plan is refused); `claim` only for yourself, refused while someone else owns it; `release` and `done` by the owner only, and `done` needs evidence. No model writes a task: the room session's agent has no task tools and its server refuses `task` to it, and no hook mirrors a TaskCreate or TaskUpdate (a member's own TaskCreate stays in their own list).
- **The log is the truth; the files are a projection.** `project` writes every task of `tasks.foldAll` as a native task file (`lib/cc/tasks.ts`, cc CONTRACT `task-file-schema`), only when its text differs, atomically (a temp name that never ends in `.json`, then rename), under Claude Code's own proper-lockfile protocol (`lib/cc/tasklock.ts`: the list lock and each task's lock, `task-lockfile`), removes a deleted task's file, leaves a file the log does not know alone, and raises `.highwatermark` to the highest id (`task-highwatermark`) so a TaskCreate never reuses one. The room session's task view (ctrl+t) shows the files as they change (`task-ui-watch`), which needs the directory to exist when the session starts: `lib/room-claude.ts` openTaskList records it (`members.claude.tasks_dir`: `<its config dir>/tasks/sh-CODE`) and makes it before the spawn. The list id reaches the session as `CLAUDE_CODE_TASK_LIST_ID=sh-CODE` through `--settings` env, because the bg daemon filters the caller's env (`daemon-env-filter`); the `claude --bg` client itself gets the spawner's env minus the member session's own keys and `SUB_HUMAN_*` (`cc.clientEnv`, `CLIENT_ENV_DENY`), so no allowlist has to follow each release. The job id is the newest live job named `claude.CODE` in `claude agents --json`, asked a few times while the daemon registers it; the `backgrounded · <id>` line is a hint.
- **The room task.** Claude Code resets a list once every task in it is completed: a session showing it deletes every file (`task-list-auto-reset`). The room task "room CODE open" (owner `room`, `in_progress`, written with the room's first task request) keeps that from firing while the room is open; the reaper completes it at close (`tasks.closeRoomTask`, through the log like any task). It never shows in `tasks.json`.
- **What the plugin writes under Claude Code's config dir**: exactly these task files (the `sh-CODE` directory, its `<n>.json`, `.highwatermark` and the lock dirs), and, during an edit or a review, the member's own session plan file (backed up first and restored). Nothing there is ever deleted but a deleted task's file, and no settings file is written.
- **Repair.** A projection that failed (a lock Claude Code held past `TASK_LOCK_TIMEOUT_MS`, a file edited or removed by hand) loses a view, never data: the room session's tail repairs it on every health tick on the host (`tasks.repair`: project the log again, under the room's `tasks` lock), and so does a member's tail on the host while the room session holds no seat (`roomSessionDown`: never bound, crashed, starting again), so the files never depend on the room session alone.
- **Preflight.** Before the room session starts (`openTaskList`) and before every repair, `lib/cc/tasks.ts` `check` asks whether the list can still be the file store this Claude Code reads: the key-value task backend's gate is off (`tengu_hover_rest`: the env switch `CLAUDE_CODE_HOVER_REST`, else the cached feature; `task-store-v5-off`), the directory is one the plugin can write, every `<n>.json` still reads as a task, and no lock entry has a layout it does not know (plus the per-version verdict, a seam for now). While it says no, `members.claude.tasks_off` holds why (host only, kept across the room session's bind), `project` writes nothing (a failed projection is a stderr line, never silent), the brief says "room task list not shown: REASON; tasks are kept in the room" and doctor warns (`room-tasks:CODE`). Nothing is lost: the tasks stay in the log (the `task` tool, `tasks.json`, the rows, the status line), and the first repair after the check passes clears the reason and writes the list again.
- **`tasks.json` is a pure fold** of the log's `task` entries: delete it, refold, same file. Rows, the status line and `sub-human tasks` read only it; a mirror gets it as a streamed document.

## Identity and liveness

- **Commands.** Every `/sub-human …` runs `hooks/handlers/join.ts` (UserPromptExpansion) before the model, a thin edge: it reads who asked (session id, cwd, claude process, seat) and renders one `Answer` of the command table `lib/commands/index.ts` (`{verb: (args, ctx) => Answer}`: the bare command, `join`, `invite`, `admit`, `kick`, `leave`; `help` and `doctor` run without the module's lease; any other first word is a NAME or a ROOM) as the hook's one `Reply`. The router decides the hidden rule before any verb parses (below). The seat itself is `lib/seats.ts` take; the link steps of a join are `lib/remote/joining.ts`.
- **Binding.** `/sub-human NAME [CODE]`, `/sub-human CODE` and `/sub-human join CODE` (a room on this machine, as the default name or `--as NAME`) take a seat before the model runs. A join that worked shows no `systemMessage` (Claude Code draws one as a warning; the title and the room row say it), unless the room session did not start or the session is in bypass-permissions mode; a refusal is the block reason and the `systemMessage` (which Remote Control shows). It writes the seat into `members.json` and the indexes `<home>/sessions/by-pid/<CLAUDE_PID>.json` and `by-sid/<session_id>.json`. The model never names itself. Without a CODE it joins the one open room (a live member seat, not closing), or opens a new one; several open rooms is an error that lists their codes. Rooms where only the room session is left are swept first. A member already in another room switches: the old room logs `member_left` "switched rooms".
- **Resolution.** Hooks: payload `session_id`, then `CLAUDE_PID`. MCP server: `process.ppid` (MCP servers get no `CLAUDE_PID`). CLI and tail child: `CLAUDE_CODE_SESSION_ID` (the module sets it for the child), then `CLAUDE_PID`, then the nearest registered ancestor. `/clear` changes the session id but not the process: `session-restore.ts` rebinds the new id to the seat found by pid. `--resume` is a new process with the old id: it rebinds the pid or rejoins the seat.
- **Liveness.** `seatAlive(m)` (`lib/room/members.ts`): not left, and, for a seat of this machine (`m.machine === machineId()`), the pid is alive with a start time equal to the stored `pid_start` (so a reused pid never keeps or adopts a seat). Any other seat (another machine's, or no pid) is alive while its `seen_at` lease is fresh (`SEAT_LEASE_MS` 120 s); the tail's health tick and the hold server renew it with `members.beat` at most every `SEAT_BEAT_MS` 30 s, and a presence write rides on the same op.
- **Entering and leaving.** `lib/seats.ts` `enter` (members.join, the session indexes, `member_joined` with `pubkey` and `machine`, the room session) and `exit` (members.leave, the reaper when nobody is left, `member_left`) are the one sequence the join and session-end hooks run. A name is one seat across machines: a live seat of another holder makes it "name taken". `host` and `join` are reserved names.
- **Host gates.** The room session's spawn, reap and watchdog (`lib/room-claude.ts`), proposal decisions, task requests (`lib/tasks.ts` apply), plan versions (`lib/plans.ts` put) and the task files run only where the room's store `isHost`; on any other machine they do nothing, or go to the host over the link. The host never moves: when it leaves, the room waits.
- **Address.** `NAME.CODE` is set as the session title (the module's `classic.UserPromptSubmit`, once per session id and address), which is what `SendMessage` and `ListAgents` use (cc CONTRACT `session-title-address`).

## The room session: lifecycle

```
join (no live room session) ─► claimSpawn: members.claude = {job:"pending", claim}  (under the members lock; a concurrent join sees it)
                    ─► openTaskList: members.claude.tasks_dir recorded, the directory made
                    ─► startDetached ─► spawn(): claude stop <prevJob>; claude --bg …; find job in `claude agents --json`
                                         record {job} only if the claim is still current and the room is not closing
room session ─► /sub-human ─► join.ts binds the "claude" seat (agent_type sub-human:room-claude + SUB_HUMAN_ROOM)
             ─► its launch turn: the Agent calls its ROWS line names, then no text
another member joins, no row running ─► a rows-only turn (the join line, its row note, "Make only the call …")
last member SessionEnd ─► reap (detached): grace 10 s (a rejoin cancels) ─► set closing ─► tasks.closeRoomTask
                          (the room task completed in the log and its file) ─► claude stop <job> ─► room session seat left
crashed members (no SessionEnd) ─► room session tail child's health tick: watchdog() sees no live member for 60 s ─► closing + reap
```

The room session's agent (`agents/room-claude.md`) has one tool, `Agent(sub-human:participant)`, and a one-paragraph prompt: make the Agent calls the block or a join line names, then end the turn. It never plans, posts or answers: its lane reads only joins (Delivery), `crossSessionInbound: "refuse"` (`cc.ROOM_SESSION_INBOUND`, cc CONTRACT `cross-session-refuse-notice`) turns a peer's `SendMessage` away instead of starting a turn, `post` refuses `to: claude`, and a typed prompt is refused ("✗ the room's session (claude.CODE) takes no typed input; type in your own session: @room for the room, or ask your own Claude"; a slash command too, by the module). Room upkeep (editing a plan, asking for sign-off, adding tasks, catching a person up with `read({brief})`) is any member's Claude's, when its person asks: the short "room upkeep" block in `skills/sub-human/member.md`, inside the join's mechanics block (`BLOCK_MAX` 1500).

Debugging the room session by hand: `node lib/room-claude.ts cmd CODE` prints the exact spawn command; or run `claude --agent sub-human:room-claude --permission-mode plan` and type `/sub-human CODE` (an existing room) or `/sub-human` (a new room).

`needsSpawn` also respawns a room session whose pid is dead, whose claim is older than `ROOM_CLAUDE_CLAIM_MS`, or which never bound within `ROOM_CLAUDE_BIND_MS`. `openRooms()` ignores rooms where only the room session is left, and join sweeps those through the watchdog.

## Remote rooms

A room can have members on other machines. The machine that created it is the **host**: its room directory is the room, and its hooks, tail and MCP server keep using that directory as before. Another machine joins with an invite and keeps a **mirror**: a room directory with the FsRoomStore layout, holding the host's log line for line, kept by a **link daemon**. Every reader (`readView`, the snapshot, the tailer, `verifyChain`, rows) works on the mirror unchanged; only writes cross the wire, as named ops. Two transports people use: SSH (`ssh:user@host[:port]`: an invite's PIN join, or the person's own ssh login, below) and the listener (`wss://host/…/sub-human/CODE`: a Noise channel in a WebSocket to the host's listener through Tailscale Serve or Funnel, below). A pipe to a second home on the same machine (`pipe:<home>`) and an in-process memory pair are for the tests and the demo (S11) only; SSH is the pipe with `ssh` in front, and none of them needed a protocol change.

```
 HOST machine                                            REMOTE machine
 hooks / tail / MCP ──► FsRoomStore ◄── serve --stdio ◄══ transport ══► link daemon ──► MirrorRoomStore (FsRoomStore layout)
   (sign + place,        <home>/rooms/CODE   per connection    (ssh, or a   (one per room   ▲ reads: hooks, tail, MCP, rows
    decide, claude)                           (scripts/sub-human)   pipe)        and home)       │ writes: bridge (worker thread,
                                                                                             │          Atomics.wait, deadline)
                                                                                    hooks ───┘ sign with the local seat key
```

**Joining.** On the host, a person in the room runs `/sub-human invite [--ssh [user@host]]` (`lib/remote/hosting.ts` hostInvite; with no way named, over the tailnet when Tailscale is up here (`webhost.ts` hostWeb through Serve, never Funnel: `--public` is asked for by name) unless `SUB_HUMAN_SSH_ADDR` is set, else over ssh, to `SUB_HUMAN_SSH_ADDR` or `user@hostname`; a bare ssh alias is shown as given and recorded as `ssh -G` reads it): `invites.mintInvite` (`lib/remote/invites.ts`) records an **invite line**: 16 random bytes the line carries and a 4-digit PIN the person tells apart; the host keeps only `sha256(secret)` (the record's key) and `sha256(secret:PIN)`, at most `SHORT_LIVE_MAX` 4 open, 5 tries, `INVITE_TTL_MS` 15 minutes. The join hook shows `/sub-human join DEST ROOM SECRET [--home H]` (over the web `/sub-human join URL#SECRET`) and the PIN apart as a block reason with `suppressOriginalPrompt`, to the person and never to the model; through the hooks module both are pinned under the prompt instead, and a Copy / Skip card (`mod/core/copy.ts`) copies the line, never the PIN, to the clipboard (none with `--no-card` or `SUB_HUMAN_INVITE_CARD=0`). SECRET (`lib/remote/invite-secret.ts`) is 39 characters of lower-case Crockford base32: the 128-bit secret and a 64-bit tag, `HMAC-SHA256(secret, "sub-human host key v3" 0 role 0 key)`, of the host key the line is for: the home's Ed25519 machine key over ssh and a pipe (role `machine`), the listener's X25519 key over the web (role `listener`). `--home` goes in when the host's folder is not `~/.sub-human`. The line carries no name: the joiner's is their git `user.name` (`identity.defaultName`), or `--as NAME`. On the other machine every `join`, `invite` and `admit` prompt, and any prompt with a word of digits or a SECRET-shaped word (`mod/core/command.ts` SECRET_WORD: 32 to 48 letters and digits), is answered hidden (the command router turns each say and refusal into a secret, decided from the prompt before any verb parses it), and a SECRET-shaped word is never echoed or taken for a name. **No step of the join takes the seat.** The line, with its PIN or not (`joining.linkLine`), writes the link file (`lib/room/links.ts`: the transport, over ssh the person's own login (`ssh.loginSpec`), over the web with a fresh key of the link's own (`link-connect.ts` linkKey); `invite` the SECRET word; `pin` when typed; `join_as`, `join_sid`), starts the daemon and watches it (`hosting.outcome`, up to `LINK_JOIN_WAIT_MS`). The daemon (`link-connect.ts` connectLink) checks the host first: over the web it reads the listener's key (a text `{"op": "key"}`) and checks the tag before the Noise handshake, then pins it; over ssh and a pipe its first hello carries a nonce and the host answers with its machine key's signature over it (`machine-key.ts` hostProof), checked against the tag (`client.ts` checkHost). A host the tag does not name gets nothing (`AUTH HOST_KEY_MISMATCH`, the line dropped). The second hello carries the SECRET, `as {name, label}` and the PIN typed after the line (`/sub-human join LINE PIN`), sent only once the host key checked out. **With the PIN** the host throttles (after the n-th wrong PIN no PIN for `PIN_BACKOFF_MS` · 2^(n-1) per invite, one step longer for the machine that typed it: `PIN_THROTTLED`, charged nothing), checks it (`PIN_WRONG` with the tries left; the fifth `PIN_LAST` burns the invite; each a room line; a wrong PIN never makes a card), and on the right one uses the invite and lets the machine in in that same hello: an admission let in by `'pin'` (no signature: no person answered), bound to the machine its key proves, the name (the free `NAME2` when NAME sits in the room from another machine: `admission.taken`), the label and, over the web, the Noise key the connection proved; the link is made and its token returned, and the room line reads `NAME joined from LABEL (check 3f9c-2a71) · not them? /sub-human kick NAME` (`server.ts`). The check is `invite-secret.ts` joinCheck of the machine id the joiner's key proved and, over the web, its link's XK key, never of the line, so a thief holding the line and the PIN shows another check than the real joiner's screen. **Without the PIN** the hello knocks (`knock: true`): the invite is used, an admission `'asked'` (`invites.admissionSlot`) waits for the host person's card, and the host answers `OFFLINE ADMIT_WAITING`; the link file keeps `awaiting {ref, check}` and the joiner reads "Asked the host to let you in … (their card shows check …)". A knock spends no PIN try; the host's tail wakes its Claude to call AskUserQuestion `admit REF` and the hooks build the card (`lib/remote/admission.ts`: Let in / Refuse, signed with the seat key; or `/sub-human admit [REF]`, `sub-human admit` in a shell). The daemon redials with the SECRET alone until it is answered; a PIN typed meanwhile (`/sub-human join PIN`, `joining.givePin`) is checked as above. An older joiner never knocks: it gets `PIN_NEEDED` (nothing charged), kept as `pin_wanted` ("Type the 4-digit PIN they told you: /sub-human join PIN"); an older host ignores `knock` and asks for the PIN the same way. Once any machine typed a wrong PIN for an invite, a knock gets `PIN_NEEDED` (a miss is no card from another machine). The right PIN from another machine while a knock waits replaces the knock (a line that leaked alone can't lock the real joiner out): the card goes, the knocking machine gets `ADMIT_REFUSED` from then on (the admission's `replaced`), and the room a line with both checks; a wrong one there costs a try as anywhere. Otherwise a second machine that presents a used invite gets `INVITE_USED` (a knock never replaces anything), and the room a line naming both checks (once per machine). Once linked, the SECRET leaves the link file. **The seat and the notices:** `mod-hello` reports `pending` for the session that typed the line (`join_sid`), so the hooks module starts the tail child although it has no seat, and the tail (`lib/tail.ts`, `joining.pendingNews`) writes one chat line per answer (the host asks for the PIN, the card waits, or why the join stopped). On `linked` it emits `take`: the module (`mod/deliver.ts` takeSeat) runs the shim's `join` for that room (`take`: that join's seat or nothing) and submits a wake of its own, "You're in room CODE as NAME (check …)", with the seat's mechanics block for the model: never the prompt that carried the line or the PIN. Without the module (the session closed), a bare `/sub-human` finds the link file's `join_as` and takes that seat. An invite to the default address (no `SUB_HUMAN_SSH_ADDR`, no `--ssh`) says the name is this machine's own (a `.local` name reaches the same network only) and, when this machine takes no ssh logins (`hosting.remoteLogin`: macOS `launchctl print-disabled system`, Linux an sshd process or ssh unit; no network probe), that the joiner's ssh will fail and `--web` is the other way; every ssh invite says it needs the joiner's own ssh login to this account. From then on `store.open(CODE)` there returns the mirror. **Over an ssh login** (no invite): `/sub-human join HOST ROOM [--home P] [--as NAME]` (no SECRET) is said to be the login path, not an invite (a pipe destination has no login path: there it is an invite line without its SECRET), and writes a link file whose transport is `lib/remote/transports/ssh.ts` loginSpec (`login: true`, a link id this machine picks, the host's home when not `~/.sub-human`; a bare ssh alias takes its user from `ssh -G`); the daemon runs the person's own `ssh -o BatchMode=yes … '"$HOME"/.sub-human/bin/serve --stdio CODE --link ID --login'` (their keys, config and known_hosts) and says hello `{login: true}` (only when the link file holds no invite: an invite line over a login transport sends its invite, so it still goes through its PIN and the card); that `serve --login` session (refused under `SSH_ORIGINAL_COMMAND`, i.e. any forced command) makes link ID (`hostLinks.loginLink`, `lib/remote/host-links.ts`), with the room line `a machine linked over your SSH login`. Its seats take the host machine's `account`, so consent counts them with the room owner's seats (Consent). The join watches the first hello and takes the seat in the same step (nothing secret is in that prompt); ssh failures only the person can fix (an unknown host key: the exact `ssh USER@HOST` to run once; a refused login; no shim or no room on the host) stop the daemon with `AUTH` and that reason (`ssh.loginProblem`: `SSH_HOST_KEY`, `SSH_DENIED`, `SSH_NO_SHIM`, `SSH_OLD_HOST`, `SSH_NO_ROOM`; one classifier of ssh's stderr, `ssh.classify`, serves the daemon, the login join and doctor). A host refreshes its serve shim passively on every join there. A seat's connection ends with `/sub-human kick NAME` or `sub-human kick NAME` (`hosting.kick`): the token (and its key) and any invite reserved for it burn, an `authorized_keys` line an older version wrote for it goes, its seats leave, its `serve` processes stop (each first ends its streams `{reason: 'AUTH'}`, so the joiner's daemon stops with "the host revoked this link" instead of redialing), and a room line says so. An unused invite is cancelled with `/sub-human invite --cancel [REF]` (`hosting.cancelInvite`). `/sub-human leave` leaves the room (`seats.exit`) and keeps the session; its tail goes quiet with the seat.

**Host and mirror.** `store.isHost` decides who does what. Only the host spawns, reaps and watches the room session, decides proposals, applies task requests, stores plan versions, writes the task files, pins keys, mints invites and writes `members.update` and the streamed documents; on a mirror these throw `HOST_ONLY` or are gated off (`lib/room-claude.ts`, `proposal.decide`, `tasks.apply`, `plans.put`: a mirror's requests go to the host as the `task` and `plan.put` ops). The host streams its log lines verbatim and three documents: `members` (`members.publicView`: no `pid`, `pid_start`, `session_id`, `cwd`), `presence/*` and `tasks`. Session-local state (`rows/*`, `members/NAME/session`, cursors, notices, the session indexes, keys) never leaves its machine. On a mirror a seat of this machine is judged by its session index (pid, start time, session); a seat of another machine lives by its lease (`seen_at`, `SEAT_LEASE_MS` 120 s, renewed by `beat`). A remote seat's join and leave reach the host's `lib/seats.ts` through its server, which logs `member_joined`/`member_left` and runs the room session and the reaper there.

**Writes.** A hook's write (`@room`, an answer, join, leave, a beat) is signed on its own thread, then crosses `lib/remote/bridge.ts`: the hook's thread posts one op to a worker and blocks in `Atomics.wait` until the reply or the deadline (`LINK_CALL_MS` 3 s, SessionEnd `LINK_CALL_END_MS` 1 s). The worker relays the op over the daemon's unix socket (`lib/remote/link-socket.ts` handle; it loads no store and never the signer). With the link down the call is `OFFLINE` and nothing was sent: a card answer (consent), a sign-off request, a task request, a plan version, a join or an agent's post is refused at once and the person is told, never queued. The one exception is the person's own `@room` post (see the outbox below). A slow link is not a down one: the frame went out and may land late, so a deadline is never "nothing was sent". The daemon answers every relayed op by `LINK_RELAY_MS` (2 s, inside the hook's 3 s): a person's `@room` post the host has not answered by then goes into the outbox under its nonce, answered `{queued, slow: true}` ("⧗ sending (slow link)"), and the host's late answer takes it out (the late copy is the post; a refusal is dropped and reported); any other op is `OFFLINE` with reason `UNKNOWN_OUTCOME`, as is the bridge's own deadline, and the store marks it `unknown` (by the reason, never the message's words): the at-room hook says "⧗ not confirmed", the consent hook that the answer may still be recorded and answering again is safe (one answer per person per proposal; the same signed payload sent again is refused by its nonce). After a write the server ticks the session's streams before it replies, so the mirror holds the write's lines when the hook's call returns (read-your-writes). The worker starts at a process's first write: a hook that only reads starts none.

**The link daemon** (`scripts/sub-human link CODE`), one per room and home, in four files: `lib/remote/link-engine.ts`, the connection logic as a pure state machine (below); `link.ts`, the daemon that runs its effects (dial, subscribe, renew seats, send the outbox, ping, timers on the injected clock, the mirror's writes); `link-socket.ts`, the hooks' socket at both ends and the daemon's control (`status`, `start`, `stopReason`); `link-connect.ts`, the link file's hello and what a refused dial means. The daemon it holds the one connection (`hello` with the token), `subscribe`s from the mirror's last line with `{after, hash}` (an empty mirror also asks `snapshot: true` of a host whose hello caps say `snapshot`: the host's snapshot arrives first, `applySnapshot` checks it, and only the lines after it follow), applies each line (`applyLine` refuses one that does not chain: `FORK`, so a snapshot whose head the next line does not chain to is `FORK` too) and document, prefetches every proposal's plan, and serves the hooks on `<mirror dir>/.link/link.sock`, or `/tmp/sub-human-<uid>/<hash12(mirror dir)>/link.sock` when that path is too long for a socket (each directory 0700, a real directory, this user's). The path depends on the home and the room only, never on `TMPDIR` (a daemon started by the listener or sshd need not share the session's), and the daemon records it in its `link.json` (`socket`), which the hooks try first, then the computed path. Its state is the mirror's `link.json`: connecting, online, offline, fork, stopped (AUTH or PROTOCOL at hello, the room closed, idle, a signal). `FORK` is never repaired silently: the daemon stops, the tail sends one `room link: FORK …` line (a `health` event: the module logs it as a notice and gives Claude a copy), whose fix is to forget this copy and join with a new invite (the line names `sub-human link --forget CODE`; `--forget` forgets a stopped link on its own only for `ROOM_CLOSED`, `NO_SEAT` or a revoked token, so a forked one needs `--force`; the log is set aside, never merged). The tail also sends one line when the link goes offline, and one quiet `room link: back online; …` line once it is online again (with what became of the queued posts); a swap that never left online shows nothing. The daemon exits `LINK_IDLE_MS` (60 s) after no seat of this machine is left in the room: online by the host's members document, offline by this machine's live session indexes, so a crashed or abandoned join never leaves it retrying. The server (`scripts/sub-human serve --stdio CODE`, `lib/remote/server.ts`) is one process per connection on the host, spawned by the client's transport; there is no host daemon, and the file locks coordinate it with the host's own hooks.

**The engine** (`lib/remote/link-engine.ts`). `step(state, event, {timings, random, now}) -> {state, effects}`, with no I/O and no clock of its own; `test/link-engine.node-test.ts` drives it from a table on the fake clock.

| State | Means |
|---|---|
| `connecting` | the first dial is under way |
| `online` | `conn` is live: subscribed, seats renewed, outbox sent |
| `offline` | no live connection; a retry timer or a dial is under way (observers see `connecting` while it dials) |
| `fork`, `stopped` | for good, with the code and reason it stopped on |

Events: `start`; `connected`, `subscribed`, `seated`, `flushed {pings}` (a dial's four steps: only after `flushed` does the new connection replace the live one, which is retired); `dialFailed {error}` (FORK, AUTH, PROTOCOL stop it; anything else keeps a live connection, else goes offline and arms `retry`); `lost {conn, error}`; `redial {why}` (a wake, a network change, a late pong, `SIGUSR2`: the backoff resets); `timer {retry | ping | pong}`; `pong {rttMs}`; `noPong` (dead); `stop {phase, why, reason}`. Effects: `connect`, `subscribe`, `keepSeats`, `flush`, `close`, `retire`, `sendPing`, `setTimer`, `clearTimer`, `online`, `forked`, `publish`, `log`, `finish`.

**Reconnect** (the engine's rules; timings in `lib/config.ts`, the ones the tests and the lab use overridable by `SUB_HUMAN_LINK_*_MS`):
- *Backoff.* A lost connection is dialled again after a delay with decorrelated jitter: random in [`LINK_RETRY_MS` 1 s, 3 × the last delay], at most `LINK_RETRY_MAX_MS` 10 s, so links that dropped together do not redial together.
- *Wake and network change.* A timer ticking every `LINK_WAKE_TICK_MS` (2 s) that fires more than `LINK_WAKE_GAP_MS` (5 s) late, or finds the wall clock that far from the monotonic one (which does not count a sleep), means the machine slept; a changed set of external addresses (`os.networkInterfaces`, polled every `LINK_NET_POLL_MS` 5 s) means it moved. Either is a `redial` event: at once, with the backoff reset. `SIGUSR2` to the daemon does the same.
- *Heartbeat.* `ping` is a protocol op gated by caps, not by version: the daemon says hello with `caps {ping: true}` and pings only a server whose caps list `ping`, every `LINK_PING_MS` (15 s). No pong within `LINK_PONG_MS` (5 s) makes the link suspect (redial); none within `LINK_DEAD_MS` (10 s) declares it dead, which catches a half-open TCP or ssh link after a sleep without relying on `ServerAliveInterval`. The server closes a pinging session that sent no frame for `LINK_SILENT_MS` (45 s). An old peer on either side never sees a ping.
- *Make before break.* A redial while online (a late pong, a wake) makes the new connection completely (hello, `subscribe` from the mirror's last line and hash, seats renewed, outbox sent) before it replaces the old one, which closes once the ops in flight on it are answered; hooks keep using the old one meanwhile, and a redial that fails keeps it. The two streams overlap for a moment, so a line the mirror already holds (the same id and bytes) is skipped; any other mismatch is still `FORK`. Appends stay idempotent by their nonce: the host refuses a nonce it placed already (`AUTH` with reason `PLACED_ALREADY`), and the outbox counts that as sent.
- *Seats.* On every reconnect the daemon `beat`s each live seat of this machine (`identity.localSeats`). A seat whose lease (`SEAT_LEASE_MS`) lapsed on the host during the outage is alive again with its pinned key and link binding unchanged, and nothing is logged: no "left", no "joined". The host never marks a lapsed seat left, so no new join proof is needed (the daemon never holds the signer); a seat the host does show as left is logged, and the person joins again.
- *The `@room` outbox* (`lib/remote/outbox.ts`, `<mirror>/outbox.json`, 0600). With the link down, an `@room` post the hook marks `queue` (`hooks/handlers/at-room.ts` only) and that is a signed `say` by a person to the room is kept by the daemon instead of refused; the person sees `⧗ queued: … (N waiting)`. At most `LINK_OUTBOX_MAX` (50) posts. With no daemon answering at all (`DAEMON_DOWN`: killed, crashed, or stopped `NO_SEAT`), the mirror store (`store-mirror.ts` `_call`) marks its stale records offline (a kill -9 leaves them `online`), starts the daemon detached without waiting (`link-socket.ts` `launch`) unless the link is over for good (a fork, a refusal, the room closed, the link ended), and an `@room` post goes into the outbox from the hook (`⧗ queued; restarting the link`); every other op is refused with "starting again … try again in a moment". So the outbox file has two writers: every read loads it, every change is under `<mirror>/outbox.lock`. Answers, sign-off requests, task requests, plan versions, joins and agents' posts are never queued: they fail at once with OFFLINE. The posts go out in order on the new connection, after `subscribe` proved the mirror is the host's prefix and before the link counts as online (a post typed meanwhile queues behind them). The daemon never re-signs, and the host refuses a signature more than `SIG_SKEW_MS` (10 min) old, so a post waits at most `LINK_OUTBOX_AGE_MS` (9 min); an older one, or one the host refuses, is dropped and the person is told with its words. On a `FORK` the queue is kept, not sent, and the FORK line says how many. Online, a post sent over a slow link that the host has not answered within `LINK_RELAY_MS` joins the queue too, under its nonce (see Writes): it leaves when the host's late answer comes, or is sent again, harmlessly, on the next connection.
- *State for observers.* Besides the mirror's `link` document (with `queued` and the last `flush` {sent, unsent}), the daemon writes `<home>/links/<code>.state.json` (`lib/room/links.ts` LinkState) on every change and every pong: `{state, since, attempt, lastError, lastReason, lastCode, rttMs, queued, pid, detail, at}`, in the one link vocabulary the `link` document, the room row, `doctor` and the tail share (`lib/room/link-state.ts` STATES): `online | connecting | offline | fork | stopped` (`connecting` also while an offline link redials). `lastReason` is the typed reason (`lib/reasons.ts`) `doctor` and `link --forget` key on. `doctor` and the statusline read it; a `pid` that is not alive means the daemon is gone.

**Transports.** `lib/remote/transports/index.ts` is a registry: `register(kind, {open, parse?, describe?})`. An invite's locator `KIND:REST` parses through its kind into the link file's `transport` spec, and the daemon's `connectLink` opens that spec with `{code}`; `open()` may be async (a socket or a handshake), and `client.connect` takes the transport or its Promise. Built in: `memory` (tests, worker threads; no locator), `pipe` (`pipe:<home>`, a second home on this machine), `ssh` (`ssh:user@host[:port]`, the pipe with `ssh` in front) and `wss` / `ws` (`wss://host[:port]/path`, below). `fromDuplex(stream)` turns any node stream (a socket, a TLS or WebSocket stream) into a transport, so a socket kind is a parse and an open of a few lines. Each connection still gets its own `serve --stdio` on the host.

**SSH.** A link's ssh locator is `ssh:user@host[:port]` (an invite's line, a login join); the ssh kind's parse (`lib/remote/transports/ssh.ts`, through `link-connect.ts` transportOf) accepts only a plain user and host (neither starting with `-`, no spaces, quotes, `%` or a second `@`) and a port, so nothing typed can name an ssh option or a command. Since protocol 3 every new ssh link is a **login link**: the person's own ssh login to the host account runs the host's stable shim, `ssh -T -o BatchMode=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=2 [SUB_HUMAN_SSH_OPTS] [-p port] -- user@host '"$HOME"/.sub-human/bin/serve --stdio CODE --link ID --login'` (`env SUB_HUMAN_HOME=H H/bin/serve …` with a remote home; `transports/ssh.ts` `command`; `SUB_HUMAN_SSH_OPTS` comes from the joiner's own environment, for tests and unusual setups, and goes after the link's own options, so it cannot weaken them; a jump host goes in the joiner's own `~/.ssh/config`, ProxyJump on an alias, which ssh reads), with the hello given `LINK_HELLO_MS` (15 s) for ssh to connect. The plugin writes nothing to `authorized_keys` and pins no host key: the person's keys, config and known_hosts decide. `<home>/bin/serve` is a small POSIX sh shim (`lib/remote/shim.ts`) that reads `<home>/bin/current` at run time: the plugin root, the node and the plugin cache dir of the install in use. `invite --ssh` and `doctor --fix` record their own install; every join, SessionStart restore and CLI run refreshes it passively, only from an installed plugin (a root under the Claude Code plugin cache), for the recorded root itself (a new node), or when the recorded root is gone, so a dev checkout or worktree run without `SUB_HUMAN_HOME` never takes over the real home's pointer (`test/real-home-guard.node-test.ts`). It runs that root's CLI, or the newest version in the cache dir when the root is gone, with that node, or `node` on PATH (then Homebrew, `/usr/bin`, nvm) when it is gone, and only ever `serve`. `serve --link ID` goes only with `--login`. Links and `authorized_keys` lines an older version (0.5.0-beta.15 or before) made are no longer served or cleaned up: such a joiner joins again with a new invite. `scripts/remote-docker/` checks it end to end against containers (see Testing).

**A shared machine (`--forward`).** For a joiner who logs in to the host machine as their own account, not the host's (#27), `/sub-human invite --forward` (`webhost.ts` hostForward) starts the listener, adds the room to its served set (mode `ssh-forward`; a room already served over the web keeps its record) and mints a `ws` invite whose tag names the listener key, as `--web` does. The line is `/sub-human join HOST ROOM SECRET --forward PORT`: HOST is `SUB_HUMAN_SSH_ADDR` or this machine's name with no user, so the joiner's own `ssh -G` supplies theirs. The joiner's link spec is `{kind: 'ws', host: '127.0.0.1', port, path: '/sub-human/CODE', tunnel: {user, host, port?}}` (`transports/ws.ts` tunnelSpec). Every dial, the key fetch included, runs `ssh -o BatchMode=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=2 -o LogLevel=INFO [SUB_HUMAN_SSH_OPTS] -W 127.0.0.1:PORT [-p P] -- user@host` (below INFO, OpenSSH says only `stdio forwarding failed`, without why) (`ssh.ts` forwardCommand, tunnel). `ws.connect` speaks the WebSocket over that pipe (its `socket` option), and above the bytes nothing differs from a web link. The target is always loopback, never from the line. When a dial fails, ssh's stderr goes through `ssh.ts` forwardProblem: `administratively prohibited` is AUTH `SSH_FORWARD_REFUSED`; `connect failed` / `stdio forwarding failed` is OFFLINE; a host key, a denied login and (first dial) an unknown name read as for a login link. Every forwarded connection's source at the listener is 127.0.0.1, so they share one `SOURCE_MAX`.

**The PIN, the card and the key binding** (`lib/remote/invites.ts`, `invite-secret.ts`, `admission.ts`, `host-links.ts`, `machine-key.ts`). What each part guards: the SECRET (128 bits) that nobody without the line gets anything (an unknown one is answered "unknown", charged nothing); the tag that the SECRET goes only to the host the line names (no one in between learns it); the PIN, checked online only (5 tries, throttled per invite and per source machine, every wrong one a room line), that a stolen line alone gets nobody in without the card; the card, the host person's signed answer to a line typed without its PIN, that nothing gets in that way they did not mean (a right PIN is that consent said ahead: the room line with its check and the kick undoes a stranger who has both); the key binding that a link is its machine (its machine key proved in every hello) and, over the web, its own Noise key (XK; `hostLinks.keyHolds`: a token over another key is `KEY_MISMATCH`), not a bearer token. A request nobody answers lapses after `ADMIT_TTL_MS`. Replaced in Stage 7b: the 4-digit PIN as CPace's password (vendored `@noble/curves` ristretto255), the enrollment door in `authorized_keys`, per-link ssh keys and the plugin's known_hosts.

**Over the web (1.1)** (`lib/remote/ws.ts`, `noise.ts`, `transports/ws.ts`, `listener.ts`, `tailscale.ts`, `webhost.ts`).
- *Hosting.* `/sub-human invite --web` (Tailscale Serve) or `--public` (Funnel) (`webhost.hostWeb`) starts the **listener** (`sub-human listen`, one per home, `127.0.0.1:7420` only, `SUB_HUMAN_LISTEN_PORT`), adds the room to its served set (`<home>/listen/state.json` `{pid, port, rooms: {CODE: {path, url, mode, tailscale?}}, conns}`, which `doctor` reads), and, with `--web`, runs `tailscale serve --bg --https=443 --set-path=/sub-human/CODE http://127.0.0.1:PORT` (`funnel` for `--public`) with the CLI on `PATH` or in `/Applications/Tailscale.app`, the name from `tailscale status --json` `Self.DNSName`. It mints an invite line (kind `ws`, its tag naming the listener's X25519 key) and shows `/sub-human join https://NAME/…/sub-human/CODE SECRET` and the PIN apart (and Funnel's certificate-transparency warning). The tests and the lab name an HTTPS front of their own instead of Tailscale (`lib/env.ts` webFront: `SUB_HUMAN_WEB_FRONT`, honoured only with `SUB_HUMAN_TEST=1` or `SUB_HUMAN_LAB=1`). `/sub-human invite --stop`, or the listener's sweep when the room closes, turns off that one path (`… --set-path=… off`, never `serve reset`). The host's next join after a reboot restarts the listener (`webhost.ensure`).
- *Joining.* `/sub-human join URL#SECRET [PIN] [--as NAME]` (also `URL SECRET [PIN]`): the room is the URL's last path segment. A WebSocket whose first message is text asks for the listener's key (`{"op": "key"}`, answered `{"v": 3, "key"}`; transports/ws.ts fetchKey). A binary first message is Noise: the listener runs **Noise XK** (prologue `sub-human ws3`: the link's own static key in message 3) and spawns `serve --stdio CODE --via ws [--peer KEY]` with the key XK proved; serve records it on the admission and the link, and holds every later hello over that link to it. Messages that arrive with message 3 are kept for the channel. The link file's transport is `{kind: 'wss', host, port?, path, hostKey, clientKey}` (the private half in `<home>/links/CODE/client-x25519.json`, 0600).
- *The wire.* The daemon's `open` connects a WebSocket (`ws.ts connect`, RFC 6455, hand-rolled with no dependency, over `net` or `tls`), then runs **Noise_XK_25519_ChaChaPoly_SHA256** as the initiator with the pinned key and the link's own static key (`noise.ts`, one token-driven handshake for XK: `node:crypto` X25519, ChaCha20-Poly1305 and HKDF-SHA256, no field arithmetic; checked against the cacophony and snow vectors). Message 1 carries `{v: 3, room}`; message 2 `{ok}` or an `{error}` only the key's holder could write; XK's message 3 carries the link's key, encrypted; a message 2 that does not decrypt is `AUTH` (the link stops). The per-link key is X25519, made on the joining machine for that link and nothing else: node:crypto cannot turn the Ed25519 machine key into an X25519 one, and a kicked link's key dies without touching the machine's identity (the machine key still proves the machine in every hello). Then each binary WebSocket message is one Noise transport message (at most 65535 bytes) of the NDJSON byte stream, through `fromDuplex`, so reconnect, ping and the outbox above work unchanged.
- *Doctor* (`lib/cli/doctor/listener.ts`): `listener` (running, pid, port, rooms; a served room with no listener fails), `web:CODE` (`tailscale serve status --json` still lists the path; Funnel warns that the name is public), and a wss link's hello over its real transport.
- *The listener* never runs `server.ts` in-process: after the handshake, if the room is served and still open, it spawns `<home>/bin/serve --stdio CODE --via ws [--peer KEY]` (the stable shim; KEY the link's own key XK proved) for that connection and pipes plaintext both ways; the child authenticates the hello as over any transport. Before a handshake completes it holds at most 16 connections in handshake (64 in all, at most 8 from one source: the front's Tailscale login or `X-Forwarded-For`), 10 s each, frames of at most 64 kB; after it, the serve child closes a session that made no link within 10 s (`LINK_AUTH_WAIT_MS`), and exits; it pings every WebSocket every 15 s and drops one silent for two intervals. It exits 10 minutes after it serves no room.

**Protocol** (`lib/remote/protocol.ts`). Newline-delimited JSON: request `{id, op, params}`, reply `{id, result}` or `{id, error: {code, message, reason?}}`, stream event `{id, ev, data}`. A frame is at most `LINK_FRAME_MAX_BYTES` (1 MiB).

| Op | Params | Result | Who may | Server does |
|---|---|---|---|---|
| `hello` | `{proto, client, caps, machine, machine_key?, nonce?, token}`, `{…, invite, pin?, as?}` or `{…, login: true}` | `{v, proto, server, caps, room, link, token?, time, machine?, host?, challenge?, closed?}` (time: the host's clock in ms, for `doctor`'s skew check; machine: this machine's id in the room as the host records it) | anyone | version: the highest common one of the two `proto` ranges (a hello with none is `PROTOCOL` `SKEW`; a beta's `v`, the least it needs, is honoured), else `PROTOCOL` `SKEW` naming who updates; `verifyToken`, or `redeemInvite` (the PIN online, then the card; the token is returned once), or `loginLink`; neither: answered, still unauthenticated. A new link records the machine id `machine_key` proves (below) |
| `join` | `{name, role: 'member', pubkey, proof}` | `{ok, rejoin?}` | a link | `checkSeatProof` (the key's holder signed this join), then `seats.enter` with the link's `machine`; another key for a pinned name is `AUTH`; binds the name to the link. A bound link (an admission's one name) joins only that name: any other is `AUTH` before a seat is taken |
| `leave` | `{name, reason}` | `{ok}` | a link, its own seat | `seats.exit` (member_left; the reaper when nobody is left) |
| `beat` | `{name, presence?}` | `{ok}` | a link, its own seat | `members.beat` (lease, presence) |
| `append` | `{payload}` | `{entry}` | a link, `payload.from` its own seat | the seat's quota (`append.human`, `append.agent`, counted in the log) or `RATE` `QUOTA`; then `store.place`: validate, rate, replay, verify against the pinned key; then `decide` after an answer. A system kind is `AUTH` (only the host writes those); a `plan` entry is `INVALID` (only `plan.put` writes one) |
| `subscribe` | `{after, hash, snapshot?}` | stream | a link | the link's `subscribe` quota; one stream per connection (a second subscribe replaces it); `hash12` of the host's line `after` must equal `hash`, else `FORK`; with `snapshot: true` and `after` 0, a host with a snapshot that fits a frame sends `snapshot` (its chain head and line, count, non-chat entries, window, pins, host) and the lines after its id; then `entry` per line, `doc` for `members`, `presence/*`, `tasks`; `end` `{reason: 'closed' \| 'FORK' \| 'AUTH', message?}` (AUTH: the link was revoked). The `snapshot` cap is additive: an older host's caps do not offer it and an older mirror never asks, so either gets every line, as before, across the host's segments; a host that began from its own host's snapshot refuses a replay of lines before it (`FORK`, with the reason) |
| `blob.get` | `{ref}` | `{bytes}` (base64) | a link | `blobs.get` |
| `blob.put` | `{name, bytes}` | `{ref}` | a link | only `plans/<hash12 of the bytes>.md`, at most `PROPOSAL_FILE_MAX`, written once; a new one counts against the link's `blob.put` quota (`RATE` `QUOTA`) |
| `ping` | `{}` | `{pong}` (the host's ms) | a link | the heartbeat; listed in the server's caps, so a client pings only a server that answers. A session whose hello carried `caps {ping: true}` and that then goes silent for `LINK_SILENT_MS` is closed |
| `task` | `{name, req}` | `{ok: true, task, text}` or `{ok: false, error}` | a link, its own seat | `lib/tasks.ts` apply under the room's `tasks` lock (a refusal is an answer, not an error); the link's `task` quota |
| `plan.put` | `{name, req: {plan, base, text, summary}}` | `{ok: true, version, unchanged?}`, `{ok: false, conflict: {version, text}, error}` or `{ok: false, error}` | a link, its own seat | `lib/plans.ts` put under the room's `plan` lock (compare-and-swap on the plan's current version); the link's `plan` quota |

Error codes, the same on both ends and on the wire: `INVALID`, `RATE`, `LOCK`, `NO_ROOM`, `OFFLINE` (the link is down or the deadline passed), `HOST_ONLY` (an op a mirror never performs), `AUTH` (no or bad token, a used invite, a `from` not this link's seat, a key mismatch, a bad signature, a replayed nonce, a stale `ts`), `FORK` (the mirror's last line is not the host's), and `PROTOCOL` (unknown version, malformed frame).

**Reasons** (`lib/reasons.ts`). Beside its code an error may carry a typed `reason`, which says exactly which failure it is: `RoomError(code, message, reason?)`, `error.reason` on the wire (additive: a 0.5 beta sends and reads none), kept by the bridge, the daemon's socket, its `link` document (`why`) and its state file (`lastReason`). Code that decides keys on it, never on the message's words (the message is for people): the outbox (`PLACED_ALREADY`), the mirror (`UNKNOWN_OUTCOME`), `doctor`'s fix lines and `link --forget` (`ROOM_CLOSED`, `NO_SEAT`, the spent-invite reasons). The list: `AUTH` PLACED_ALREADY, INVITE_UNKNOWN, INVITE_USED, INVITE_BURNT, INVITE_EXPIRED, INVITE_OTHER_MACHINE, INVITE_OTHER_LINK, PIN_NEEDED, PIN_WRONG, PIN_LAST, PIN_THROTTLED, HOST_KEY_MISMATCH, KEY_MISMATCH, ADMIT_REFUSED, ADMIT_LAPSED, ADMIT_REVOKED, ADMIT_LATE, TOKEN_UNKNOWN, LINK_REVOKED, NOT_BOUND, NOT_JOINED, LOGIN_ONLY, MACHINE_TAKEN, SSH_HOST_KEY, SSH_DENIED, SSH_NO_SHIM, SSH_NO_ROOM, SSH_OLD_HOST, SSH_HOST_UNKNOWN; `OFFLINE` UNKNOWN_OUTCOME, NOT_SENT, DAEMON_DOWN, ADMIT_WAITING, QUEUE_FULL; `RATE` QUOTA; `PROTOCOL` SKEW; `FORK` LOG_RESET, NOT_CHAINED; a stopped link ROOM_CLOSED, NO_SEAT. Against a beta host, which sends none, a decision falls back to the code alone (a duplicate a slow link resent is then reported unsent, although it landed).

**Quotas** (`lib/config.ts` LINK_QUOTAS, `lib/remote/quota.ts`). Every op a link sends counts against its own window; over one is `RATE` with reason `QUOTA` and when to try again.

| Op | Max per window | Counted |
|---|---|---|
| `append.human`, `append.agent` | 30 per minute | per seat, in the log (a Claude's posts to every addressee together) |
| `blob.put` (a new plan) | 40 per hour | per link, the host document `remote/quota` (a reconnect resets nothing) |
| `subscribe` | 60 per 10 minutes | per link |
| `seat` (join, leave) | 30 per 10 minutes | per link |
| `hello` | 120 per 10 minutes | per link |
| any hello on one connection | 10 per minute | per connection |
| `task`, `plan.put` (a plan version offered) | 60, 30 per minute | per link |
| `beat`, `blob.get`, `ping` | 120, 600, 60 per minute | per connection |

**The host's watch.** A `subscribe` stream follows `FsRoomStore.watch` (`lib/room/watch.ts`): one recursive `fs.watch` per room directory and process (shared by every stream of the web listener), coalesced to one change per turn of the event loop that names what changed: the log (a line, a segment, the snapshot) and which documents. A log change reads the tail; a changed document (`members`, `tasks`, `presence/NAME`) is read again alone and sent when it differs; a `members` change also checks whether the room closed. A poll every `FOLLOW_SLOW_MS` (2 s) covers an event the watcher missed; a watcher that cannot start or fails, or a store with no watch (the memory store), is polled every `FOLLOW_POLL_MS` (250 ms) as before. A replay (a first sync, a long gap) goes out `REPLAY_BATCH` (500) lines per turn and waits for the transport to drain (`Transport.writable`) between batches; after a write the stream sends everything at once (read-your-writes).

**Machine ids.** Each home has an Ed25519 machine key (`lib/remote/machine-key.ts`, `<home>/keys/machine.json`, 0600, under the hooks module's `Read` guard). The link daemon's hello carries its proof: over an invite line a signature over the room and the challenge the host's reply to the hello before handed out (`machine-key.ts` proofFor; every hello reply carries a fresh `challenge`, so the proof is good in that one session: anyone who saw it cannot replay it within the clock skew), else over the room and a fresh `ts` (a token's or a login's hello, where the id decides nothing a replay could take); the host records the machine id the key gives (`k` and 15 hex of its sha256) for a new link, and the id the hello reports only as the link's `label`. The hello's reply says the recorded id; the joiner keeps it per room (`<home>/machines.json`, `home.machineIn(code)`), reports it in every later hello and compares a seat's `machine` with `home.isMine` (any of this home's ids): liveness, the admission card's targets, the seat's `account`, `mod/send.ts`'s choice between a native and a room message. One key, one id, for every room and host: a machine that joins again (a new invite) is the machine it was, and no machine without the key can be it. A hello with no proof (a 0.5 beta's) keeps the reported id, which may not be the host's own or another link's (`AUTH` `MACHINE_TAKEN`).

Stream events besides `entry`, `doc` and `end`: `snapshot` (the host's snapshot, first, for an empty mirror that asked). **When the host leaves**, the room waits: nothing moves it (no handoff, no failover); each mirror's link goes offline and redials with backoff, and a person's `@room` posts queue in that mirror's outbox until the host is back (or age out after `LINK_OUTBOX_AGE_MS`).

**Versions.** `protocol.PROTO` is the range of protocol versions an end speaks (now 5–5: protocol 3's invite line (its SECRET in hello's `invite`, the PIN checked online, `as`), the hello's `nonce` and the reply's `host` proof and Noise XK over the web, plus the `task` and `plan.put` ops, with the host epochs and the handoff ops gone; 5, 0.5.0-beta.24, the author's own check of a plan version first, which a protocol-4 end would decide as a sign-off by the author alone) and `PLUGIN_VERSION` its plugin version. The client's `hello` sends `proto` and `client` (and may send `v`, the least it needs, which the server honours). The server answers `v = negotiate(its range, the hello's)` plus its own `proto` and `server`. A hello with no `proto` (a sub-human before 0.5) and no overlap are both `PROTOCOL` `SKEW` with `skewMessage`, which names the side to update: "host runs sub-human 0.4.0 (protocol 3–4); you run 0.3.0 (protocol 2). Update your plugin: /plugin update sub-human", or "The host must update" when the joiner is newer. A protocol-3 or -4 peer (0.5.0-beta.23 and before) shares no version with this one: its hello is `PROTOCOL SKEW` with that message, the daemon stops on it, the join shows it, and links it made stop until the person updates and joins again. Readers tolerate a newer host: lines of unknown kinds or fields are stored verbatim and rendered generically (an unknown `via` as "bob (via relay)", never as the person's words, and never a wake), and an unknown streamed document or event is skipped and logged instead of stopping the link. Writes stay strict: the host validates every payload, so a newer joiner's new kind is `INVALID` on an older host (the host is updated first). `test/remote-server.node-test.ts`, `remote-invite-line.node-test.ts` and `test/remote-link.node-test.ts` fake N-1 and N+1 on both ends.

**What changed for trust.**
- **Sig v2.** A signature covers the payload, not its place in the log (without `id`, `at`, `prev`; with `room`, `from`, `nonce`, `ts`), so the remote hook signs and the host places. v1 lines still verify. The host refuses a replayed nonce and a `ts` outside `SIG_SKEW_MS` (10 min); `at` is the host's clock.
- **Keys are pinned in the log** and strictly: `member_joined` carries the seat's public key, the first key per name is that name's for the room's life, and a lost key means a new name.
- **A link writes only as its own seats.** The server checks every `from` against the seats joined over that link (`mayWriteAs`), validates again and verifies against the pinned key. A `join` needs a proof signed by the seat's key, since the public key alone is in the log.
- **Credentials.** An invite line is single-use and shown once; the host keeps `sha256(secret)` and `sha256(secret:PIN)` only. The link token is a seat-level credential: kept in clear in the joining machine's link file (0600, the same trust as the seat key), hashed on the host; a web link made under protocol 3 also needs its own Noise key, so the token alone gets nowhere. An invite is untrusted input: its locator is only a home path or a plain `user@host[:port]`, and the daemon always runs this plugin's own `serve` (or `ssh` with fixed options), never a command or option the invite names. The SECRET goes only to a host that proved the key the line's tag names; the PIN is checked online only (5 tries per invite, throttled, at most 4 open), and one that holds still waits for the host person's card; neither reaches a model (every `join`/`invite`/`admit` prompt, and any with a word of digits or a SECRET-shaped word, is a hidden block, and neither step takes the seat) and the PIN leaves the joining machine's link file once the host answered. Over ssh nothing is written to `authorized_keys`: the joiner's own login is the way in. The Bash guard denies `sub-human invite`, `admit`, `kick`, `listen`, `link`, `serve` and `doctor --fix`/`--bundle` to a model (a plain `doctor` is read only) and sends the person to a terminal outside Claude Code (its `!` mode would put the output in the conversation: run there, `invite` masks the SECRET and the PIN). A link the host refused before any token drops its invite and PIN from the link file (`refused` says why).
- **Over the web, the front sees ciphertext.** Tailscale or Funnel's relays end TLS and see IPs, timing and sizes; every byte inside the WebSocket is Noise ciphertext keyed to the listener's own X25519 key (`<home>/listen/host-x25519.json`, 0600, random, never derived from or used for anything else), which the joiner pins from the URL. The listener binds loopback only. A Funnel hostname is public (certificate-transparency logs), so probes cost a PIN try at most, and each wrong PIN is a room line.
- **Addressed is not private.** A post with `to` has its own rate bucket (`RATE_ADDRESSED_MAX`), but the whole room reads the log, on every machine.

**Latency** (Apple M2, node 24; two homes on one machine over the pipe; `test/support/link-bench.ts`, `test/support/bridge-bench.ts`). Times in ms, p50 / p99.

| | host | remote | overhead |
|---|---|---|---|
| one signed append, bridge up (the link's round trip) | 0.70 / 1.1 | 1.0 / 1.6 | 0.34 / 0.52 |
| `prompt.ts`, a plain prompt (no worker) | 38.2 / 43.2 | 38.3 / 41.7 | 0.1 / −1.5 |
| `prompt.ts`, an `@room` post | 41.3 / 43.8 | 60.0 / 63.1 | 18.8 / 19.4 |

A hook that only reads costs nothing extra; one that writes pays about 20 ms, nearly all of it the worker's boot (about 16 ms), plus a round trip of about 1.5 ms.

**Observability.** `lib/room/link-state.ts` reads how a link is doing: the daemon's state record `<home>/links/<code>.state.json` (`{state: online|connecting|offline|fork|stopped, since, attempt, lastError, lastReason, lastCode, rttMs, queued}`), else the mirror's `link.json`; a record whose daemon pid is gone reads `offline`, not running, since it was last known online (fork and stopped stay). The queued count is the mirror's `outbox.json` itself (the records' only when it is not a list), so it shows while any post waits, online too (a slow host). The room row (`lib/rows.ts`, so also the agent statusline) leads with the link while it is not online (`✕ offline 2m · 2 queued`, `… connecting (3)`, `✕ not running (offline 2m)`, `✕ stopped`, `✕ out of step: /sub-human doctor`) and ends with `⇄ online` (`⇄ online · 1 queued` while a slow post waits) while it is; the tail's line is `room link: OFFLINE` / `STOPPED` / `FORK` and `back online`; a room hosted here shows nothing. `sub-human doctor` (`lib/cli/doctor.ts`, the checks in `lib/cli/doctor/`: `links.ts`, `ssh.ts`, `listener.ts`, `claude.ts`, `rooms.ts`, `redact.ts`) checks, each with a fix: Node 22.18+ or 24.3+, the home's modes (0700), the serve shim and its pointer, `authorized_keys` lines that bypass the shim (written before 0.5: remove them and invite again), `ssh -V`, and per link its transport, daemon, state and last error with its reason (a link's fix is chosen by `lastReason`, never by the error's words) (the state record, else the daemon's log), plus a `hello` without a credential to the host (the server answers it and nothing else; over ssh, BatchMode, with ssh's own error turned into a hint), both protocol versions and, when the reply carries the host's time, the clock skew (warn at 2 min, fail at `SIG_SKEW_MS`). A host that answers beside a link that is down is never "reachable" next to `✕ offline`: the line says the host is up but this machine's link to it is down, and the fix what restarts it (a bare `/sub-human`: `link-socket.ts` `start` launches a daemon that is gone and tells one that is offline to redial now, `SIGUSR2`). Then Claude Code's version against `cc.MIN_VERSION` / `cc.PROBED_VERSION` (and `cc.probe` of the binary when it differs; an internal reported changed on that version is named), the bg daemon (`cc.daemonStatus` + `cc.exeState`: a deleted executable fails, another version than `claude --version` warns; the fix is `claude daemon stop --any --keep-workers`, never run by `--fix`), each open room's room session (bound and live, or why its start failed), and settings that turn hooks off. `--fix` refreshes the shim and repairs the modes; `/sub-human doctor` runs `doctor --quick` read only inside the session. `--bundle` writes the report as an allowlist (versions, config timings, verdicts, link states, recent daemon errors) with every free text redacted: `~` for paths under `$HOME`, room codes, host and user names and IPs hashed with a per-bundle salt, SSH keys cut to a fingerprint prefix, invites, tokens and long hex removed; no log entry is ever read into it.

## Security model

One machine per room (its host), trusted collaborators: everyone on the host runs as its one OS user, and the host itself is trusted by everyone who joins it. The threat is a member's Claude (possibly steered by text posted in the room) speaking or consenting as a person. Defences: `via=human` only from hooks (and the sign-off fallback's answer to Claude Code's own MCP question, which the model never sees: an `Elicitation` hook can answer it, as a `PermissionRequest` hook can the plan view), signed with a key only hook processes (and that one answer) load (on whichever machine the person sits; the host verifies against the key pinned in the log); the store guard (the hooks module's `mod/guard.ts`, in-process) denies file-tool writes into the store, reads of its secret directories (`keys/`, `listen/`, `links/`, `sessions/`) and of Claude Code's history and this session's transcript, and Bash commands that name the store or reach it by a placed word (a glob, `?`, a brace, a `cd`), point a tree walker above it, set `SUB_HUMAN_HOME` or run the plugin's modules: a lexical check, so a model with Bash as the same user can still build the key's path at run time, and the signature proves a person's words only against a Claude that never read the key (the hash chain, which `sub-human doctor` and `verify CODE` check, still shows a line written around the store); the module's `prompt.submit` gate drops an `@room` whose engine-set origin is not the person's (composer, sdk, bridge), and at-room posts only with that origin and the session's module nonce (a seat requires the module). The module mints the nonce per session id, keeps it in `$.state`, and `mod-hello` writes it to the 0600 lease `<home>/sessions/mods/<sid>.json`: forging an `@room` takes reading that lease, which the guards deny by path but a determined local process can still do. The store guard is a string check: a script file written first, an obfuscated path or a variable built at run time evades it. What it cannot evade: `via=human` needs the seat key's signature, readers mark an unsigned human line "(unverified)", and the hash chain shows an edited log. The room session's typed-input refusal reads the origin unchecked, since forging it only refuses more. An `@room` is refused, never passed to the model, whenever the prompt shim fails; consent only from the native dialog; a link writes only as the seats joined over it, an SSH key reaches only its forced command's room and link, and the guard denies `sub-human invite|admit|kick|listen|link|serve` and `doctor --fix`/`--bundle` to a model. The guard also denies `Read` of a seat's private key (`<home>/keys`): the one file a model could sign `via=human` with; the rest of the store stays readable. Over a link the host binds an admitted machine to the one name the card let in (`LinkRecord.bound`), counts a link's posts, task requests, plan versions and new blobs against its quotas (`LINK_QUOTAS`), and a plan version's text is only what the hooks capture at `ExitPlanMode` (the plan file's text as Claude Code passes it, header off), stored as people's content and sent to every mirror; no model writes a `plan` entry or a task file directly. Not covered: other MCP servers, a hostile local user. Full list: [README → Threat model](../plugin/sub-human/README.md#threat-model).

## Claude Code contract (generated)

Every internal the plugin relies on, from `lib/cc/contract.json`. `§` points into [`docs/internals/cc-2.1.281.md`](internals/cc-2.1.281.md) (changes since: [`cc-2.1.292.md`](internals/cc-2.1.292.md), [`cc-2.1.296.md`](internals/cc-2.1.296.md), [`cc-2.1.300.md`](internals/cc-2.1.300.md)); "Checked on" is the first version the entry was checked against and the last (the JSON's `probed`). Each entry also carries the literal binary search strings, optional code shapes (`~` for a minified identifier) and, for an array the plugin relies on, `contains` groups: the array found at a literal or shape holds those names, in any order, more allowed. `npm run probe` checks all three. An entry reported to change on a newer version than the probed one carries `degraded` (the version, the issue): the probe may still pass there, so `doctor` and the probe name it.

The code that reads Claude Code is `lib/cc/`: `env.ts` (the session's env, the config, plans and task directories, the settings the plugin reads, the hook matcher rule; imported by the hooks, so it loads no JSON), `transcript.ts` (the JSONL readers, the plan file, the dialog's answer, the person's last prompt, pastes), `bg.ts` (`claude --bg` jobs, `claude agents --json`, `claude stop`, `claude daemon status`, a process's executable, and `clientEnv`, the env a `claude --bg` client is handed) and `contract.ts` (the JSON typed, `probe`, `locateBinary`, `degradedOn`). `scripts/probe-cc.ts` reads the JSON itself and runs `contract.ts` `probe`, the same matcher `sub-human doctor` runs on a user's machine, where `scripts/` is not installed.

**Per-version verdict.** Each entry names the `feature` it serves. `lib/cc/verdict.ts` keeps what this machine found for a Claude Code version in `<home>/cc/<version>.json` (`{version, probedAt, contract, failed, off}`; `contract` a hash of the JSON, so a plugin update checks again). The module reads `$.session.version` and hands it to `mod-hello`, which reads the verdict, starts `node lib/cc/verdict.ts run VERSION` detached when there is none (the probe, ~3-5 s, under one lock per version, only against the binary whose `VERSION` is that version; the probed version is verified without one), keeps the version in the session's mod lease (`cc_version`) and in `<home>/cc/seen.json`, and returns `cc: {version, verified, off}` in the hello. `off` holds only the gated features (`mod/core/cc.ts` `GATED`: room-session, tasks, plan-edit, sign-off; sign-off implies plan-edit) of failed entries (probe misses plus `degraded` ones); a failed core, cosmetic, rows or other entry only makes the version unverified. A seated session on a version with something off gets one `$.ui.log` line (`ccNotice`), once per version. Node code asks `verdict.off(feature, {sid})` (the lease's version) or `verdict.off(feature)` (the version seen last). `SUB_HUMAN_CC_OFF=feature,…` forces features off. `doctor` (`--quick` too) reports the kept verdict, and a full doctor's probe is kept as one.

## TypeScript

The runtime (`lib/`, `hooks/`, `mcp/`, `statusline/`, `mod/`) is ESM `.ts` with no build step: what is committed is what runs.

- **Node strips the types** of each `.ts` it loads (Node 22.18+ or 24.3+: the first with no flag, no ExperimentalWarning and `import.meta.main`; 23 never had it). Only erasable syntax works (no `enum`, `namespace`, parameter properties or decorators: `erasableSyntaxOnly`), and every import spells out its `.ts` specifier. Every node command Claude Code starts (`.mcp.json`, `hooks.json`, the module's shims) runs through `hooks/node.sh`: the node the plugin last ran with (`<home>/bin/current`), else node on `PATH` if it is one of those, else the first such node in the usual install places (Homebrew, nvm, fnm, mise, asdf, Volta); with none it says what to do, and `/sub-human` shows it.
- **The hooks module** (`mod/register.ts`) runs in Claude Code's Bun worker, which transpiles it itself.
- **Nothing checks types at run time.** `tsc` runs only in `npm test` (`npm run typecheck`) and CI. The root `tsconfig.json` is the whole plugin as one project: the runtime, its node tests, the module's wiring tests (`mod/test`) and the two plain JavaScript files (`hooks/compile-cache.js`, `lib/cache-dir.js`: `// @ts-check` with JSDoc, `allowJs` and `checkJs`). Its flags: `strict`, `noUnusedLocals`, `noUnusedParameters` (an unused parameter takes a `_` prefix), `noImplicitReturns`, `noImplicitOverride`, `noFallthroughCasesInSwitch`, `isolatedModules`, `verbatimModuleSyntax`, `erasableSyntaxOnly`, `noEmit`, `exactOptionalPropertyTypes` (an optional field that a caller fills with `undefined`, or that a decoder's `opt()` reads, is typed `?: T | undefined`; a field set only when there is a value is spread in, `...(x ? { x } : {})`) and `noUncheckedIndexedAccess` (an index read is `T | undefined` until checked: a destructuring, `.at()` with a check, `for…of`, or a regex group read as `m?.[1]`). `tsconfig.runtime.json` checks the runtime again on its own, so it never leans on a test's declarations, and `scripts/tsconfig.json` extends the root for the repo scripts. Runtime code has no non-null `!` (the ratchet holds it at 0): a value that may be missing is narrowed, or a slot gets a harmless default (a hold's `resolve` is a no-op until its call blocks). `noPropertyAccessFromIndexSignature` is off: it reports 756 errors over the plugin and its tests (223 in the runtime) and 398 in the scripts, nearly all dotted reads of `Record<string, T>` documents and fixtures that `noUncheckedIndexedAccess` already types `T | undefined`, so the flag would buy bracket syntax and little safety. tsc takes no extensionless file, so `scripts/typecheck-shim.ts` checks `scripts/sub-human` through a temporary `.js` copy. `typescript`, `@types/node`, `oxlint` and `oxlint-tsgolint` are root devDependencies; `plugin/sub-human/package.json` is only `{"type":"module"}`, so Claude Code installs nothing.
- **Claude Code's types** come from `typings/claude-code/`, a committed snapshot of the declarations Claude Code writes beside a hooks module (`import type … from 'claude-code'`); the same file declares `claude-code/testing`, the kit `mod/test` imports. `typings/claude-code-tools/` (the built-in tools' inputs) and `typings/claude-code-mcp/` (the MCP tools' inputs) merge into it. Claude Code writes the folder (`plugin/sub-human/.claude-plugin/types/`, gitignored) when an interactive `claude --plugin-dir plugin/sub-human` session loads the module (not `-p`, `plugin validate` or `plugin test`); `npm run typings` (`scripts/typings.ts`) copies it into `typings/`, and `npm run probe` fails while `typings/claude-code`'s first line, "Written by Claude Code X", is not `contract.json` `probed`.
- **Lint and the ratchet.** `npm run lint` (`scripts/lint.ts`) runs oxlint with its type-aware rules (oxlint-tsgolint, on tsgo; `.oxlintrc.json`: `no-explicit-any`, `no-non-null-assertion`, the `no-unsafe-*` family, `no-floating-promises`, `no-misused-promises`, `only-throw-error`, `consistent-type-imports` and `no-unnecessary-type-assertion` are errors on `plugin/sub-human` and `scripts/`, and `switch-exhaustiveness-check` in runtime code; `no-floating-promises` allow-lists node:test's `test`, `describe`, `it` and `suite` (`allowForKnownSafeCalls`, a package specifier), whose promise the runner awaits; a deliberate fire-and-forget says `void p` and why. `no-unsafe-type-assertion` (every narrowing cast) and `prefer-nullish-coalescing` (with `ignorePrimitives`: a `||` on a string or number is a choice; the rule does not see a brand as a primitive, so its last runtime reports are left) warn, as does the correctness category), then `scripts/ts-ratchet.ts`: the explicit `any`, `as` casts (not `as const`) and non-null `!` per directory may not rise above `scripts/ts-ratchet.json` (`--update` writes lower counts). Lint bans `any` and `!` (a reasoned `oxlint-disable-next-line` aside) but not a cast, so the ratchet is what caps casts, and the disables too. tsgolint types each file by the nearest `tsconfig.json` whose project holds it and takes no other, which is why the root config is one project; the lint moves Claude Code's generated `plugin/sub-human/tsconfig.json` (gitignored) aside for its run, since that one would claim `hooks/`.
- **Shared types** live beside their slice: `lib/room/types.ts` (entries, the store), `lib/remote/types-core.ts` and `types-rest.ts` (the wire, links), `lib/types-app.ts` (seats, the tail, rows), `hooks/types.ts` (hook payloads), `mod/core/types.ts`, `lib/cli/types.ts`, `mcp/types.ts`.

- **Tests are TypeScript too.** `plugin/sub-human/test/**/*.node-test.ts` and their helpers (`test/helpers.ts`, `test/hooks/helpers.ts`, `test/support/*.ts`) are ESM `.ts` that `node --test` runs with the same type stripping, typed against the plugin's own types. The root `tsconfig.json` holds them with the runtime, under the same flags. A test never writes `!`: `test/support/must.ts` `must(v, what)` asserts a value present and narrows it, `assert.ok(x)` narrows, `test/support/fs-store.ts` `fsStore(s)` asserts the fs store; an object a test builds is a typed const or a small typed factory, not a cast, and a deliberately malformed input is written as it is under `// @ts-expect-error -- deliberate: why`. `mod/test` is typed against `claude-code/testing` (`On`, `Engine`) with no `any` and no cast. They are named `*.node-test.ts`, not `*.test.ts`, because `claude plugin test` collects every `*.test.ts(x)` under the plugin it is given (recursively, skipping only `node_modules` and dot folders; cc CONTRACT `plugin-test-discovery`): with that suffix `npm run test:mods` runs only `mod/test/*.test.ts`, and a bare `claude plugin test plugin/sub-human` stays correct too. `npm run test:plugin` globs them (`node --test 'plugin/sub-human/test/**/*.node-test.ts'`, each file in its own process) and preloads `test/helpers.ts` with `--import`.
- **Boundaries are decoded.** Data from outside the type system (a file, stdin, the wire, a child's stdout) is `unknown` until a decoder accepts it. `lib/decode.ts` has the decoders, zero-dependency and loaded only where data is decoded: `str`, `num`, `int`, `bool`, `lit`, `arr`, `record`, `obj` (unknown keys allowed and kept: the value is the input itself), `opt`, `nullable`, `union`, `refine`, `decode`, `decodeOr`, and `Result` (`lib/errors.ts`'s). `objAs<T>()` reads a plain object as `T` without checking its fields. It is used for a document whose readers check each field as they use it, such as this home's own records, the store's documents and Claude Code's files. `lib/io.ts` `readJson(file, decoder, fallback)` and `readInput()` return what was decoded, or `unknown`. A decoder of an on-disk record accepts every shape an older version wrote: only the fields every reader needs are required (`test/decode.node-test.ts` holds such records). The hooks' stdin is checked in `hooks/run.ts` by hand (a hook loads only its handler's modules): each base field must be a string, and the handler's own fields are its input type's, each one optional and checked where it is read. The handlers sit in a table checked as `Handler<its own input>`. The wire's params are `WireParams<O>` (each field `unknown`) until the op checks them.
- **Errors.** A catch variable is `unknown` and is read through `lib/errors.ts` (zero runtime imports, so a hook loads it for free), never cast: `msgOf(e)` (its message, else `String(e)`), `stackOf(e)`, `errCode(e)` (any thrown value's string code: a RoomError's, a system error's), `isErrno(e, code?)` and `isCoded(e)`, the guard for `CodedError` = `RoomError | NoiseError` (their prototypes carry a `Symbol.for` brand). `RoomError.code` is a `WireCode`, whose source is `lib/remote/protocol.ts` `CODE_NAMES`: a code that is not one of them does not compile, and one that arrives from a peer, the bridge or the link socket reads as `INVALID` (as the server and the link socket already send one). `lib/reasons.ts` `REASON_CODE` is the source of `Reason` and pairs each reason with its code (null: a reason a link stops with, carried beside the stop's code); `ReasonFor<C>` types the helpers that build an error of one code (`server.ts` `authError`, `invites.ts` `authError`, `ssh.ts` `loginProblem`), and `test/errors.node-test.ts` checks every literal pair in the source. `Result<T, E = RoomError>` lives here too (`lib/decode.ts` re-exports it). A hook's `capture` says whether its handler threw (`threw`), so only an Error or an unknown is rethrown.
- **Closed unions.** Every switch over a closed union ends in `assertNever(x, what)` (`mod/core/never.ts`: pure, no imports, so the hooks module, `lib/` and the hooks share the one copy, as with `mod/core`'s constants; `hooks/reply.ts`, which every hook loads beside its handler alone, inlines the same `const none: never` check). tsc refuses the call while a member is unhandled, and lint's `switch-exhaustiveness-check` is an error in runtime code (`.oxlintrc.json`), so a `default:` cannot stand in for the missing cases. The domain tables are the source of their unions, on `lib/reasons.ts`'s pattern (an `as const` tuple, its union, a guard that is a Set lookup with no cast): `lib/room/validate.ts` `AGENT_KINDS`, `HUMAN_KINDS`, `SYSTEM_KINDS`, `LEGACY_KINDS`, `TASK_OPS` and `VIAS` (`Kind`, `LegacyKind`, `TaskOp`, `Via` in `lib/room/types.ts`), `lib/remote/protocol.ts` `OPS` and `EVENTS` (`Op`, `EventName`; `OpParams`, `OpResults` and `EventData` are keyed by them), `lib/room/link-state.ts` `STATE_WORDS` (`LinkStateWord`) and `lib/room/members.ts` `PRESENCE_STATES` (`PresenceState`); `test/unions.node-test.ts` checks each union against its table. Open data keeps a graceful default: a log line's `kind` is `KnownKind` or a newer host's word, so a reader that branches over several kinds first narrows it with `validate.ts` `parseEntry(e)` (the entry itself, typed `KnownEntry`, or null for a kind this version does not know; no copy), handles the null, then switches (`lib/room/consent.ts` fold, `lib/room/render.ts` chat line). `isKindOf(e, 'say')` narrows a single-kind filter. The per-kind types (`EntryOf<K>`) claim only the kind: an older or hand-edited log may lack the other fields. The two state machines keep one record each (the link engine's `EngineState`, the consent `Review`): their step functions move a record from phase to phase with its fields carried along, and the reducer tests pin which fields each phase holds.

| an `@room` post, warm (median) | ≤ 50 ms | 1.5 ms | **0.6 ms** |
| the status line, warm (median) | ≤ 30 ms | 5.5 ms | **3.7 ms** |
| an `@room` post, a fresh process | ≤ 60 ms (cold) | 7 ms | **5.5 ms** |
| the status line, a fresh process | ≤ 60 ms (cold) | 86 ms | **20 ms** |
| the first append in a room from before segments (it seals the 15 MB log once) | | 128 ms | 137 ms |

The warm append reads back only the active segment and the snapshot's window; the status line reads `room.readRecent` (every non-chat entry and the lines since the last rotation) instead of every line.

**Idle cost per seat (stage 8, for the hub decision).** The plan's test for Stage 9 (the hub) is: skip it if, at N ≤ 5 seats, tail + hold + status line cost under 1% of a core idle, with no `ps` on the hot path. This was measured on an Apple M2 (8 cores, macOS, node 24.15, Claude Code 2.1.296) in a scratch home with fake seats (sleeping processes) and a fake MCP client, no real Claude. Each tail and room MCP server was left idle for 60 s, and `ps -o time=` was read at the start and end of the window (10 ms resolution). The status line figure is the median of 20 fresh runs. A PATH shim logged every `ps`.

| Per seat | 1 seat: CPU % of a core | 1 seat: `ps`/min | 5 seats: CPU % per seat | 5 seats: `ps`/min |
|---|---|---|---|---|
| room tail | 0.28 | 2 | 0.22–0.23 | 10 per tail (50 on the machine) |
| room MCP server with its holds (1 s timer only while a hold is open) | 0.18 | 0 | 0.18–0.20 | 0 |
| status line, one refresh (a fresh `node`) | 30 ms CPU, 40 ms wall | 0 | 40 ms CPU, 40 ms wall | 0 |
| status line every 5 s (Claude Code's rate while rows show) | 0.6–0.8 | 0 | 0.6–0.8 | 0 |
| **total** | **1.1–1.3** | 2 | **1.0–1.2** | 10 per host tail |

At stage 8 the only idle `ps` was the host tail's seat sweep: `ps -o lstart= -p PID` per local seat (`lib/lock.ts` pidStart, cached 30 s), not the batched `pidStarts`; the review fix pass removed it (below). Tail and hold together cost 0.4–0.5 % per seat and stay flat from 1 to 5 seats. The total is just over budget because of the status line, which is Claude Code starting a node process every 5 s; a hub would not remove that cost. Not measured: the room's Claude's own tail, a seat in a room hosted elsewhere (its link daemon), the host's per-link `serve`, and real sessions.

**After the review fix pass (stage 8b), the same scripts on the same machine.** The seat sweep reads every local seat's start time with one `pidStarts` call and keeps it while `kill(pid, 0)` finds the pid (at most 10 minutes; a pid seen gone is dropped, so a reuse is read again), and the status line's entry no longer loads `lib/tail.ts`, `lib/proposal.ts` with the consent reducer, or `lib/room/watch.ts` (42 plugin modules, now 38; no remote code before or after).

| Per seat | 1 seat: CPU % | 1 seat: `ps`/min | 5 seats: CPU % per seat | 5 seats: `ps`/min |
|---|---|---|---|---|
| room tail | 0.28 | **0** (was 2) | 0.22–0.25 | **0** (was 10 per tail) |
| room MCP server with its holds | 0.22 | 0 | 0.17–0.23 | 0 |
| status line, one refresh (a fresh `node`; 100 in a row, per refresh) | 46 ms CPU, 42 ms wall (was 50 and 44; a bare `node -e ''` is 24 and 25) | 0 | the same | 0 |
| status line every 5 s | about 0.9 by the 100-run figure (0.6–0.8 by stage 8's 20-run median at 10 ms resolution, unchanged) | 0 | the same | 0 |

**Stage 9 (hub): not built.** Tail and hold cost 0.4–0.5 % of a core per seat, flat from 1 to 5 seats, and no `ps` runs while idle any more; the rest is the status line, which is Claude Code starting a fresh `node` every 5 s while rows show, and half of each refresh is node's own start. A hub would not remove that process; it would add a long-lived host process (with the lock busy-wait the plan says to retire first) to save the 0.4–0.5 % per seat that tail and hold cost now.

## Testing

- `npm test`: `npm run typecheck` (strict `tsc` over the whole plugin, then the runtime alone (`tsconfig.runtime.json`), then the repo scripts (`scripts/tsconfig.json`), then the CLI shim; zero errors), then `node --test` over `plugin/sub-human/test/**/*.node-test.ts` (each file in its own process, in parallel; `test/helpers.ts`, preloaded with `--import`, strips `CLAUDE*` env and removes temp dirs) and `scripts/test/**/*.test.ts`. Hooks are driven as child processes with JSON payloads, through `hooks/run.ts <handler>` as Claude Code and the module run them (`test/hooks/`; `test/hooks/stdin.node-test.ts` feeds every handler stdin it cannot use). The tail runs on a fake clock (`lib/clock.ts`).
- **Store contract**: `test/store-contract.node-test.ts` runs one suite against `FsRoomStore`, `MemoryRoomStore` and `remote` (a mirror through the bridge to a server on a worker thread); `store-bypass.node-test.ts` checks nothing else touches room files; `hooks/security.node-test.ts` checks who can load the signer.
- **CI**: `.github/workflows/ci.yml` runs `npm test` on Node 22.18.0, 22, 24 and 26 (ubuntu) and Node 24 (macOS), `npm run lint` once (ubuntu, Node 24), `node scripts/check-version.ts origin/<base>` on pull requests, and a separate job runs `npm run test:remote-docker` (Docker on ubuntu). Without Claude Code the mods tests and the probe test skip.
- **No timing guesses**: a test waits on a condition (a gate file the stub claude waits for, a child's pid, `test/support/started.ts` stamping a child's start) or reads what the code asked for (the link's retry delays), never on a sleep that a loaded machine outruns. `npm test` passes with four copies running at once.
- **Probe**: `npm run probe` (`scripts/probe-cc.ts`, through `cc.probe`) checks the installed Claude Code binary for every `CONTRACT` search string and shape (about 3 s: one latin1 view, each shape tested only around its longest literal), and fails while the typings snapshot names another Claude Code than `contract.json` `probed`; `test/cc.node-test.ts` runs it when a binary is present and bounds its CPU time, not its wall time. No search names a minified identifier (shapes use `~` instead), so a miss means the code itself changed: re-read that spot and record what changed in a new `docs/internals/cc-<version>.md`.
- **Docs**: `npm run docs` regenerates this file's tables; `scripts/test/arch-doc.test.ts` fails when they are stale.
- **Remote**: `remote-protocol`, `remote-server` and `remote-link` tests cover the wire, invites, links, quotas and the daemon; `link-engine.node-test.ts` drives the daemon's state machine from a table on the fake clock; `room-watch.node-test.ts` the host's watch; `remote-e2e.node-test.ts` runs two homes on one machine with the real hooks as child processes and the daemon over the pipe transport. `npm run test:remote-docker` (opt-in, needs Docker; `scripts/remote-docker/harness.ts scenarios`) runs the lab's scenarios over real SSH and wss (`scripts/remote-docker/README.md`). `harness.ts up|say|cut|heal|latency|down` keeps the same stack up for real Claudes to join by hand (`up --host-seat NAME --joiners A,B`: per joiner a key, an invite and `/tmp/sub-human-remote-manual/NAME.env`).
- **Demo**: `scripts/demo.sh` drives scenes S1–S11 with real sessions in tmux (S11: a third seat from a second home over the pipe link) (real cost; run only when asked). `scripts/checks.ts` then labels each check **deterministic** (log, chain, files, panes: a failure exits 1) or **behavioural** (model-call counts, wakes, noise: compared against `scripts/baselines.json` thresholds, warn only). `scripts/walkthrough.ts` builds `docs/rebuild/walkthrough.html`.
- **Mods**: `npm run test:mods` runs `claude plugin test plugin/sub-human` (the `mod/test/*.test.ts` wiring tests; it skips without a 2.1.292+ binary or with hooks modules off); `npm test` runs it last. `test/mod-core*.node-test.ts` test `mod/core` (and the copied constants against `lib/`) and `mod-hello.ts` in node, and check `validate`'s report: every gating hook has a `.catch`, and `HOOKS` lists what the module registers.
- `npm run validate`: `claude plugin validate plugin/sub-human --strict`.
