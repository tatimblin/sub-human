# Architecture

How sub-human works today, for a new contributor or a fresh Claude session. User-facing behaviour is in [`plugin/sub-human/README.md`](../plugin/sub-human/README.md); the Claude Code internals behind it are in [`docs/internals/cc-2.1.281.md`](internals/cc-2.1.281.md), with the 2.1.292 and 2.1.296 changes in [`docs/internals/cc-2.1.292.md`](internals/cc-2.1.292.md) and [`cc-2.1.296.md`](internals/cc-2.1.296.md). Sections marked *generated* are rewritten by `npm run docs` (`scripts/arch-doc.js`) from the code; edit the code, not the table. `npm test` fails when they are stale.

## Purpose and design rules

Several people, each in their own Claude Code session, share a **room**. The room lives on one machine (its host); people on other machines join it over a link (see [Remote rooms](#remote-rooms)). A person's exact words reach the room only through a hook (`@room …`, or `@claude …`, which also wakes the room's Claude: a post `to=claude`). Claudes talk to each other with native `SendMessage`, addressed `NAME.CODE`. A headless **room Claude** keeps the shared task list and plans only when asked. Consent to a proposal is recorded only from the person's own answer in a native dialog.

The one security goal: **a model can never speak or consent as a person.** The rules that follow from it, and from keeping the plugin unobtrusive (also in `CLAUDE.md`):

- Never pin a model (agents, the room's Claude spawn, the demo, tests).
- No writes to user settings files and no symlinks into `~/.claude`. The plugin keeps its own home and uses the native task list.
- The room's Claude takes no typed input. People reach it with `@claude …` or through their Claude.
- Keep the agent-panel rows (the room row with members nested in it; the room Claude's panel lists every human).
- Consent is native: plan view first, question card as fallback; only `via=human` answers count.
- Unprescriptive: no required workflow; injected text covers mechanics only.
- Every undocumented Claude Code behaviour relied on is listed in `lib/cc/contract.json` and checked by `npm run probe`.
- Zero dependencies, Node 24.3+, macOS/Linux. The runtime is ESM TypeScript with no build step (see [TypeScript](#typescript)); the plugin's node tests (`plugin/sub-human/test/**/*.node-test.ts`) are ESM TypeScript run the same way; repo `scripts/` and their tests are CommonJS JavaScript; the module's wiring tests (`mod/test/*.test.ts`) run under `claude plugin test`.

## Process model

```
 member session (claude, interactive)                    the room's Claude (claude --bg, one per room)
 ┌──────────────────────────────────────────┐            ┌───────────────────────────────────────┐
 │ main thread (the person's Claude)        │ SendMessage│ main thread: agent sub-human:room-claude
 │   spawns ─► room row  (agent room, bg)   │◄──────────►│   spawns ─► participant row per human  │
 │               spawns ─► participant rows │            │   native task list = the room's list   │
 │ hooks: one hooks module (+2 command hooks)│            │ hooks: the same, module included       │
 │ tail child: scripts/sub-human tail (module)  │            │ tail child (formatter + watchdog)      │
 │ MCP: mcp/room-server.ts (+hold, +task)   │            │ MCP: its own room-server.ts            │
 │ subagentStatusLine: <home>/bin/row-status│            └───────────────────────────────────────┘
 └──────────────┬───────────────────────────┘                             │
                │          all read/write through lib/room/store.ts       │
                └────────────────► <home>/rooms/<CODE>/ ◄─────────────────┘
```

Per session, Claude Code starts:

- **Hooks.** The hooks module (`mod/register.ts`) runs in-process in every session: the store guard, the prompt gate, the delivery, and shims that start node only where a handler can act (`mod/core/prefilter.ts`; table below). Every node start of a hook is one entry, `node --import hooks/compile-cache.js hooks/run.ts <handler>`: it reads stdin once, loads only `hooks/handlers/<handler>.ts` and writes that handler's one answer at the edge (`hooks/reply.ts`; the `Reply` type in `hooks/types.ts`: the join's `say`, `refused`, `secret` and `joined`, every other hook's `classic` lines, exit code and stderr). `hooks.json` keeps two command hooks: the `/sub-human` expansion (`join`, behind the node version check) and `SessionEnd` (`session-end`, behind a shell check that starts node only for a session with a lease, a session index or a seat by pid). The module runs the rest with `$.process.run`: `prompt` (at-room and consent's prompt handler in one process), `consent`, `tasks`, `presence`, `row-guard`, `row-map`, `row-hold`, `row-rewake`, `session-restore` and `mod-hello` (the hello, below). Shared pieces: `hooks/seat.ts` resolves the seat (no signer), `hooks/context.ts` builds the mechanics block, `hooks/launcher.ts` writes the row status launcher. Only the handlers that sign arm the seat key's signer (`at-room`, `consent`, `join`: `hooks/seat-key.ts` arm). Identity comes from the payload's `session_id`, then `CLAUDE_PID` (Claude Code sets it for a command hook; `hooks/run.ts` sets it to its parent, the claude process, for one the module runs); the tail child finds its seat by the `CLAUDE_CODE_SESSION_ID` the module gives it; see Identity and liveness.
- **The tail child** (`mod/deliver.ts` starts `scripts/sub-human tail --ndjson` → `lib/tail.ts` with `$.process.spawn`): one per seated session (and per seatless session whose PIN join waits for the host's card: below), for the session's life, restarted with backoff if it exits. It follows the seat's room and writes one JSON event per line, which the module routes: `chat` → `$.ui.log` (a dim notice the person sees; no model turn), `pull` → an isMeta user row the model reads with its next request, `wake` → `$.prompt.submit` (origin `plugin`; folded into a running turn instead when busy), `rows` → held for the person's next prompt. It is the seat's only delivery, which is why a seat needs the module: the join (`lib/commands/index.ts`) refuses without its hello lease. A line is sent at most once (the tail's cursor moves when the line is written). A wake whose submit is dropped by a hook or fails falls back to the isMeta append, and when that fails too it is held and appended at the next `turn.start`, so it arrives once; its room lines (not the `(for Claude)` ones) are then logged as notices, since no prompt row shows them. Every delivery failure (an event not applied, a child that exited or did not start, a wake nothing took) adds to `$.state` `deliveryErrors` and shows one dim notice, at most every 5 min: "a room message could not be delivered; `sub-human read` shows the room".
- **Remote Control.** The bridge carries a session's user and assistant rows and a command hook's `systemMessage` to the phone, never a `$.ui.log` notice, and an isMeta row goes as synthetic (cc CONTRACT `bridge-forwarded-rows`); a function hook's result has no `systemMessage`. So while the person's last typed prompt came through Remote Control (prompt.submit origin `bridge`; `composer` or `sdk` turns it off), what a notice would show is **relayed** as a prompt of its own: room chat lines, and an `@room`'s refusal (at-room writes it as `systemMessage`; "✓ sent" is not relayed). A relay is only the lines the person reads (`alice: hi`, `room: "Rate limiting" agreed (bob)`), submitted `asUser` so Claude Code adds no "plugin sent a message" frame (CONTRACT `plugin-prompt-frame`); what the model needs (`RELAY_CONTEXT`: room lines, not the person's words; a few words of reply at most, or none) is context the phone does not show, and no node runs for it. Relays are batched (`relayQueue`): queued lines go as one prompt once idle (held through a running turn), at most one per `RELAY_GAP_MS` (3 s), on top of the tail's own settle. A relay is still a model turn: the price of the phone seeing the room. Command hooks need nothing: the join's and consent's refusals are `systemMessage`s, which the bridge forwards. The signal is the last typed prompt, so a person who only reads on the phone gets relays after they type there once.
- **The MCP server** (`.mcp.json` → `mcp/room-server.ts`): stdio JSON-RPC, one per session. Its plug-ins `mcp/hold.ts` and `mcp/task.ts` add tools. It resolves the caller from `process.ppid` on every call. It cannot sign `via=human`.
- **Rows**: background subagents that make one blocking MCP call (`hold`) and stream progress, so they cost no tokens while they hold. Their panel text comes from the plugin's `subagentStatusLine` (`settings.json` → `<home>/bin/row-status`, written by `hooks/launcher.ts`, which runs `statusline/`).

Who spawns whom:

| Spawner | Spawns | How |
|---|---|---|
| `hooks/handlers/join.ts` (first member, or a room with no live room Claude) | the room's Claude | claim under the members lock, then detached `node lib/room-claude.ts start` → `claude --bg -n claude.CODE --agent sub-human:room-claude --permission-mode plan --settings {…} /sub-human` |
| a member's main thread | one `sub-human:room` row | the `Agent` call the join/restore context lists under ROWS |
| a room row | one `sub-human:participant` row per other member | on start, and when `hold({room})` returns `JOINED`/`RESPAWN` |
| the room Claude's main thread | one participant row per human | on a pushed `member_joined` that carries the Agent call |
| the hooks module (`mod/deliver.ts`) | the tail child, per seated session | `$.process.spawn node scripts/sub-human tail --ndjson` |
| `hooks/handlers/session-end.ts`, `lib/room-claude.ts` watchdog | the reaper | detached `node lib/room-claude.ts reap CODE` |

The row hooks are the module's (`mod/rows.ts`), and start node only for a row agent (`sub-human:room`, `sub-human:participant`) in a seated session: `row-guard` (classic.PreToolUse Agent) denies a duplicate row spawn; `row-map` (PostToolUse) records which panel row is which agent; `row-hold` (SubagentStop) tells a row that gave up to hold again; `row-rewake` (classic.SessionStart resume, in the background) re-spawns rows after `--resume`: its row calls go to the model as a wake, one line shown to the person.

### Function hooks (generated)

The plugin ships one hooks module (Claude Code 2.1.292+; [mods plan](archive/MODS-PLAN.md)). Its hooks run in-process, above the command hooks of the same event. `hooks/handlers/mod-hello.ts` (run by the module with `$.process.run`, not a hooks.json entry) writes the module's lease `<home>/sessions/mods/<sid>.json` and tells it the home, this session's seat and whether a SessionStart has a seat to put back (`restorable`), which it keeps in `$.state`. The module never writes room state. Its pure logic is in `mod/core/*.ts` (node-tested in `test/mod-core*.node-test.ts`), its wiring tests in `mod/test/*.test.ts` (`npm run test:mods`).

- **The lease** holds the claude pid (the hello's parent) and its start time, the time written, and the session's nonce (below). The join accepts a lease from this claude process, or one written within `MOD_LEASE_FRESH_MS`; `session-end.ts` deletes it, and join's sweep prunes leases whose process is gone. Without one the join is refused with `NO_MODULE`: Claude Code older than 2.1.292, `--bare`, safe mode, hooks modules turned off by policy, or an old session id resumed where the module is off.
- **The hello at session start** runs node only when the session may have a seat: its session index `<home>/sessions/by-sid/<sid>.json` exists (`$.fs.exists`; `mod/core/seat.ts` sidIndex, the path `lib/identity.ts` writes), or this process knew a seat before (a `/clear`). Otherwise the hello is the module's own (`localHello`: the home from `SUB_HUMAN_HOME` or `HOME` by `lib/home.ts`'s rule, its real path, no seat), so a session that never joins starts no node at all; its lease is written before its first `/sub-human` (`command.run`, or `classic.UserPromptExpansion` beneath when the module does not answer), since the join refuses a session without one.
- **The hello refresh** runs after the join and after a SessionStart restore. One that fails keeps the last hello (the guard still knows the home) but with `sid` null, as no session's, so every prefilter runs node until a refresh succeeds: a join whose hello failed must not make "no seat" look certain.
- **classic.PreToolUse carries the call alone** (`tool`, `tool_use_id`, the arguments), while `row-guard` and `consent` read `session_id`, `transcript_path`, `permission_mode` and `agent_id`. The module keeps the transcript path and mode of the last main-loop classic event it saw (UserPromptSubmit, PostToolUse, Stop, SessionStart, …) and the `agentId` a `tool.call` carried while that call runs (`mod/core/facts.ts`), and builds the payload from them. A mode changed with shift+tab in the middle of a turn is seen at the next event. Both classic.PreToolUse hooks call `next(e)` on every path and put their answer above what the hooks beneath said (`mergePre`: a deny wins, then an ask, then an allow; cc CONTRACT `classic-chain-order`); an allow's reason, which a command hook's allow showed the person, is a notice.
- **The tail child's life.** It starts on `session.start` (also after a reload or a lost worker), after the join and after `classic.SessionStart`, unless the hello is sure the session has no seat (and no PIN join of its own waiting: `pending`). A `/clear` runs on under a new session id: the old child is stopped and one is started for the new id; `session.end` stops the child for good. A child that exits is started again after 1 s, doubling to 60 s; one that ran over 60 s before it exited was healthy, and the backoff starts over. It dies with the module (a reload, the session's end): the `$.process.spawn` loop is its life.
- **Mid-turn wakes.** A wake while a main-loop turn runs (a `turn.start` with no `turn.complete` yet) is appended as an isMeta row, and its visible lines are logged. At that turn's `turn.complete` it is submitted after all when no main-loop tool call (`classic.PostToolUse` / `PostToolUseFailure` without `agent_id`) finished after the append: each finished call is followed by a model request, so without one the request then in flight was the turn's last and never carried the row. A wake neither a submit nor an append took is held for the next `turn.start` (at most `PENDING_MAX` 20, newest kept), when the session is evidently running turns again.
- **Presence** has one writer: the module runs `presence` (not awaited) for a typed prompt ("working", unless it already wrote that for this seat), `Notification` (idle, permission) and `StopFailure` (error). No other hook writes it: a seat just taken or put back has none until its person types.
- **`@room` fails closed.** When the prompt shim fails (it throws, times out or exits other than 0 or 2), an `@room` (or, in a seated session, an `@claude`) is blocked with the prompt suppressed, never handed to the model as typed text.
- **The session title** `NAME.CODE` is set once per session id and address, so a switch to another room retitles the session.
- **Shared constants and parsers live in `mod/core`.** What both the module and node read has one copy, in `mod/core` (pure, no imports): the `@room`/`@claude` parsers, `TYPED_ORIGINS` and the refusal wordings (`mod/core/prompt.ts`), the nonce check `attested` (`state.ts`), the hidden-reply rule `mayHoldSecret` (`command.ts`), the name, code and session-id patterns (`seat.ts`), the row agent types (`rows.ts`), and the restart, notice and chat-line constants (`constants.ts`). `lib/` and the hook handlers import them from there (`lib/config.ts`, `lib/text.ts` and `lib/rows.ts` re-export theirs); nothing is copied, so no test pins copies.

## The room store

Everything persistent goes through the **RoomStore** interface in `lib/room/store.ts` (the header there is the full contract). `lib/room.ts` wraps it: `room.open(code) → Room` (cached per code, no process-wide state) adds delivery, rendering and the consent queries on top, each judged by the store's own trust.

The store is six files behind `store.ts`, each with one job:

| File | Job | I/O |
|---|---|---|
| `lib/room/trust.ts` | whether a `via=human` entry is the person's: `verdict(e, ctx)` over the keys a store passes in (`pins()`, the seat's local `.pub` for a legacy room); `trustOver(ctx)` is a store's `trust` | none |
| `lib/room/rules.ts` | what a placement checks and stamps: `toPayload`, `admit`, `scanTail`, the rates, `checkSigned`, `checkPin`, `checkHere`, `placeAfter`; `normalize` | none |
| `lib/room/log-io.ts` | the log's bytes, in segments with a snapshot: the cached `readAll`, `readView` and its in-memory checkpoint over the active segment, `verifyChain`, the tailer across segments, the locked append and the rotation | the log; imported by `fs-store.ts` alone |
| `lib/room/snapshot.ts` | what a snapshot holds of the sealed lines (`extend`), and whether one from another machine can be taken (`problem`) | none |
| `lib/room/fs-store.ts` | `FsRoomStore`: a room directory on this machine; `pins()` and `hostState()` carried forward one new line at a time | the room's files (the only module that names them) |

## Entries and `via`

An entry is `{id, at, from, via, kind, text?, prev, …kind fields}`. `id` is monotonic, `prev` is `hash12` of the previous line, `from` comes from a trusted caller that resolved identity (never from env or the model). `lib/room/validate.ts` decides which `via` may write which kind:

| via | Kinds | Written by |
|---|---|---|
| `human` | `say`, `signoff`, `objection`, `proposal` | hooks only: `@room` and `@claude` (at-room.ts), the plan view / card answers (consent.ts) |
| `agent` | `say`, `question`, `status`, `proposal`, `task_req` | the MCP server (`post`, `propose`, `task`) on behalf of a member's Claude |
| `system` | `decision`, `member_joined`, `member_left`, `task`, `status`, `host_changed` | hooks, the reaper and the handoff (`lib/handoff.ts`), with `{system: true}` |

**Signing.** Every hook process runs `seat-key.arm()`, which installs a signer. `append` is `place(toPayload(…))`: `toPayload` validates and, for `via=human`, signs (sig v2, `lib/room/envelope.ts`: Ed25519 over the payload with sorted keys plus `room`, `from`, `nonce`, `ts`, without `id`/`at`/`prev`, so a payload signed on one machine can be placed on another). `place` validates again, refuses a replayed nonce or a `ts` outside `SIG_SKEW_MS`, verifies the signature, then stamps `id`, `at`, `prev` under the log lock. The MCP server, CLI, tail and module never load `seat-key.ts` (`test/hooks/security.node-test.ts`), so they cannot write `via=human`; the store refuses. Keys are pinned in the log: the join hook puts the seat's public key in `member_joined`, the first key seen per name is that name's key for the room's life, and a join with another key is refused (`AUTH`). Readers ask the store that read the entry, `store.trust(e)` (`lib/room/trust.ts`, explicit: the store's keys go in, nothing rides on the entry): `verified` (v2, or v1 from before the pin, against the pinned key, signed for this room; the local `.pub` only in a room that pins none), `legacy` (unsigned, in a room that pins no key, from a seat with no local key), or `unverified` (shown as `bob (unverified): …`, never counted for consent or tasks). `Room` passes its store's trust to every fold, render and delivery; a caller with an entry and no store uses `trustOf(e)` (the store of the room the entry names; an entry naming none is never verified). MCP `read` gives the model the rendered line (`render.line({full})`), so the marker is in what it reads.

**Hash chain, segments and the snapshot.** The log is cut into segments (`lib/room/log-io.ts`). Once an append leaves `log.jsonl` at `SEGMENT_MAX_BYTES` (1 MiB, about 5,000 lines), and only if every line of it chains, it is sealed: linked as the next `log-NNNN.jsonl`, `snapshot.json` written, and `log.jsonl` replaced by the sealed last line alone. Each segment's first line repeats the previous one's last, so the chain runs on across files unchanged (each line's `prev` is still the hash12 of the line before it in the log), an appender that knows only `log.jsonl` (an older plugin still running after an update) still finds the right `id` and `prev`, and every reader skips the repeat. A segment that does not chain is never sealed: a break is never laundered into a snapshot, and stays visible. A crash between the steps is finished by the next append; a lost `snapshot.json` is rebuilt from the sealed segments. **A rotation waits for older readers:** a reader of 0.5.0-beta.15 or before sees a rotated log as two lines and a broken chain, so a due rotation runs only when no seat of this machine that may still run lacks `log_v` (`lib/room/members.ts` holdsRotation: a person's seat that is alive and has not left; the room's Claude while its job may run). Each seat records `log_v` (2: segments) at its join (`identity.join`; a link's seat sends it in its `join` op, additively) and the room's Claude at its spawn. While one holds it, the log grows in one segment and the host's room hears it once (`log/rotation-held`, cleared by the next rotation).

The snapshot carries what a reader needs of the sealed lines: every non-chat entry (what decides delivery: proposals, answers, decisions, joins, tasks, host changes; the consent fold's whole input), the pinned keys and host they give, and the window of entries the next placement looks back over (the rate buckets of the last minute, and the nonces of the last `2 × SIG_SKEW_MS`, so a payload replayed after a rotation is refused as before). `readView({after})` is that snapshot plus the active segment, read through a checkpoint each process keeps in memory, so a cold reader parses one segment: the pinned keys for a person's append, the status line's rows (`room.readRecent`: every non-chat entry and the lines since the last rotation). `readAll` still gives every line, from the sealed segments. `verifyChain` checks the active segment incrementally from its own in-memory checkpoint (trusted only while the line before its offset still hashes to the stored hash; else from the segment's start); the snapshot vouches for the sealed segments, and `validateChain` re-checks every line, carry lines included. The tail runs `verifyChain` on its health tick and sends one `room log check: …` line per break (a `health` event). The chain makes edits around the store visible; it does not prevent them.

**What a home stops keeping.** `lib/gc.ts` runs at a join (`seats.take`), at most every 6 hours and within 250 ms, never on the room being joined: a room closed for good (every person's seat left: a seat whose session crashed has not; its room Claude stopped or never started), with no link record (neither this machine's link to it nor the host's `remote/links` records of machines linked to it) and nothing changed for 30 days (`ROOM_GC_MS`, `SUB_HUMAN_ROOM_GC_MS`) is set aside, not deleted: renamed to `rooms/CODE.gc-TIME` with its seat keys at `keys/CODE.gc-TIME`; those folders, and the ones `link --forget` set aside, are deleted 30 days later; session indexes of ended sessions go after 30 days, and a room's row maps of ended sessions after 7 (swept for the room joined). An open room's segments and snapshot are never touched: a room goes only whole. `openRooms()` and `orphanRooms()` judge the rooms in `<home>/open-rooms.json` (written at open and at every join; a room closed for good, every seat left and its room Claude stopped, leaves it), not every room ever made.

**Who typed an `@room` or `@claude`.** (Outside a room `@claude` is a plain prompt and passes untouched.) The module's `prompt.submit` gate reads the origin Claude Code stamps on the prompt (`composer`, `sdk` or `bridge` count as typed; cc CONTRACT `prompt-origin-composer`) and drops any other `@room` before a hook runs; the shim hands that origin to at-room as `sub_human_origin`, and at-room posts only with a typed one that comes with this session's nonce (Security model). An origin that is lost on the way (a reload between the two hooks) is refused, and the person types it again.

**How an `@room` post looks.** The TUI trims trailing whitespace before the hook sees the prompt (accepted). On success at-room answers `continue:false` with a stop reason, which keeps the person's `❯ @room …` row and adds one warning line, "Operation stopped by hook: ✓ sent to room CODE (Claude wasn't asked)" (for `@claude`, "✓ sent; the room's Claude will answer"), and an isMeta copy of it; the model sees the row and the copy natively on its next turn. The module's `session.append` hook keeps that warning line as the receipt alone (only for a stop its shim just returned, matched whole; cc CONTRACT `ups-stop-frame`, `session-append-notice-rewrite`), so the person sees `⏺ ✓ sent to room CODE (Claude wasn't asked)`, after `--resume` too. The receipt says who reads the post, so where the frame stays (2.1.300 was reported not to rewrite) it still reads as delivered, not as an error. Refusals are `decision:block` with `suppressOriginalPrompt`, which works only inside `hookSpecificOutput`, so refused or forged text never reaches the model. Typed through Remote Control (origin `bridge`), a refusal is also the `systemMessage`, relayed to the phone (Process model, Remote Control); "✓ sent" is not (the phone shows the person's own row, and a relay costs a turn). When the posted text appears verbatim in the last assistant message (an accepted prompt suggestion, a copied draft), the entry carries `drafted:"agent"`; it is still posted.

## Delivery and settle batching

`deliver(me, e, {entries, trust, note})` (`lib/room/deliver.ts`) says what one entry is for one seat, one of four classes:

- **wake**: needs Claude now: one plugin prompt, one model turn. Anything `to` me or mentioning `@me` (for the room's Claude only `to=claude`, a person's leading `@claude` tag: an `@claude` inside the text is just words), a proposal naming me that I have not answered, a decision on a proposal I am in, a task assigned to me that someone else asked for, an objection to my proposal; for the room's Claude a task request and a join whose row note says no row runs.
- **notice**: for the person, no wake (the tail's `chat` event): another person's own words not addressed to me, another member's join or leave, a host move. The model gets a copy as context.
- **context**: for Claude, no wake: the tail sends it as "Room since your last turn", which the model reads with its next request.
- **none**: my own posts, and what concerns neither me nor the room's state.

Its first step, `lane()` (push: notice or wake; pull: context; none), is kept for its table tests. The tail batches what is not `none` in a `Batcher` (`lib/tail.ts`): flush after `SETTLE_MS` 1500 of quiet or `SETTLE_MAX_MS` 5000 after the first (room Claude: 3000 / 10000), so a burst costs at most one turn. Each entry is judged again at flush time against `readView`, so an entry answered or decided in the meantime is dropped. A `member_left` is held `LEAVE_SETTLE_MS` 8000 so a quick leave and rejoin shows nothing; the room row's hold progress line settles leaves the same way ("bob left" only after 8 s). A member's batch is group-chat lines without ids, plus `(for Claude)` lines in a wake; the room Claude's batch starts with `stateLine()` and keeps ids. All timings live in `lib/config.ts` with `SUB_HUMAN_*_MS` overrides. The room's Claude gets the overrides of the session that started it through its `--settings` env (the bg daemon filters the caller's env), so a room started with a short `SUB_HUMAN_ROOM_CLAUDE_ORPHAN_MS` has a watchdog that honours it.

The plan-view review runs only in the modes `default`, `acceptEdits` and `auto` (not plan already, not `bypassPermissions` or `dontAsk`) and only while clear-context-on-accept is off; otherwise the card is used. A plan edited in the dialog (Ctrl+G) records nothing: a signoff needs the proposal text unedited. **One reducer.** What the consent hook does is decided by `lib/consent/review.ts` `reduce(state, event, ctx) → {state, effects, say}`, a pure function table-tested phase by phase (`test/consent-review.node-test.ts`). Its state is the seat's two documents above, `review` (phase `entering | shown | exiting | restore`, the plan-file backup, `unread` while the dialog's answer is not on disk) and `note` (its `stage`); its events are the hook events with their facts (`enter`, `entered`, `exit`, `permission`, `exited`, `stop`, `roomTool`, `prompt`, `ask`, `answered`, and `planFailed` when a write fails). `hooks/handlers/consent.ts` only gathers the facts under the review lock (the transcript, the plan file, the room's pending and answerable proposals, a join request or handoff ask waiting), runs the effects in order (`save` a snapshot before `writePlan`, so the backup is on disk before the overwrite; `restorePlan`; `pick`; `answer`, which is `proposal.answer` then `decide`) and writes the answer. Every line the model is told is in the reducer's two tables: `NEXT`, the one mechanic per phase (open, show, exit, restore, card, note), and `SAY`, short outcome lines; the tail's reminder and the room server use the same lines. The cards the hooks build (the fallback consent card, the note's confirm card, the handoff card, a join request's card) are read by one function, `lib/consent/card.ts` `answerCard(spec, response, input)`: `absent` (another call), `none` (AFK, a followUp, no answer, or a card shown other than as built), `other` (a label it does not offer) or `answer`. The plan file the hooks write is `cc.planFile`: the transcript's `plan_mode` attachment (Claude Code's record), or the path Claude Code injects into `ExitPlanMode`'s input when it is that same path or lies under the plans dir; a path the model put in any other call is never read. PLAN-COLLAB's versions, threads, withdraw and changes requested land on this reducer as events and fields (`shownHash` is where the composed text's hash replaces the proposal's).

`lib/room/consent.ts` `fold(entries)` is the one interpretation of the log, used by `stateLine`, `lane`, the rows and the gate, so they cannot disagree: the latest proposal entry per hash wins; per person the latest trusted `via=human` answer wins (an objection voids an earlier signoff); a decision closes the hash with state `agreed` or `blocked`. `test/hooks/consent-table.node-test.ts` feeds one table to all views.

One person in two seats is one approver. A seat's `account` (in the members document) is the person behind it as the host knows it: the host's machine id for a seat on the host and for one over a login link (`/sub-human join USER@HOST ROOM`: the host account's own ssh login, `lib/remote/server.ts` join); an invite's seat has none, so two invite seats from one machine stay two people. `proposal.create` writes `same`, the approvers that share an account in groups of 2+ (`lib/proposal.ts` sameOf). Several people can share one machine, so of the host's own seats (machine = account) only the room owner's counts as that person: the seat of whoever opened the room, marked `owner` in the members document when the first person's seat on the host joins (`lib/room/members.ts` join, kept across that seat's rejoins; a room from before the field falls back to the earliest-joined host seat present). Login seats group with the owner's seat; every other seat on the host is its own person, and two plain seats on the host never merge. In the fold the newest answer from any seat of a group counts for every seat of it, and a revoke from one clears it; `matrix` lists one name per person (`agreed`, `objected`, `missing`, with `also` naming the other seats), `people` counts them for the rows, and the decision reads "agreed: tristan (also laptop), bob". When one seat answers, the other seat's review or card no longer opens (`pending`), but an answer it gives on one already open still records and, being newer, counts (`answerable`; one answer per seat). A host before this version refuses an unknown field, so `same` is gated on the host's caps: protocol `FIELDS` (`['same']`) rides the hello's caps, the link daemon writes the host's list into the mirror's document `link` (`fields`), and a mirror writes `same` only while it is there. A peer that ignores `same` counts every seat: stricter, never wrong.

## Tasks

```
member's Claude ─ task({op, …}) ─► task_req (via=agent, by=member)   a wake for the room's Claude only
room Claude ─ TaskCreate/TaskUpdate (metadata {req, by}) ─► native list sh-CODE under <claude config>/tasks/
hooks/handlers/tasks.ts PostToolUse ─► task entry (via=system, full snapshot) ─► tasks.json = tasks.fold(task entries)
hooks/handlers/tasks.ts TaskCompleted ─► tasks.gate(): exit 2 unless the owner asked done with evidence
```

- **Reconcile.** A mirror run can be lost (a module hook that failed, a reload). So on every room Claude run `hooks/handlers/tasks.ts` also compares the native list with the log and appends an `add` snapshot for each native task the log has no `task` entry for; the next run repairs a lost one.
- The room Claude's **native task list is the ledger**: `CLAUDE_CODE_TASK_LIST_ID=sh-CODE`, passed through `--settings` env because the bg daemon filters the caller's env (`cc.DAEMON_ENV_ALLOW`). The plugin never writes under `~/.claude`.
- **`metadata.req`** links a native task to the `task_req` it applies. The TaskCompleted input carries no metadata, so the gate reads the task file (which still shows the old status).
- **`tasks.json` is a pure fold** of the log's `task` entries: delete it, refold, same file. Rows and `sub-human tasks` read only it.
- **The gate**: only the owner's own `done` request with evidence after the last claim (or a trusted human entry from the owner citing it) passes. A blocked TaskUpdate drops every field in that call, so the room's Claude is told to change status in a call of its own. Task 1, "room CODE open", stays open until the room is closing, which keeps the native list from being wiped.

## Identity and liveness

- **Commands.** Every `/sub-human …` runs `hooks/handlers/join.ts` (UserPromptExpansion) before the model, a thin edge: it reads who asked (session id, cwd, claude process, seat) and renders one `Answer` of the command table `lib/commands/index.ts` (`{verb: (args, ctx) => Answer}`: the bare command, `join`, `invite`, `admit`, `kick`, `leave`, `handoff`; `help` and `doctor` run without the module's lease; any other first word is a NAME or a ROOM) as the hook's one `Reply`. The router decides the hidden rule before any verb parses (below). The seat itself is `lib/seats.ts` take; the link steps of a join are `lib/remote/joining.ts`.
- **Binding.** `/sub-human NAME [CODE]`, `/sub-human CODE` and `/sub-human join CODE` (a room on this machine, as the default name or `--as NAME`) take a seat before the model runs. A join that worked shows no `systemMessage` (Claude Code draws one as a warning; the title and the room row say it), unless the room's Claude did not start or the session is in bypass-permissions mode; a refusal is the block reason and the `systemMessage` (which Remote Control shows). It writes the seat into `members.json` and the indexes `<home>/sessions/by-pid/<CLAUDE_PID>.json` and `by-sid/<session_id>.json`. The model never names itself. Without a CODE it joins the one open room (a live member seat, not closing), or opens a new one; several open rooms is an error that lists their codes. Rooms where only the room's Claude is left are swept first. A member already in another room switches: the old room logs `member_left` "switched rooms".
- **Resolution.** Hooks: payload `session_id`, then `CLAUDE_PID`. MCP server: `process.ppid` (MCP servers get no `CLAUDE_PID`). CLI and tail child: `CLAUDE_CODE_SESSION_ID` (the module sets it for the child), then `CLAUDE_PID`, then the nearest registered ancestor. `/clear` changes the session id but not the process: `session-restore.ts` rebinds the new id to the seat found by pid. `--resume` is a new process with the old id: it rebinds the pid or rejoins the seat.
- **Liveness.** `seatAlive(m)` (`lib/room/members.ts`): not left, and, for a seat of this machine (`m.machine === machineId()`), the pid is alive with a start time equal to the stored `pid_start` (so a reused pid never keeps or adopts a seat). Any other seat (another machine's, or no pid) is alive while its `seen_at` lease is fresh (`SEAT_LEASE_MS` 120 s); the tail's health tick and the hold server renew it with `members.beat` at most every `SEAT_BEAT_MS` 30 s, and a presence write rides on the same op.
- **Entering and leaving.** `lib/seats.ts` `enter` (members.join, the session indexes, `member_joined` with `pubkey` and `machine`, the room's Claude) and `exit` (members.leave, the reaper when nobody is left, `member_left`) are the one sequence the join and session-end hooks run. A name is one seat across machines: a live seat of another holder makes it "name taken". `host` and `join` are reserved names.
- **Host gates.** Room Claude spawn, reap and watchdog (`lib/room-claude.ts`) and proposal decisions run only where the room's store `isHost`; on any other machine they do nothing. A handoff (Remote rooms, Moving the host) flips `isHost` on both machines: `store.open` decides a room's kind again when its link file appears or goes, and the tail starts its session again over the new store.
- **Address.** `NAME.CODE` is set as the session title (the module's `classic.UserPromptSubmit`, once per session id and address), which is what `SendMessage` and `ListAgents` use (cc CONTRACT `session-title-address`).

## The room's Claude: lifecycle

```
join (no live room Claude) ─► claimSpawn: members.claude = {job:"pending", claim}  (under the members lock; a concurrent join sees it)
                    ─► startDetached ─► spawn(): claude stop <prevJob>; claude --bg …; find job in `claude agents --json`
                                         record {job} only if the claim is still current and the room is not closing
room Claude session ─► /sub-human ─► join.ts binds the "claude" seat (agent_type sub-human:room-claude + SUB_HUMAN_ROOM)
             ─► TaskCreate "room CODE open"
last member SessionEnd ─► reap (detached): grace 10 s (a rejoin cancels) ─► set closing ─► status to=claude
                          "room closed: complete task 1" ─► wait ≤ 20 s ─► claude stop <job> ─► room Claude seat left
crashed members (no SessionEnd) ─► room Claude tail child's health tick: watchdog() sees no live member for 60 s ─► closing + reap
```

Debugging the room's Claude by hand: `node lib/room-claude.ts cmd CODE` prints the exact spawn command; or run `claude --agent sub-human:room-claude --permission-mode plan` and type `/sub-human CODE` (an existing room) or `/sub-human` (a new room).

`needsSpawn` also respawns a room Claude whose pid is dead, whose claim is older than `ROOM_CLAUDE_CLAIM_MS`, or which never bound within `ROOM_CLAUDE_BIND_MS`. `openRooms()` ignores rooms where only the room's Claude is left, and join sweeps those through the watchdog.

## Remote rooms

A room can have members on other machines. The machine that created it is the **host**: its room directory is the room, and its hooks, tail and MCP server keep using that directory as before. Another machine joins with an invite and keeps a **mirror**: a room directory with the FsRoomStore layout, holding the host's log line for line, kept by a **link daemon**. Every reader (`readView`, the snapshot, the tailer, `verifyChain`, rows, digests) works on the mirror unchanged; only writes cross the wire, as named ops. Two transports people use: SSH (`ssh:user@host[:port]`: an invite's PIN join, or the person's own ssh login, below) and the listener (`wss://host/…/sub-human/CODE`: a Noise channel in a WebSocket to the host's listener through Tailscale Serve/Funnel, any HTTPS front or a `CONNECT` proxy, below). A pipe to a second home on the same machine (`pipe:<home>`) and an in-process memory pair are for the tests and the demo (S11) only; SSH is the pipe with `ssh` in front, and none of them needed a protocol change. The plan, with its as-built notes and decisions: [`docs/archive/REMOTE-PLAN.md`](archive/REMOTE-PLAN.md).

```
 HOST machine                                            REMOTE machine
 hooks / tail / MCP ──► FsRoomStore ◄── serve --stdio ◄══ transport ══► link daemon ──► MirrorRoomStore (FsRoomStore layout)
   (sign + place,        <home>/rooms/CODE   per connection    (ssh, or a   (one per room   ▲ reads: hooks, tail, MCP, rows
    decide, claude)                           (scripts/sub-human)   pipe)        and home)       │ writes: bridge (worker thread,
                                                                                             │          Atomics.wait, deadline)
                                                                                    hooks ───┘ sign with the local seat key
```

**Joining.** On the host, a person in the room runs `/sub-human invite [--ssh [user@host]] [--via JUMP]` (`lib/remote/hosting.ts` hostInvite; over ssh by default, to `SUB_HUMAN_SSH_ADDR` or `user@hostname`; a bare ssh alias is shown as given and recorded as `ssh -G` reads it): `invites.mintInvite` (`lib/remote/invites.ts`) records an **invite line** (protocol 3): 16 random bytes the line carries and a 4-digit PIN the person tells apart; the host keeps only `sha256(secret)` (the record's key) and `sha256(secret:PIN)`, at most `SHORT_LIVE_MAX` 4 open, 5 tries, `INVITE_TTL_MS` 15 minutes. The join hook shows `/sub-human join DEST ROOM SECRET [--via J] [--home H]` and the PIN apart as a block reason with `suppressOriginalPrompt`, to the person and never to the model. SECRET (`lib/remote/invite-secret.ts`) is 39 characters of lower-case Crockford base32: the 128-bit secret and a 64-bit tag, `HMAC-SHA256(secret, "sub-human host key v3" 0 role 0 key)`, of the host key the line is for: the home's Ed25519 machine key over ssh and a pipe (role `machine`), the listener's X25519 key over the web (role `listener`). `--home` goes in when the host's folder is not `~/.sub-human`. The line carries no name: the joiner's is their git `user.name` (`identity.defaultName`), or `--as NAME`. On the other machine every `join`, `invite` and `admit` prompt, and any prompt with a word of digits or a SECRET-shaped word (`mod/core/command.ts` SECRET_WORD: 32 to 48 letters and digits), is answered hidden (the command router turns each say and refusal into a secret, decided from the prompt before any verb parses it), and a SECRET-shaped word is never echoed or taken for a name. **Two steps, neither takes the seat.** The line (`joining.linkLine`) writes the link file (`lib/room/links.ts`: the transport, over ssh the person's own login (`ssh.loginSpec`), over the web with a fresh key of the link's own (`link-connect.ts` linkKey); `invite` the SECRET word; `join_as`, `join_sid`), starts the daemon and watches it (`hosting.outcome`, up to `LINK_JOIN_WAIT_MS`). The daemon (`link-connect.ts` connectLink) checks the host first: over the web it reads the listener's key (a text `{"op": "key"}`) and checks the tag before the Noise handshake, then pins it; over ssh and a pipe its first hello carries a nonce and the host answers with its machine key's signature over it (`machine-key.ts` hostProof), checked against the tag (`client.ts` checkHost). A host the tag does not name gets nothing (`AUTH HOST_KEY_MISMATCH`, the line dropped). The second hello carries the SECRET and `as {name, label}`: the host answers `PIN_NEEDED` (nothing charged), which the link file keeps as `pin_wanted` and the join shows ("Type the 4-digit PIN they told you: /sub-human join PIN"). `/sub-human join PIN` (`joining.givePin`) puts the PIN in the link file and starts the daemon again: the host throttles (after the n-th wrong PIN no PIN for `PIN_BACKOFF_MS` · 2^(n-1) per invite, one step longer for the machine that typed it: `PIN_THROTTLED`, charged nothing), checks it (`PIN_WRONG` with the tries left; the fifth `PIN_LAST` burns the invite; each a room line), and on the right one marks the invite used and records an admission (`invites.admissionSlot`) bound to the machine its key proves, the name, the label and, over the web, the Noise key the connection proved, answering `OFFLINE ADMIT_WAITING`; the link file drops the PIN and keeps `awaiting {ref, check: "check 3f9c-2a71"}`, which the card shows too: the check is `invite-secret.ts` joinCheck of the machine id the joiner's key proved and, over the web, its link's XK key, never of the line, so a thief holding the line and the PIN shows another check on the card than the real joiner's screen. A second machine that presents a used invite gets `INVITE_USED`, and the room a line naming both checks (once per machine). The daemon redials with the SECRET alone until the host person's card (`lib/remote/admission.ts`: Let in / Refuse, or `/sub-human admit [REF]`, `sub-human admit` in a shell) lets that machine in; then the host makes the link, bound to that one name (and over the web to that key), and returns its token; the SECRET leaves the link file. A bare `/sub-human` finds the link file's `join_as` and takes that seat. **The notices:** `mod-hello` reports `pending` for the session that typed the line (`join_sid`), so the hooks module starts the tail child although it has no seat, and the tail (`lib/tail.ts`, `joining.pendingNews`) writes one chat line per answer: the host asks for the PIN (again, after a wrong one), "the host let you in to room CODE: type /sub-human to join it as NAME", or why the join stopped. A line whose last word is 4 digits came from a host before protocol 3: the join says the host must update. An invite to the default address (no `SUB_HUMAN_SSH_ADDR`, no `--ssh`) says the name is this machine's own (a `.local` name reaches the same network only) and, when this machine takes no ssh logins (`hosting.remoteLogin`: macOS `launchctl print-disabled system`, Linux an sshd process or ssh unit; no network probe), that the joiner's ssh will fail and `--web` is the other way; every ssh invite says it needs the joiner's own ssh login to this account. From then on `store.open(CODE)` there returns the mirror. **Over an ssh login** (no invite): `/sub-human join HOST ROOM [--via J] [--home P] [--as NAME]` (no SECRET) is said to be the login path, not an invite (a pipe destination has no login path: there it is an invite line without its SECRET), and writes a link file whose transport is `lib/remote/transports/ssh.ts` loginSpec (`login: true`, a link id this machine picks, the host's home when not `~/.sub-human`; a bare ssh alias takes its user from `ssh -G`); the daemon runs the person's own `ssh -o BatchMode=yes … '"$HOME"/.sub-human/bin/serve --stdio CODE --link ID --login'` (their keys, config and known_hosts) and says hello `{login: true}` (only when the link file holds no invite: an invite line over a login transport sends its invite, so it still goes through its PIN and the card); that `serve --login` session (refused under `SSH_ORIGINAL_COMMAND`, i.e. any forced command) makes link ID (`hostLinks.loginLink`, `lib/remote/host-links.ts`), with the room line `a machine linked over your SSH login`. Its seats are their own person for consent unless the host person turned on the room option `login-same-person` (below). The join watches the first hello and takes the seat in the same step (nothing secret is in that prompt); ssh failures only the person can fix (an unknown host key: the exact `ssh USER@HOST` to run once; a refused login; no shim or no room on the host) stop the daemon with `AUTH` and that reason (`ssh.loginProblem`: `SSH_HOST_KEY`, `SSH_DENIED`, `SSH_NO_SHIM`, `SSH_OLD_HOST`, `SSH_NO_ROOM`; one classifier of ssh's stderr, `ssh.classify`, serves the daemon, the login join and doctor). A host refreshes its serve shim passively on every join there. A seat's connection ends with `/sub-human kick NAME` or `sub-human kick NAME` (`hosting.kick`): the token (and its key) and any invite reserved for it burn, an `authorized_keys` line an older version wrote for it goes, its seats leave, its `serve` processes stop (each first ends its streams `{reason: 'AUTH'}`, so the joiner's daemon stops with "the host revoked this link" instead of redialing), and a room line says so. An unused invite is cancelled with `/sub-human invite --cancel [REF]` (`hosting.cancelInvite`). `/sub-human leave` leaves the room (`seats.exit`) and keeps the session; its tail goes quiet with the seat.

**Host and mirror.** `store.isHost` decides who does what. Only the host spawns, reaps and watches the room's Claude, decides proposals, pins keys, mints invites and writes `members.update` and the streamed documents; on a mirror these throw `HOST_ONLY` or are gated off (`lib/room-claude.ts`, `proposal.decide`). The host streams its log lines verbatim and three documents: `members` (`members.publicView`: no `pid`, `pid_start`, `session_id`, `cwd`), `presence/*` and `tasks`. Session-local state (`rows/*`, `members/NAME/review|title`, cursors, notices, the session indexes, keys) never leaves its machine. On a mirror a seat of this machine is judged by its session index (pid, start time, session); a seat of another machine lives by its lease (`seen_at`, `SEAT_LEASE_MS` 120 s, renewed by `beat`). A remote seat's join and leave reach the host's `lib/seats.ts` through its server, which logs `member_joined`/`member_left` and runs the room's Claude and the reaper there.

**Writes.** A hook's write (`@room`, an answer, join, leave, a beat) is signed on its own thread, then crosses `lib/remote/bridge.ts`: the hook's thread posts one op to a worker and blocks in `Atomics.wait` until the reply or the deadline (`LINK_CALL_MS` 3 s, SessionEnd `LINK_CALL_END_MS` 1 s). The worker relays the op over the daemon's unix socket (`lib/remote/link-socket.ts` handle; it loads no store and never the signer). With the link down the call is `OFFLINE` and nothing was sent: a card answer (consent), a proposal, a join or an agent's post is refused at once and the person is told, never queued. The one exception is the person's own `@room` post (see the outbox below). A slow link is not a down one: the frame went out and may land late, so a deadline is never "nothing was sent". The daemon answers every relayed op by `LINK_RELAY_MS` (2 s, inside the hook's 3 s): a person's `@room` post the host has not answered by then goes into the outbox under its nonce, answered `{queued, slow: true}` ("⧗ sending (slow link)"), and the host's late answer takes it out (the late copy is the post; a refusal is dropped and reported); any other op is `OFFLINE` with reason `UNKNOWN_OUTCOME`, as is the bridge's own deadline, and the store marks it `unknown` (by the reason, never the message's words): the at-room hook says "⧗ not confirmed", the consent hook that the answer may still be recorded and answering again is safe (one answer per person per proposal; the same signed payload sent again is refused by its nonce). After a write the server ticks the session's streams before it replies, so the mirror holds the write's lines when the hook's call returns (read-your-writes). The worker starts at a process's first write: a hook that only reads starts none.

**The link daemon** (`scripts/sub-human link CODE`), one per room and home, in four files: `lib/remote/link-engine.ts`, the connection logic as a pure state machine (below); `link.ts`, the daemon that runs its effects (dial, subscribe, renew seats, send the outbox, ping, timers on the injected clock, the mirror's writes); `link-socket.ts`, the hooks' socket at both ends and the daemon's control (`status`, `start`, `stopReason`); `link-connect.ts`, the link file's hello and what a refused dial means. The daemon it holds the one connection (`hello` with the token), `subscribe`s from the mirror's last line with `{after, hash}` (an empty mirror also asks `snapshot: true` of a host whose hello caps say `snapshot`: the host's snapshot arrives first, `applySnapshot` checks it, and only the lines after it follow), applies each line (`applyLine` refuses one that does not chain: `FORK`, so a snapshot whose head the next line does not chain to is `FORK` too) and document, prefetches every proposal's plan, and serves the hooks on `<mirror dir>/.link/link.sock`, or `/tmp/sub-human-<uid>/<hash12(mirror dir)>/link.sock` when that path is too long for a socket (each directory 0700, a real directory, this user's). The path depends on the home and the room only, never on `TMPDIR` (a daemon started by the listener, sshd or a handoff need not share the session's), and the daemon records it in its `link.json` (`socket`), which the hooks try first, then the computed path. Its state is the mirror's `link.json`: connecting, online, offline, fork, stopped (AUTH or PROTOCOL at hello, the room closed, idle, a signal). `FORK` is never repaired silently: the daemon stops, the tail sends one `room link: FORK …` line (a `health` event: the module logs it as a notice and gives Claude a copy), and `sub-human link --reset CODE` re-mirrors. The tail also sends one line when the link goes offline, and one quiet `room link: back online; …` line once it is online again (with what became of the queued posts); a swap that never left online shows nothing. The daemon exits `LINK_IDLE_MS` (60 s) after no seat of this machine is left in the room: online by the host's members document, offline by this machine's live session indexes, so a crashed or abandoned join never leaves it retrying. The server (`scripts/sub-human serve --stdio CODE`, `lib/remote/server.ts`) is one process per connection on the host, spawned by the client's transport; there is no host daemon, and the file locks coordinate it with the host's own hooks.

**The engine** (`lib/remote/link-engine.ts`). `step(state, event, {timings, random, now}) -> {state, effects}`, with no I/O and no clock of its own; `test/link-engine.node-test.ts` drives it from a table on the fake clock.

| State | Means |
|---|---|
| `connecting` | the first dial is under way |
| `online` | `conn` is live: subscribed, seats renewed, outbox sent |
| `offline` | no live connection; a retry timer or a dial is under way (observers see `connecting` while it dials) |
| `fork`, `stopped` | for good, with the code and reason it stopped on |

Events: `start`; `connected`, `subscribed`, `seated`, `flushed {pings}` (a dial's four steps: only after `flushed` does the new connection replace the live one, which is retired); `dialFailed {error}` (FORK, AUTH, PROTOCOL stop it; anything else keeps a live connection, else goes offline and arms `retry`); `lost {conn, error}`; `movedAway`; `redial {why}` (a wake, a network change, a late pong, `SIGUSR2`: the backoff resets); `timer {retry | ping | pong}`; `pong {rttMs}`; `noPong` (dead); `stop {phase, why, reason}`. Effects: `connect`, `subscribe`, `keepSeats`, `flush`, `close`, `retire`, `sendPing`, `setTimer`, `clearTimer`, `online`, `forked`, `publish`, `log`, `finish`.

**Reconnect** (the engine's rules; timings in `lib/config.ts`, the ones the tests and the lab use overridable by `SUB_HUMAN_LINK_*_MS`):
- *Backoff.* A lost connection is dialled again after a delay with decorrelated jitter: random in [`LINK_RETRY_MS` 1 s, 3 × the last delay], at most `LINK_RETRY_MAX_MS` 10 s, so links that dropped together do not redial together.
- *Wake and network change.* A timer ticking every `LINK_WAKE_TICK_MS` (2 s) that fires more than `LINK_WAKE_GAP_MS` (5 s) late, or finds the wall clock that far from the monotonic one (which does not count a sleep), means the machine slept; a changed set of external addresses (`os.networkInterfaces`, polled every `LINK_NET_POLL_MS` 5 s) means it moved. Either is a `redial` event: at once, with the backoff reset. `SIGUSR2` to the daemon does the same.
- *Heartbeat.* `ping` is a protocol op gated by caps, not by version: the daemon says hello with `caps {ping: true}` and pings only a server whose caps list `ping`, every `LINK_PING_MS` (15 s). No pong within `LINK_PONG_MS` (5 s) makes the link suspect (redial); none within `LINK_DEAD_MS` (10 s) declares it dead, which catches a half-open TCP or ssh link after a sleep without relying on `ServerAliveInterval`. The server closes a pinging session that sent no frame for `LINK_SILENT_MS` (45 s). An old peer on either side never sees a ping.
- *Make before break.* A redial while online (a late pong, a wake) makes the new connection completely (hello, `subscribe` from the mirror's last line and hash, seats renewed, outbox sent) before it replaces the old one, which closes once the ops in flight on it are answered; hooks keep using the old one meanwhile, and a redial that fails keeps it. The two streams overlap for a moment, so a line the mirror already holds (the same id and bytes) is skipped; any other mismatch is still `FORK`. Appends stay idempotent by their nonce: the host refuses a nonce it placed already (`AUTH` with reason `PLACED_ALREADY`), and the outbox counts that as sent.
- *Seats.* On every reconnect the daemon `beat`s each live seat of this machine (`identity.localSeats`). A seat whose lease (`SEAT_LEASE_MS`) lapsed on the host during the outage is alive again with its pinned key and link binding unchanged, and nothing is logged: no "left", no "joined". The host never marks a lapsed seat left, so no new join proof is needed (the daemon never holds the signer); a seat the host does show as left is logged, and the person joins again.
- *The `@room` outbox* (`lib/remote/outbox.ts`, `<mirror>/outbox.json`, 0600). With the link down, an `@room` post the hook marks `queue` (`hooks/handlers/at-room.ts` only) and that is a signed `say` by a person to the room is kept by the daemon instead of refused; the person sees `⧗ queued: … (N waiting)`. At most `LINK_OUTBOX_MAX` (50) posts. Answers, consent, proposals, joins and agents' posts are never queued: they fail at once with OFFLINE. The posts go out in order on the new connection, after `subscribe` proved the mirror is the host's prefix and before the link counts as online (a post typed meanwhile queues behind them). The daemon never re-signs, and the host refuses a signature more than `SIG_SKEW_MS` (10 min) old, so a post waits at most `LINK_OUTBOX_AGE_MS` (9 min); an older one, or one the host refuses, is dropped and the person is told with its words. On a `FORK` the queue is kept, not sent, and the FORK line says how many. Online, a post sent over a slow link that the host has not answered within `LINK_RELAY_MS` joins the queue too, under its nonce (see Writes): it leaves when the host's late answer comes, or is sent again, harmlessly, on the next connection.
- *State for observers.* Besides the mirror's `link` document (with `queued` and the last `flush` {sent, unsent}), the daemon writes `<home>/links/<code>.state.json` (`lib/room/links.ts` LinkState) on every change and every pong: `{state, since, attempt, lastError, lastReason, lastCode, rttMs, queued, pid, detail, at}`, in the one link vocabulary the `link` document, the room row, `doctor` and the tail share (`lib/room/link-state.ts` STATES): `online | connecting | offline | fork | stopped` (`connecting` also while an offline link redials). `lastReason` is the typed reason (`lib/reasons.ts`) `doctor` and `link --forget` key on. `doctor` and the statusline read it; a `pid` that is not alive means the daemon is gone.

**Transports.** `lib/remote/transports/index.ts` is a registry: `register(kind, {open, parse?, describe?})`. An invite's locator `KIND:REST` parses through its kind into the link file's `transport` spec, and the daemon's `connectLink` opens that spec with `{code}`; `open()` may be async (a socket or a handshake), and `client.connect` takes the transport or its Promise. Built in: `memory` (tests, worker threads; no locator), `pipe` (`pipe:<home>`, a second home on this machine), `ssh` (`ssh:user@host[:port]`, the pipe with `ssh` in front) and `wss` / `ws` (`wss://host[:port]/path`, below). `fromDuplex(stream)` turns any node stream (a socket, a TLS or WebSocket stream) into a transport, so a socket kind is a parse and an open of a few lines. Each connection still gets its own `serve --stdio` on the host.

**SSH.** A link's ssh locator is `ssh:user@host[:port]` (an invite's line, a login join, a handoff's invite); the ssh kind's parse (`lib/remote/transports/ssh.ts`, through `link-connect.ts` transportOf) accepts only a plain user and host (neither starting with `-`, no spaces, quotes, `%` or a second `@`) and a port, so nothing typed can name an ssh option or a command. Since protocol 3 every new ssh link is a **login link**: the person's own ssh login to the host account runs the host's stable shim, `ssh -T -o BatchMode=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=2 [SUB_HUMAN_SSH_OPTS] [-J via] [-p port] -- user@host '"$HOME"/.sub-human/bin/serve --stdio CODE --link ID --login'` (`env SUB_HUMAN_HOME=H H/bin/serve …` with a remote home; `transports/ssh.ts` `command`; `SUB_HUMAN_SSH_OPTS` comes from the joiner's own environment, for tests and unusual setups, and goes after the link's own options, so it cannot weaken them), with the hello given `LINK_HELLO_MS` (15 s) for ssh to connect. The plugin writes nothing to `authorized_keys` and pins no host key: the person's keys, config and known_hosts decide. `<home>/bin/serve` is a small POSIX sh shim (`lib/remote/shim.ts`) that reads `<home>/bin/current` at run time: the plugin root, the node and the plugin cache dir of the install in use. `invite --ssh` and `doctor --fix` record their own install; every join, SessionStart restore and CLI run refreshes it passively, only from an installed plugin (a root under the Claude Code plugin cache), for the recorded root itself (a new node), or when the recorded root is gone, so a dev checkout or worktree run without `SUB_HUMAN_HOME` never takes over the real home's pointer (`test/real-home-guard.node-test.ts`). It runs that root's CLI, or the newest version in the cache dir when the root is gone, with that node, or `node` on PATH (then Homebrew, `/usr/bin`, nvm) when it is gone, and only ever `serve`. **Lines an older version wrote** still work: a link an admit let in before protocol 3 has its own key and pinned host key in its link file (`key`, `knownHosts`, `alias`: the daemon's ssh adds `-i KEY -o IdentitiesOnly=yes -o UserKnownHostsFile=F -o StrictHostKeyChecking=yes -o HostKeyAlias=…`) and a forced-command line on the host (`command="SUB_HUMAN_HOME=<home> <home>/bin/serve --stdio CODE --link ID",restrict <key> sub-human:CODE:ID`; `serve --link ID` without `--login` accepts only that link's token); kick removes it (`lib/remote/sshkeys.ts`). A beta.15 enrollment door (`… --enroll CODE --kind ssh",restrict … sub-human-enroll:CODE`) now runs `serve --enroll`, which answers the old joiner's first frame with the skew message; `doctor` names such a line and `doctor --fix` removes it. A line written before 0.5 (both paths baked in) is a `doctor` warning. `scripts/remote-docker/` checks it end to end against containers (see Testing).

**The PIN, the card and the key binding** (`lib/remote/invites.ts`, `invite-secret.ts`, `admission.ts`, `host-links.ts`, `machine-key.ts`). What each part guards: the SECRET (128 bits) that nobody without the line gets anything (an unknown one is answered "unknown", charged nothing); the tag that the SECRET goes only to the host the line names (no one in between learns it); the PIN, checked online only (5 tries, throttled per invite and per source machine, every wrong one a room line), that a stolen line alone gets nobody in; the card, the host person's signed answer, that nothing gets in that they did not mean; the key binding that a link is its machine (its machine key proved in every hello) and, over the web, its own Noise key (XK; `hostLinks.keyHolds`: a token over another key is `KEY_MISMATCH`), not a bearer token. A request nobody answers lapses after `ADMIT_TTL_MS`. Replaced in Stage 7b: the 4-digit PIN as CPace's password (vendored `@noble/curves` ristretto255), the enrollment door in `authorized_keys`, per-link ssh keys and the plugin's known_hosts (`docs/archive/short-invites.md`). A locator may name jump hosts, `ssh:user@host[:port]?via=[user@]jump[:port][,…]` (each as plain as the destination), which become `-J`. `sub-human prime CODE` opens a ControlMaster interactively (`ssh -M -N -f -o ControlPersist=8h`, `ControlPath <home>/ssh/cm-%C`) and marks the link `mux`; the daemon then adds `-o ControlMaster=no -o ControlPath=…`: it rides a primed master (one MFA prompt for hours) under BatchMode, never prompts, and never becomes a master itself.

**Over the web (1.1)** (`lib/remote/ws.ts`, `noise.ts`, `transports/ws.ts`, `listener.ts`, `tailscale.ts`, `webhost.ts`).
- *Hosting.* `/sub-human invite --web` (Tailscale Serve), `--public` (Funnel) or `--url https://FRONT[/prefix]` (`webhost.hostWeb`) starts the **listener** (`sub-human listen`, one per home, `127.0.0.1:7420` only, `SUB_HUMAN_LISTEN_PORT`), adds the room to its served set (`<home>/listen/state.json` `{pid, port, rooms: {CODE: {path, url, mode, tailscale?}}, conns}`, which `doctor` reads), and, with `--web`, runs `tailscale serve --bg --https=443 --set-path=/sub-human/CODE http://127.0.0.1:PORT` (`funnel` for `--public`) with the CLI on `PATH` or in `/Applications/Tailscale.app`, the name from `tailscale status --json` `Self.DNSName`. It mints an invite line (kind `ws`, its tag naming the listener's X25519 key) and shows `/sub-human join https://NAME/…/sub-human/CODE SECRET` and the PIN apart (and Funnel's certificate-transparency warning). `/sub-human invite --stop`, or the listener's sweep when the room closes, turns off that one path (`… --set-path=… off`, never `serve reset`). The host's next join after a reboot restarts the listener (`webhost.ensure`).
- *Joining.* `/sub-human join URL SECRET [--as NAME]`, then `/sub-human join PIN`: the room is the URL's last path segment. A WebSocket whose first message is text asks for the listener's key (`{"op": "key"}`, answered `{"v": 3, "key"}`; transports/ws.ts fetchKey); a beta.15 joiner's text `enroll.start` is answered with the skew message. A binary first message is Noise: the listener tries **XK** (prologue `sub-human ws3`: the link's own static key in message 3) and then NK (`sub-human ws1`: a link made under protocol 2), and spawns `serve --stdio CODE --via ws [--peer KEY]` with the key XK proved; serve records it on the admission and the link, and holds every later hello over that link to it. Messages that arrive with message 3 are kept for the channel. The link file's transport is `{kind: 'wss', host, port?, path, hostKey, clientKey}` (the private half in `<home>/links/CODE/client-x25519.json`, 0600).
- *The wire.* The daemon's `open` connects a WebSocket (`ws.ts connect`, RFC 6455, hand-rolled because Node's global `WebSocket` has no proxy support; through an HTTP `CONNECT` proxy from `HTTPS_PROXY` / `NO_PROXY`), then runs **Noise_XK_25519_ChaChaPoly_SHA256** as the initiator with the pinned key and the link's own static key (`noise.ts`, one token-driven handshake for XK and NK: `node:crypto` X25519, ChaCha20-Poly1305 and HKDF-SHA256, no field arithmetic; both patterns checked against the cacophony and snow vectors); a link made under protocol 2 (no `clientKey` in its file) runs **Noise_NK** as before. Message 1 carries `{v: 3, room}` (NK: `{v: 1, room}`); message 2 `{ok}` or an `{error}` only the key's holder could write; XK's message 3 carries the link's key, encrypted; a message 2 that does not decrypt is `AUTH` (the link stops). The per-link key is X25519, made on the joining machine for that link and nothing else: node:crypto cannot turn the Ed25519 machine key into an X25519 one, and a kicked link's key dies without touching the machine's identity (the machine key still proves the machine in every hello). Then each binary WebSocket message is one Noise transport message (at most 65535 bytes) of the NDJSON byte stream, through `fromDuplex`, so reconnect, ping and the outbox above work unchanged.
- *Handoff.* A next host's locator may be a web one (`/sub-human handoff NAME https://FRONT`, `--url`; `webhost.webLocator`): on acceptance it serves the room on its own listener (`webhost.serveAt`) and every invite it mints (`invites.mintFor` `hostKey`) pins its listener's X25519 key, so the others' link files (`handoff.onMoved`, `afterMoved`) carry that key and a fresh key of their own (XK). Its Tailscale path is set up by `/sub-human invite --web` after the move.
- *Doctor* (`lib/cli/doctor/listener.ts`): `listener` (running, pid, port, rooms; a served room with no listener fails), `web:CODE` (`tailscale serve status --json` still lists the path; Funnel warns that the name is public), and a wss link's hello over its real transport.
- *The listener* never runs `server.ts` in-process: after the handshake, if the room is served and still open, it spawns `<home>/bin/serve --stdio CODE --via ws [--peer KEY]` (the stable shim; KEY the link's own key XK proved) for that connection and pipes plaintext both ways; the child authenticates the hello as over any transport. Before a handshake completes it holds at most 16 connections in handshake (64 in all), 10 s each, frames of at most 64 kB; it pings every WebSocket every 15 s and drops one silent for two intervals. It exits 10 minutes after it serves no room.

**Protocol** (`lib/remote/protocol.ts`). Newline-delimited JSON: request `{id, op, params}`, reply `{id, result}` or `{id, error: {code, message, reason?}}`, stream event `{id, ev, data}`. A frame is at most `LINK_FRAME_MAX_BYTES` (1 MiB).

| Op | Params | Result | Who may | Server does |
|---|---|---|---|---|
| `hello` | `{proto, client, caps, machine, machine_key?, token, epoch?}`, `{…, invite, pin?}` or `{…, login: true}` | `{v, proto, server, caps, room, link, token?, epoch, time, machine?}` (time: the host's clock in ms, for `doctor`'s skew check; machine: this machine's id in the room as the host records it) | anyone | version: the highest common one of the two `proto` ranges (a hello with none is `PROTOCOL` `SKEW`; a beta's `v`, the least it needs, is honoured), else `PROTOCOL` `SKEW` naming who updates; a mirror's `epoch` later than this log's is `STALE`; `verifyToken`, or `redeemInvite` (a promote's invite checks the PIN; the token is returned once), or `loginLink`; neither: answered, still unauthenticated. A new link records the machine id `machine_key` proves (below) |
| `join` | `{name, role: 'member', pubkey, proof}` | `{ok, rejoin?}` | a link | `checkSeatProof` (the key's holder signed this join), then `seats.enter` with the link's `machine`; another key for a pinned name is `AUTH`; binds the name to the link. A bound link (an admission's one name, a handoff's or promote's pre-bound seats) joins only those names: any other is `AUTH` before a seat is taken |
| `leave` | `{name, reason}` | `{ok}` | a link, its own seat | `seats.exit` (member_left; the reaper when nobody is left) |
| `beat` | `{name, presence?}` | `{ok}` | a link, its own seat | `members.beat` (lease, presence) |
| `append` | `{payload, epoch?}` | `{entry}` | a link, `payload.from` its own seat | the seat's quota (`append.human`, `append.agent`, counted in the log) or `RATE` `QUOTA`; then `store.place`: validate, rate, replay, verify against the pinned key; then `decide` after an answer. A system kind is `AUTH` (only the host writes those) |
| `subscribe` | `{after, hash, snapshot?}` | stream | a link | the link's `subscribe` quota; one stream per connection (a second subscribe replaces it); `hash12` of the host's line `after` must equal `hash`, else `FORK`; with `snapshot: true` and `after` 0, a host with a snapshot that fits a frame sends `snapshot` (its chain head and line, count, non-chat entries, window, pins, host) and the lines after its id; then `entry` per line, `doc` for `members`, `presence/*`, `tasks`; `end` `{reason: 'closed' \| 'FORK' \| 'AUTH', message?}` (AUTH: the link was revoked). The `snapshot` cap is additive: an older host's caps do not offer it and an older mirror never asks, so either gets every line, as before, across the host's segments; a host that began from its own host's snapshot refuses a replay of lines before it (`FORK`, with the reason) |
| `blob.get` | `{ref}` | `{bytes}` (base64) | a link | `blobs.get` |
| `blob.put` | `{name, bytes}` | `{ref}` | a link | only `plans/<hash12 of the bytes>.md`, at most `PROPOSAL_FILE_MAX`, written once; a new one counts against the link's `blob.put` quota (`RATE` `QUOTA`) |
| `ping` | `{}` | `{pong}` (the host's ms) | a link | the heartbeat; listed in the server's caps, so a client pings only a server that answers. A session whose hello carried `caps {ping: true}` and that then goes silent for `LINK_SILENT_MS` is closed |
| `handoff.accept` | `{id, accept, locator, invites}` | `{ok, epoch, entry}` | a link, the ask's target seat | `lib/handoff.ts` serverAccept: the ask pending and not expired, `accept` signed by the target's pinned key for this id, epoch and locator, the invites to that locator; appends `host_changed`; after the reply, stops the room's Claude job and mirrors the new host |
| `handoff.refuse` | `{id}` | `{ok}` | a link, the ask's target seat | the ask becomes `refused` |

Error codes, the same on both ends and on the wire: `INVALID`, `RATE`, `LOCK`, `NO_ROOM`, `OFFLINE` (the link is down or the deadline passed), `HOST_ONLY` (an op a mirror never performs), `AUTH` (no or bad token, a used invite, a `from` not this link's seat, a key mismatch, a bad signature, a replayed nonce, a stale `ts`), `FORK` (the mirror's last line is not the host's), `PROTOCOL` (unknown version, malformed frame) and `STALE` (another host epoch: a host the room moved away from, or a copy that has not caught up with the move).

**Reasons** (`lib/reasons.ts`). Beside its code an error may carry a typed `reason`, which says exactly which failure it is: `RoomError(code, message, reason?)`, `error.reason` on the wire (additive: a 0.5 beta sends and reads none), kept by the bridge, the daemon's socket, its `link` document (`why`) and its state file (`lastReason`). Code that decides keys on it, never on the message's words (the message is for people): the outbox (`PLACED_ALREADY`), the mirror (`UNKNOWN_OUTCOME`), `doctor`'s fix lines and `link --forget` (`ROOM_CLOSED`, `NO_SEAT`, the spent-invite reasons, `MOVED_AWAY`). The list: `AUTH` PLACED_ALREADY, INVITE_UNKNOWN, INVITE_USED, INVITE_BURNT, INVITE_EXPIRED, INVITE_OTHER_MACHINE, INVITE_OTHER_LINK, PIN_NEEDED, PIN_WRONG, PIN_LAST, ADMIT_REFUSED, ADMIT_LAPSED, ADMIT_REVOKED, ADMIT_LATE, TOKEN_UNKNOWN, LINK_REVOKED, KEY_REVOKED, NOT_BOUND, NOT_JOINED, LOGIN_ONLY, MACHINE_TAKEN, SSH_HOST_KEY, SSH_DENIED, SSH_NO_SHIM, SSH_NO_ROOM, SSH_OLD_HOST; `OFFLINE` UNKNOWN_OUTCOME, NOT_SENT, DAEMON_DOWN, ADMIT_WAITING, QUEUE_FULL; `RATE` QUOTA; `PROTOCOL` SKEW; `STALE` MOVED_AWAY, BEHIND; `FORK` LOG_RESET, NOT_CHAINED; a stopped link ROOM_CLOSED, NO_SEAT. Against a beta host, which sends none, a decision falls back to the code alone (a duplicate a slow link resent is then reported unsent, although it landed).

**Quotas** (`lib/config.ts` LINK_QUOTAS, `lib/remote/quota.ts`). Every op a link sends counts against its own window; over one is `RATE` with reason `QUOTA` and when to try again.

| Op | Max per window | Counted |
|---|---|---|
| `append.human`, `append.agent` | 30 per minute | per seat, in the log (a Claude's posts to every addressee together) |
| `blob.put` (a new plan) | 40 per hour | per link, the host document `remote/quota` (a reconnect resets nothing) |
| `subscribe` | 60 per 10 minutes | per link |
| `seat` (join, leave) | 30 per 10 minutes | per link |
| `hello` | 120 per 10 minutes | per link |
| any hello on one connection | 10 per minute | per connection |
| `beat`, `blob.get`, `ping`, `handoff.*` | 120, 600, 60, 20 per minute | per connection |

**The host's watch.** A `subscribe` stream follows `FsRoomStore.watch` (`lib/room/watch.ts`): one recursive `fs.watch` per room directory and process (shared by every stream of the web listener), coalesced to one change per turn of the event loop that names what changed: the log (a line, a segment, the snapshot) and which documents. A log change reads the tail; a changed document (`members`, `tasks`, `presence/NAME`) is read again alone and sent when it differs; a `members` or `remote/handoff` change also checks the handoff and the closed room. A poll every `FOLLOW_SLOW_MS` (2 s) covers an event the watcher missed; a watcher that cannot start or fails, or a store with no watch (the memory store), is polled every `FOLLOW_POLL_MS` (250 ms) as before. A replay (a first sync, a long gap) goes out `REPLAY_BATCH` (500) lines per turn and waits for the transport to drain (`Transport.writable`) between batches; after a write the stream sends everything at once (read-your-writes).

**Machine ids.** Each home has an Ed25519 machine key (`lib/remote/machine-key.ts`, `<home>/keys/machine.json`, 0600, under the hooks module's `Read` guard). The link daemon's hello carries its proof (a signature over the room and a fresh `ts`); the host records the machine id the key gives (`k` and 15 hex of its sha256) for a new link, and the id the hello reports only as the link's `label`. The hello's reply says the recorded id; the joiner keeps it per room (`<home>/machines.json`, `home.machineIn(code)`), reports it in every later hello and compares a seat's `machine` with `home.isMine` (any of this home's ids): liveness, the admission card's targets, the seat's `account`, handoff, `mod/send.ts`'s choice between a native and a room message. One key, one id, for every room and host: a machine that joins again (a new invite, a handoff's new host) is the machine it was, and no machine without the key can be it. A bound invite's link keeps the machine it was minted for. A hello with no proof (a 0.5 beta's) keeps the reported id, which may not be the host's own or another link's (`AUTH` `MACHINE_TAKEN`).

**Room options** (`lib/room/options.ts`, the host document `options`, never streamed). Set only by the host person in their own shell: `sub-human options CODE [NAME on|off]` (the Bash guard refuses it to a model). `login-same-person` (default off): a seat that joins over the host account's own ssh login gets the host's `account`, so consent counts it as one person with the host's seats; off, each such seat is its own person, as an invite's is (on a shared login, everyone who has it would otherwise answer as the owner).

Stream events besides `entry`, `doc` and `end`: `handoff` (the ask, to the link holding its target seat only) and `moved` (after the `host_changed` line: `{epoch, host, machine, locator, invite}`, the invite this link's machine's alone), then `end {reason: 'moved'}`. Both are private to one link and never in the log.

**Moving the host** (`lib/handoff.ts`, the CLI bodies in `lib/cli/handoff.ts`). The host's machine holds the log, serves the links and runs the room's Claude on the host person's model account, so a sleeping host means an offline room. Authority is the log's: a `host_changed` entry (via system) `{epoch, host, machine, locator, accept?, ask?, promoted?}` moves it, and `store.hostState()` reads the last one (epoch 0 before any). There is no automatic failover.

```
A (host, alice)                         B (bob, mirror)                         C (carol, mirror)
/sub-human handoff bob ─► remote/handoff {asked, epoch 1}
serve(B's link) ─ ev handoff ─────────► daemon: kv handoff ─► tail: wake ─► AskUserQuestion card
                                         (the hooks' card: the room's Claude runs on bob's account; stay reachable)
                                         "Host it here" (via=human, consent.ts) ─► accept: mint one invite per
                                         other machine (invites.mintFor: that machine, its seats), sign host_accept
serve(B's link) ◄─ op handoff.accept ──
  check ask, signature, invites; append host_changed {epoch 1, bob, B, locator, accept, ask}
  room Claude record left; remote/handoff = moved + invites; reply (B's mirror holds the line: read-your-writes)
  after the reply: claude stop <job>; link file = A's invite; daemon started (A mirrors B)

                                         seats' pid/session back (identity.adoptLocalSeats), room Claude started here
serve(C's link) ─ entry host_changed, ev moved {invite for C} , end moved ─────────► onMoved: link file ->
```

- **Epochs are enforced, not merged.** The old host's `FsRoomStore.place` refuses every line once its log says the room moved to another machine (`STALE`; a `host_changed` naming this machine at a later epoch, a promote, passes). Its server then serves only `hello`, `subscribe`, `blob.get` and `ping`, so a member that reconnects late still gets the line and its machine's invite (kept a day). A server refuses a hello from a mirror at a later epoch (a host the room moved away from) and an append from another epoch. The link daemon sends its mirror's epoch with both.
- **Unreachable new host.** A re-pointed link that cannot connect stays offline with a reason that names the new host and says to ask for an invite (`/sub-human invite` there) and type its line. That join replaces the link's credentials (the old transport's pinned key and mux kept where the destination is the same), restarts the daemon and marks the link `rebind`, so once the new host's card lets the machine in, a bare `/sub-human` (in a room, with a `rebind` link) joins the seat again over the new link. `sub-human handoff --status` on the new host lists the machines that have not reconnected. Over SSH a re-pointed link keeps what this machine added to it (`hosting.linkTransport`): its own link key (one is made for an old host that had none), `mux` from `sub-human prime`, and the new host's sshd key pinned (a handoff's and a promote's invites carry it); `--via JUMP` on `handoff`/`promote` puts a ProxyJump in the locator. Until the new host lets that key in, the offline reason (and `doctor`) says to ask for an invite.
- **Promote** (`sub-human promote CODE --confirm CODE`, a person's own shell): refused while the link is online or down less than `PROMOTE_OFFLINE_MS` (10 min, `--force`). The member's full mirror becomes the room at epoch + 1 (`host_changed` with `promoted: true`) and prints one invite per other machine. **It can fork**: an old host that was only asleep goes on alone, and lines it wrote that the promoter never got are lost to the room. A member still linked to it stays on the old side until it gets an invite. When the old host returns, `sub-human demote CODE` (the invite and its PIN pasted on stdin) sets its log aside (`orphaned-<time>.jsonl`, never merged), stops its room Claude and mirrors the new host. A mirror whose copy is behind the promoter's catches up; one that is ahead (it got lines the promoter never did) meets `FORK` and re-mirrors with `sub-human link --reset`.
- **Limits.** The new host must be reachable by every member over the transport in the ask's locator. For SSH that means the new host must let each member's key in. The design for automating that has members send their SSH public key over the existing link, and the new host shows one consent card to authorize them all. That is not built: today a member that cannot get in is given an invite (`/sub-human invite`), types its line, and the new host's card lets it in; the lab's `handoff` scenario does that. A handoff's and a promote's invites are one record, a bound invite (`invites.mintFor`: `{v: 2, machine, seats, expires_at, handoff?, pin_sha256?, tries?}`): bound to one machine with its seats pre-bound. A handoff's has no PIN, since each travels only over that machine's already authenticated link; a promote's has a 6-digit PIN checked online (`pin: true`), printed as "run `sub-human demote CODE` and paste: INVITE PIN": each machine (a member, or the old host coming back) runs its own (`handoff.demote`), and the invite and PIN go in on stdin or `--from FILE`, never in argv.

**Versions.** `protocol.PROTO` is the range of protocol versions an end speaks (now 1–3: 2 adds a promote's invite PIN; 3 the invite line (its SECRET in hello's `invite`, the PIN checked online, `as`), the hello's `nonce` and the reply's `host` proof, and Noise XK over the web) and `PLUGIN_VERSION` its plugin version. The client's `hello` sends `proto` and `client`; a 0.5 beta's also sends `v`, the least it needs, which the server honours. The server answers `v = negotiate(its range, the hello's)` plus its own `proto` and `server`. A hello with no `proto` (a sub-human before 0.5) and no overlap are both `PROTOCOL` `SKEW` with `skewMessage`, which names the side to update: "host runs sub-human 0.4.0 (protocol 3–4); you run 0.3.0 (protocol 2). Update your plugin: /plugin update sub-human", or "The host must update" when the joiner is newer; with `need` (an invite line needs 3) it names the side that lacks it even when the ranges overlap. **Pairings with 0.5.0-beta.15 (protocol 1–2):** a link made under 2 (a token; NK over the web; an ssh key let in with a forced command) keeps working at v2 against this version either way, until it is invited again or kicked. A beta.15 host's line ends with a 4-digit PIN: this joiner refuses it locally, saying the host must update. This host's line ends with a SECRET: beta.15's parser refuses it ("the PIN is the 4 digits"), and this host's invite text says the joiner needs a newer sub-human. A beta.15 enrollment that still reaches this host (a line minted before the host updated) gets `PROTOCOL SKEW` with `skewMessage` from the listener or from the door's `serve --enroll`. A v3 invite line at v < 3, or over NK, is `SKEW`. Everything else added since (`error.reason`, `machine_key`, the reply's `machine`) is additive. The daemon stops on it and the join shows it. Readers tolerate a newer host: lines of unknown kinds or fields are stored verbatim and rendered generically (an unknown `via` as "bob (via relay)", never as the person's words, and never a wake), and an unknown streamed document or event is skipped and logged instead of stopping the link. Writes stay strict: the host validates every payload, so a newer joiner's new kind is `INVALID` on an older host (the host is updated first). `test/remote-server.node-test.ts`, `remote-invite-line.node-test.ts` and `test/remote-link.node-test.ts` fake N-1 and N+1 on both ends.

**What changed for trust.**
- **Sig v2.** A signature covers the payload, not its place in the log (without `id`, `at`, `prev`; with `room`, `from`, `nonce`, `ts`), so the remote hook signs and the host places. v1 lines still verify. The host refuses a replayed nonce and a `ts` outside `SIG_SKEW_MS` (10 min); `at` is the host's clock.
- **Keys are pinned in the log** and strictly: `member_joined` carries the seat's public key, the first key per name is that name's for the room's life, and a lost key means a new name.
- **A link writes only as its own seats.** The server checks every `from` against the seats joined over that link (`mayWriteAs`), validates again and verifies against the pinned key. A `join` needs a proof signed by the seat's key, since the public key alone is in the log.
- **Credentials.** An invite line is single-use and shown once; the host keeps `sha256(secret)` and `sha256(secret:PIN)` only. The link token is a seat-level credential: kept in clear in the joining machine's link file (0600, the same trust as the seat key), hashed on the host; a web link made under protocol 3 also needs its own Noise key, so the token alone gets nowhere. An invite is untrusted input: its locator is only a home path or a plain `user@host[:port]` with plain jump hosts, and the daemon always runs this plugin's own `serve` (or `ssh` with fixed options), never a command or option the invite names. The SECRET goes only to a host that proved the key the line's tag names; the PIN is checked online only (5 tries per invite, throttled, at most 4 open), and one that holds still waits for the host person's card; neither reaches a model (every `join`/`invite`/`admit` prompt, and any with a word of digits or a SECRET-shaped word, is a hidden block, and neither step takes the seat) and the PIN leaves the joining machine's link file once the host answered. Over ssh nothing is written to `authorized_keys`: the joiner's own login is the way in. The Bash guard denies `sub-human invite`, `admit`, `kick`, `prime`, `listen`, `link`, `serve`, `options`, `handoff`, `promote`, `demote` and `doctor --fix`/`--bundle` to a model (a plain `doctor` is read only) and sends the person to a terminal outside Claude Code (its `!` mode would put the output in the conversation: run there, `invite` masks the SECRET and the PIN, `promote` the PIN). A link the host refused before any token drops its invite and PIN from the link file (`refused` says why). A handoff moves only on the new host person's own card answer, signed with their seat key and kept in `host_changed` beside the old host's signed ask; its invites (bound invites with no PIN: one machine, its seats pre-bound) travel only over each machine's authenticated link, and a follower reaches the new host over its own ssh login or, over the web, with a key of its own.
- **Over the web, the front sees ciphertext.** Tailscale, Funnel's relays or a reverse proxy end TLS and see IPs, timing and sizes; every byte inside the WebSocket is Noise ciphertext keyed to the listener's own X25519 key (`<home>/listen/host-x25519.json`, 0600, random, never derived from or used for anything else), which the joiner pins from the URL. The listener binds loopback only. A Funnel hostname is public (certificate-transparency logs), so probes cost a PIN try at most, and each wrong PIN is a room line.
- **Addressed is not private.** A post with `to` has its own rate bucket (`RATE_ADDRESSED_MAX`), but the whole room reads the log, on every machine.

**Observability.** `lib/room/link-state.ts` reads how a link is doing: the daemon's state record `<home>/links/<code>.state.json` (`{state: online|connecting|offline|fork|stopped, since, attempt, lastError, lastReason, lastCode, rttMs, queued}`), else the mirror's `link.json`; a record whose daemon pid is gone reads `offline` (fork and stopped stay). ## Security model

One machine per room (its host), trusted collaborators: everyone on the host runs as its one OS user, and the host itself is trusted by everyone who joins it. The threat is a member's Claude (possibly steered by text posted in the room) speaking or consenting as a person. Defences: `via=human` only from hooks, signed with a key only hook processes load (on whichever machine the person sits; the host verifies against the key pinned in the log); the store guard (the hooks module's `mod/guard.ts`, in-process) denies file-tool writes into the store and Bash commands that name it, set `SUB_HUMAN_HOME` or run the plugin's modules; the module's `prompt.submit` gate drops an `@room` whose engine-set origin is not the person's (composer, sdk, bridge), and at-room posts only with that origin and the session's module nonce (a seat requires the module). The module mints the nonce per session id, keeps it in `$.state`, and `mod-hello` writes it to the 0600 lease `<home>/sessions/mods/<sid>.json`: forging an `@room` takes reading that lease, which the guards deny by path but a determined local process can still do. The store guard is a string check: a script file written first, an obfuscated path or a variable built at run time evades it. What it cannot evade: `via=human` needs the seat key's signature, readers mark an unsigned human line "(unverified)", and the hash chain shows an edited log. The room Claude's typed-input refusal reads the origin unchecked, since forging it only refuses more. An `@room` is refused, never passed to the model, whenever the prompt shim fails; consent only from the native dialog; a link writes only as the seats joined over it, an SSH key reaches only its forced command's room and link, and the guard denies `sub-human invite|admit|kick|prime|listen|link|serve|handoff|promote|demote` and `doctor --fix` to a model; the room's host moves only on the new host person's own card answer. The guard also denies `Read` of a seat's private key (`<home>/keys`): the one file a model could sign `via=human` with; the rest of the store stays readable. Over a link the host binds an admitted machine to the one name the card let in (`LinkRecord.bound`), takes at most `LINK_HUMAN_RATE_MAX` of a person's posts a minute and `LINK_BLOBS_MAX` plans a connection, and `propose({path})` reads only under the session's cwd or Claude Code's plans dir (the bytes go to every mirror). Not covered: other MCP servers, a hostile local user. Full list: [README → Threat model](../plugin/sub-human/README.md#threat-model).

## TypeScript

The runtime (`lib/`, `hooks/`, `mcp/`, `statusline/`, `mod/`) is ESM `.ts` with no build step: what is committed is what runs. Plan and reasoning: [archive/TYPESCRIPT.md](archive/TYPESCRIPT.md).

- **Node strips the types** of each `.ts` it loads (Node 24.3+, the first 24 without an ExperimentalWarning). Only erasable syntax works (no `enum`, `namespace`, parameter properties or decorators: `erasableSyntaxOnly`), and every import spells out its `.ts` specifier. `hooks.json` checks the Node version and `/sub-human` says when it is too old.
- **The hooks module** (`mod/register.ts`) runs in Claude Code's Bun worker, which transpiles it itself.
- **Nothing checks types at run time.** `tsc` (root `tsconfig.json`: `strict`, `noUnusedLocals`, `noEmit`) runs only in `npm test` (`npm run typecheck`) and CI. `typescript` and `@types/node` are root devDependencies; `plugin/sub-human/package.json` is only `{"type":"module"}`, so Claude Code installs nothing.
- **Claude Code's types** come from `typings/claude-code/`, a committed snapshot of the declarations Claude Code writes beside a hooks module (`import type … from 'claude-code'`).
- **Shared types** live beside their slice: `lib/room/types.ts` (entries, the store), `lib/remote/types-core.ts` and `types-rest.ts` (the wire, links), `lib/types-app.ts` (seats, the tail, rows), `hooks/types.ts` (hook payloads), `mod/core/types.ts`, `lib/cli/types.ts`, `mcp/types.ts`.
- **`scripts/sub-human` stays JavaScript.** Its path is frozen (the serve shim, `authorized_keys` lines, the row launcher and the daemons run it), and node strips no types from an extensionless file, so it is a shim that imports `lib/cli/main.ts`.
- **Compile cache.** Every node command preloads `hooks/compile-cache.js` (`node --import …/compile-cache.js …/X.ts`: `hooks.json` and the module's `shimArgv` (`hooks/run.ts <handler>`), `.mcp.json`), plain JS that turns on `module.enableCompileCache(<home>/cache)` (`lib/cache-dir.js`; 0700, so no shared temp directory holds the code cache of a process that signs) before the hook's modules load. Without it each run strips every module again (about 50 ms a hook); with it a hook starts within about 5 ms of the old JavaScript.
- **Tests are TypeScript too.** `plugin/sub-human/test/**/*.node-test.ts` and their helpers (`test/helpers.ts`, `test/hooks/helpers.ts`, `test/support/*.ts`) are ESM `.ts` that `node --test` runs with the same type stripping, typed against the plugin's own types. `tsconfig.test.json` extends the root config over `plugin/sub-human/test`, and `npm run typecheck` runs both. They are named `*.node-test.ts`, not `*.test.ts`, because `claude plugin test` collects every `*.test.ts(x)` under the plugin it is given (recursively, skipping only `node_modules` and dot folders; cc CONTRACT `plugin-test-discovery`): with that suffix `npm run test:mods` runs only `mod/test/*.test.ts`, and a bare `claude plugin test plugin/sub-human` stays correct too. `npm run test:plugin` globs them (`node --test 'plugin/sub-human/test/**/*.node-test.ts'`, each file in its own process) and preloads `test/helpers.ts` with `--import`.
- **Lazy loads.** A module that must load only past an early exit, or that breaks an import cycle, is loaded with `createRequire(import.meta.url)` at that point (`require(esm)` is synchronous and cached) and typed `typeof import('./x.ts')`. Everything else is a static named import; there are no default exports.

## Performance

Everything is a `node` start, so the number of processes per event is the main cost. Measured per event for the stage 2 hooks entry (0.5.0-beta.15 → this tree), in a scratch home: the `hooks.json` command hooks run through `sh` exactly as written, with a `node` first on `PATH` that only counts its starts (each entry whose matcher matches; SessionEnd's own shell check decides), plus the module's `$.process.run` and `$.process.spawn` calls counted by the wiring test `mod/test/starts.test.ts` (the same events raised through the test kit). "Seated" is a member whose tail child has not yet reported the seat, so its prompts still run `prompt.ts`; with a delivering tail child a plain prompt is 0 (+1 `presence`, not awaited, when the last presence was not "working").

| Event | No seat, before | No seat, after | Seated, before | Seated, after |
|---|---|---|---|---|
| session start | 2 (`row-launcher`, `mod-hello`) | **0** | 3 | 2 (`mod-hello`, the tail child) |
| a plain prompt | 0 | 0 | 2 | 2 (`prompt`, `presence`) |
| an `@room` | 1 (its refusal) | **0** (the module refuses it) | 1 | 1 (`prompt`: signing) |
| `Bash`, `Read`, `Write`/`Edit` | 0 | 0 | 0 | 0 |
| `Agent` (not a row) | 2 (`row-guard`, `row-map`) | **0** | 2 | **0** |
| `Agent` (a row) | 2 | **0** | 2 | 2 (`row-guard`, `row-map`) |
| SubagentStop (not a row) | 1 (`row-hold`) | **0** | 1 | **0** |
| SubagentStop (a row) | 1 | **0** | 1 | 1 (`row-hold`) |
| `AskUserQuestion`, `EnterPlanMode` | 2 each (`consent` Pre, Post) | **0** | 2 each | 2 each |
| `ExitPlanMode` | 3 (Pre, PermissionRequest, Post) | **0** | 3 | 2 (PermissionRequest only while a review may be open) |
| a room MCP tool | 1 (`consent` Pre) | **0** | 1 | 0 while no review may be open (else 1) |
| `TaskCreate`/`TaskUpdate`, completion | 0 | 0 | 0 | 0 (the room's Claude: 1, `tasks`) |
| turn end (Stop) | 0 | 0 | 1 | 0 while no review may be open (else 1) |
| Notification, StopFailure | 1 each (`presence`) | **0** | 1 each | 1 each (`presence`, not awaited) |
| `/compact` | 2 (`session-restore`, `mod-hello`) | **0** | 2 | 2 (`session-restore`, `mod-hello`) |
| `/clear` | 4 | **0** | 5 | 4 (`session-end`, `session-restore`, `mod-hello`, the tail child) |
| `--resume` | 4 | **0** | 4 | 3 (`session-restore`, `mod-hello`, `row-rewake`) |
| session end | 1 (`session-end`) | **0** | 1 | 1 (`session-end`) |
| `/sub-human` (typed) | 3 (`join`, `mod-hello`, a tail child) | 3 (`mod-hello` for the lease, `join`, `mod-hello`) | 2 | 2 (`join`, `mod-hello`) |

So a session that never joins a room starts no node on any event but `/sub-human` (`mod/test/starts.test.ts` holds that), where before it paid 2 at its start and 1 to 3 on every subagent, card, plan-mode call, room tool, notification, compact, clear, resume and its end. The SessionEnd check is a few shell builtins (`[ -e ]` on three paths) in the shell Claude Code runs every command hook in.

Long-lived per seated session: the tail child and the MCP server (one idle `node` each); a session with no seat runs only the MCP server, unless it typed a PIN join (then also the tail child, which looks the join up every 2 s until the host's card answered, every 10 s after). `append` reads only the log's tail for `id` and `prev` (a person's entry also reads back `2 × SIG_SKEW_MS` for its nonce); the pinned keys and the room's host come from the store's non-chat entries, carried forward one new line at a time. Readers keep a per-file cache and parse only appended bytes: `readAll` returns that cache itself (sealed segments parsed once), and `readView` starts from the snapshot and keeps the checkpoint it reached in the active segment in memory, so a process's first read parses one segment and the health tick re-parses nothing.

The 100k-entry budget (`test/perf.node-test.ts`, in-process after warm-up, the median of 15; a log written as a day of a busy room leaves it: one entry a second, a proposal every 1,000 with answers, 1 % signed human words), measured on this Mac before the stage 5 store split (0.5.0-beta.15 plus stages 1 to 4) and after:

| | Budget | Before | After |
|---|---|---|---|
| an `@room` post: the signed append | ≤ 50 ms | 150 ms (cold 175) | **1.5 ms** (cold 130) |
| the agent-panel status line (room row and one participant row) | ≤ 30 ms | 73 ms (cold 352) | **5.5 ms** (cold 77) |

Before, a person's append re-read the pinned keys from the whole log (no `log.idx` to start from) inside the log lock, and the status line refolded consent over every entry, normalizing each, and scanned the log several times per row. The cold numbers are a process's first call, which parses the log once.

Stage 6 (segments and the snapshot) measured the same test, and a fresh process over the room once its log is in segments (its first append and status line, imports done before timing; before: stage 5 with `log.idx` written, as a live room's tail leaves it):

| | Budget | Stage 5 | Stage 6 |
|---|---|---|---|
| an `@room` post, warm (median) | ≤ 50 ms | 1.5 ms | **0.6 ms** |
| the status line, warm (median) | ≤ 30 ms | 5.5 ms | **3.7 ms** |
| an `@room` post, a fresh process | ≤ 60 ms (cold) | 7 ms | **5.5 ms** |
| the status line, a fresh process | ≤ 60 ms (cold) | 86 ms | **20 ms** |
| the first append in a room from before segments (it seals the 15 MB log once) | | 128 ms | 137 ms |

The warm append reads back only the active segment and the snapshot's window; the status line reads `room.readRecent` (every non-chat entry and the lines since the last rotation) instead of every line.

**Idle cost per seat (stage 8, for the hub decision).** The plan's test for Stage 9 (the hub) is: skip it if, at N ≤ 5 seats, tail + hold + status line cost under 1% of a core idle, with no `ps` on the hot path. This was measured on an Apple M2 (8 cores, macOS, node 24.15, Claude Code 2.1.296) in a scratch home with fake seats (sleeping processes) and a fake MCP client, no real Claude. Each tail and room MCP server was left idle for 60 s, and `ps -o time=` was read at the start and end of the window (10 ms resolution). The status line figure is the median of 20 fresh runs. A PATH shim logged every `ps`.

| Per seat | 1 seat: CPU % of a core | 1 seat: `ps`/min | 5 seats: CPU % per seat | 5 seats: `ps`/min |
|---|---|---|---|---|
| room tail | 0.28 | 2 | 0.22–0.23 | 10 per tail (50 on the machine) |
| room MCP server with its holds (1 s timer only while a hold is open) | 0.18 | 0 | 0.18–0.20 | 0 |
| status line, one refresh (a fresh `node`) | 30 ms CPU, 40 ms wall | 0 | 40 ms CPU, 40 ms wall | 0 |
| status line every 5 s (Claude Code's rate while rows show) | 0.6–0.8 | 0 | 0.6–0.8 | 0 |
| **total** | **1.1–1.3** | 2 | **1.0–1.2** | 10 per host tail |

The only idle `ps` is the host tail's seat sweep: `ps -o lstart= -p PID` per local seat (`lib/lock.ts` pidStart, cached 30 s), not the batched `pidStarts`. Tail and hold together cost 0.4–0.5 % per seat and stay flat from 1 to 5 seats. The total is just over budget because of the status line, which is Claude Code starting a node process every 5 s; a hub would not remove that cost. Not measured: the room's Claude's own tail, a seat in a room hosted elsewhere (its link daemon), the host's per-link `serve`, and real sessions.

## Testing

- `npm test`: `npm run typecheck` (strict `tsc` over the runtime and, with `tsconfig.test.json`, the tests; zero errors), then `node --test` over `plugin/sub-human/test/**/*.node-test.ts` (each file in its own process, in parallel; `test/helpers.ts`, preloaded with `--import`, strips `CLAUDE*` env and removes temp dirs) and `scripts/test`. Hooks are driven as child processes with JSON payloads, through `hooks/run.ts <handler>` as Claude Code and the module run them (`test/hooks/`; `test/hooks/stdin.node-test.ts` feeds every handler stdin it cannot use). The tail runs on a fake clock (`lib/clock.ts`).
- **Store contract**: `test/store-contract.node-test.ts` runs one suite against `FsRoomStore`, `MemoryRoomStore`, the thread store and `remote` (a mirror through the bridge to a server on a worker thread); `store-bypass.node-test.ts` checks nothing else touches room files; `hooks/security.node-test.ts` checks who can load the signer.
- **CI**: `.github/workflows/ci.yml` runs `npm test` and `npm run test:thread-store` on Node 24.3.0, 24 and 26 (ubuntu) and Node 24 (macOS), `node scripts/check-version.js origin/<base>` on pull requests, and a separate job runs `npm run test:remote-docker` (Docker on ubuntu). Without Claude Code the mods tests and the probe test skip.
- **No timing guesses**: a test waits on a condition (a gate file the stub claude waits for, a child's pid, `test/support/started.ts` stamping a child's start) or reads what the code asked for (the link's retry delays), never on a sleep that a loaded machine outruns. `npm test` passes with four copies running at once.
- **Probe**: `npm run probe` (`scripts/probe-cc.js`, through `cc.probe`) checks the installed Claude Code binary for every `CONTRACT` search string and shape (about 3 s: one latin1 view, each shape tested only around its longest literal); `test/cc.node-test.ts` runs it when a binary is present and bounds its CPU time, not its wall time. No search names a minified identifier (shapes use `~` instead), so a miss means the code itself changed: re-read that spot and record what changed in a new `docs/internals/cc-<version>.md`.
- **Docs**: `npm run docs` regenerates this file's tables; `scripts/test/arch-doc.test.js` fails when they are stale.
- **Remote**: `remote-protocol`, `remote-server` and `remote-link` tests cover the wire, invites, links, quotas and the daemon; `link-engine.node-test.ts` drives the daemon's state machine from a table on the fake clock; `room-watch.node-test.ts` the host's watch; `remote-e2e.node-test.ts` runs two homes on one machine with the real hooks as child processes and the daemon over the pipe transport. `npm run test:thread-store` runs the hook tests with every store call over the bridge. `npm run test:remote-docker` (opt-in, needs Docker; `scripts/remote-docker/harness.js run`) checks SSH for real: a devbox container (sshd, the host room, alice) behind toxiproxy, bob joining from this machine with the real hooks and a throwaway key, and 11 assertions (distinct machines, nothing host-only on the joiner, serve under sshd as the forced command, bytes on the wire, cut and resume with no gap, a latency toxic, wrong-link AUTH, nothing left behind); it writes an evidence bundle to `/tmp/sub-human-remote-proof-<time>/`. `harness.js up|say|cut|heal|latency|down` keeps the same stack up for real Claudes to join by hand (`up --host-seat NAME --joiners A,B`: per joiner a key, an invite and `/tmp/sub-human-remote-manual/NAME.env`).
