   Plan: cursor paging for GET /tasks

   To decide: how GET /tasks lists tasks, newest first, with cursor paging. bob asked for: "cursor paging for GET
   /tasks: ?limit&after, opaque cursor, newest first".

   Context

   - src/server.js returns 501 for GET /tasks right now, with a TODO saying to agree on the design in the room first.
   - src/store.js: allTasks() returns tasks in insertion order. Each task looks like {id, title, done, createdAt}.
   - It stands in for a Postgres table with about 4M rows and about 30 inserts/s at peak. So offset paging would be
     slow and would drift as new rows arrive.
   - Tasks share timestamps. seed() gives every 3 tasks the same createdAt ("as bulk imports do in production"). A
     cursor built only on createdAt would skip or repeat rows at page edges.

   Proposed design

   - Order: createdAt DESC, id DESC. id breaks ties, so the order is total and stable.
   - Request: GET /tasks?limit=N&after=CURSOR
     - limit: default 20, max 100. If it is not a positive integer, or is over the max, the server returns 400 (it
       does not clamp).
     - after: optional. Leave it out to get the first (newest) page.
