# Is sub-human 0.7.0 worth doing? Item by item

Date: 2026-11-02. Spec: `quiet-plan:docs/next/PLAN-QUIET.md`, section "0.7.0". Evidence: `docs/next/quiet/*` on `quiet-plan`, `plugin/sub-human` at 0.5.8, the 0.6.0 worktree as it stands (read only), `gh issue list`, and the `drop-row-statusline` history.

I assume 0.6.0 has shipped: canonical lines, receipts in the debug log, Claude-only text as context, readable plan names (the plan label replaces the hex stub), help, invite, leave, `sessionTitle`, and the guard (#35). `row closed` and `✓ sent` are already gone.

## Two findings that change the plan

1. **Item 7 has been tried before and rolled back.** The plugin shipped a `settings.json` `subagentStatusLine` until 0.5.2. Commit `cb5e4fa` removed it because the plugin directory refuses any command path the shell computes (`COMMAND_PATH_COMPUTED`, re-implemented in `scripts/directory-lint.ts`, whose own test case is the old `"${SUB_HUMAN_HOME:-$HOME/.sub-human}/bin/row-status"`). The only form the lint accepts is a literal `${CLAUDE_PLUGIN_ROOT}/<file>`, and Claude Code 2.1.296 does not expand that variable in `subagentStatusLine` (PRESENCE L12, live). PRESENCE's own workaround, `"$HOME/.sub-human/bin/row-status"`, fails the lint. A person's own `subagentStatusLine` also overrides the plugin's. As specified, item 7 can't ship.
2. **Item 4 has no mechanism.** Claude Code picks the plan file: `<plansDir>/<random slug>.md`, one per session (cc-2.1.296-tasks-plans S3.1). `exitplan-normalize` reads that file into every ExitPlanMode. The plugin can't give a plan its own file without a Claude Code change. The backup and restore it would replace has been verified live, and the problem it fixes (the footer naming your own file, R19) is rated "CC (low impact)" in EVALUATION §4.

Two smaller findings:
- **Spike 3 is already answered.** PRESENCE B1 found that the native view's `_internal` filter also feeds the 5 s auto-reset check. Marking task #1 `_internal` would remove the thing that holds off the reset. Take the fallback: filter it only in sub-human's own renderings.
- **#9 may already have a free fix.** 0.6.0 now denies review calls with an empty `permissionDecisionReason` and puts the words in `additionalContext` (`hooks/consent.ts:284` in the worktree). The plan-save deny (`edit.ts` `storedCheck`, `hooks/consent.ts:581`) still sends a red reason. If an empty reason draws nothing red, the same one-line change fixes #9 without `ui.render`. It needs a 5-minute live check of what 2.1.296 draws for an empty-reason deny.

## Cheaper bundles

**The suggested 2 + 5 + 7 + 9:** 7 is blocked, so this is really 2 + 5 + 9. That gets the two heaviest defects (#34 and the stale row and its tokens) but leaves the `Backgrounded agent` block and the hand-back turns, which 6 removes almost for free while 5 is being rewritten.

**Recommended bundle: 2 + 5 + 6, a small 3 (#9 and "Entered plan mode"), and 10.** Move 1 and 9 into 0.6.0. 8 is a gated extra if time allows. By ledger weight that captures roughly 85-90% of 0.7.0's user-visible value: #34, the red save, the false banner, the stale row, the spawn block, the hand-back turns, the tokens. It drops the blocked item (7), the item with no mechanism (4), the speculative one (title redraw), and one task #1 approach.

## Move into 0.6.0, or drop

- **Into 0.6.0 (cheap, stable, plugin-only):** item 1, the frame line. From item 9: the `claude` filter, task #1 out of every rendering, and the reap if small. From item 3: the empty-reason deny for #9, if a quick probe shows nothing red is drawn. That matches what 0.6.0 already does for review denies.
- **Drop:** item 4 (no mechanism), the `_internal` half of item 9 (answered: it breaks the reset), and the title half of item 3 (probe 9 makes it very unlikely).
- **Park behind a CC request:** item 7.

## Recommended scope for 0.7.0

0.7.0 "plan mode that keeps your mode, one quiet row":
1. Spike 1, measuring dialogs as well as the mode. Then card-first objection, the "No" path keeps the note, one exit (#34). If the spike fails, use the fallback and reopen the pane question for reviews.
2. One room row: delete participant rows (5), spawned by `$.agent.spawn` (6), with no hand-back.
3. `ui.render` hides, only for what 0.6.0 couldn't fix: #9 (if still red) and "Entered plan mode" while a review is open.
4. Optional, gated: the `Waiting for 1 background agent` redraw (8).
5. Verify: the two-person scene plus a no-plan scene, with the criteria above.

New early-access contract entries: `$.agent.spawn`, `ui.render` ToolResult/ToolUse scoping, and (if 8) `TurnDuration` plus `$.agent.list`. That is three or four, down from about seven in the full spec.

## Overall verdict

0.7.0 as written mixes two real defects with polish and two items that can't ship. The real defects, #34 (your partner's plan costs you your permission mode, in 3 of 3 objections) and the 1+N row (a stale, wrong label all session, about 7k tokens per extra member, and model turns on leave), sit squarely on "neither holds the other back" and "feel native". They are worth fixing before anything else is built on top of rooms. Most of the row work is deletion, which lowers risk. The frame line and the `claude` and task #1 filters are cheap enough to go out in 0.6.0. The `subagentStatusLine` presence label is blocked by the plugin directory's lint and an unexpanded variable (it was already reverted once). One plan file per plan has no mechanism. The title redraw is unlikely to work. Cut all three. Trimmed this way, 0.7.0 is a short release, perhaps a third of the spec. It should go ahead of pairing tools because it fixes how the room behaves under any workflow, and pairing would inherit both defects. It should stay small so that close-end pairing (follow, then suggest) can be the headline of 0.8.0 rather than wait behind presence and ceremony polish. If spike 1 shows the mode still can't survive inside plan mode without a third dialog, that result is the evidence to reopen D3 for reviews, not a reason to build more around plan mode.
